# simai_transformer · 舞萌 DX 谱面生成工具

输入音乐和目标等级，生成可在 Simai 工具中继续编辑、检查和试玩的舞萌 DX 谱面草稿。支持 Tap、Hold、Slide、Touch 等音符，以及等级和风格条件。

**当前开发主路线是 ChartComposer：模型族 `chart_composer_v1`，新训练默认架构 `audio_grounded_v3`。** 本文按 2026-10-26 的工作区实现核实。旧 event、song-form 和 stream 模型保留各自的兼容入口；它们的参数、检查点和输出文件不完全相同。

### 第一次接触制谱？先认识这些词

| 名词 | 可以怎样理解 |
| --- | --- |
| Tap / Hold / Slide / Touch | Tap 是点按音符；Hold 是按住一段时间的长条；Slide 是俗称“星星”的滑条；Touch 是屏幕上的触摸音符，需要长按的叫 TouchHold。 |
| BPM | 每分钟有多少拍，决定节拍网格的速度。BPM 填错，往往越往后越对不上音乐。 |
| 首拍偏移 `first` | 谱面第 0 拍对应原音频的第几秒，用来对齐网格起点。开头可以空拍，所以它不等于第一个音符的出现时间。 |
| 音符头与事件组 | 一个音符的起点算一个音符头；同一时刻的音符合为一个事件组。例如双押 `1/5` 是 1 个事件组、2 个音符头。 |
| checkpoint / 检查点 | 保存模型权重和配置的 `.pt` 文件。先加载兼容模型，才能生成谱面。 |

## 1. 启动程序

### 准备工作

- Windows，以及可用的 **64位 Python 3.11或3.12**。启动脚本原有自动选择范围为Python 3.10–3.13；升级系统Python后仍需检查项目环境及依赖，不能直接沿用已卸载版本的入口。
- 第一次安装依赖时需要网络。NVIDIA 显卡可加速训练和生成；没有可用 CUDA 时也可使用 CPU，速度通常较慢。
- 若只做生成，准备一个本项目支持的 `.pt` 模型文件，以及一首音频。无需先预处理训练集。

### 一键启动本地网页（WebUI）

在项目根目录双击 **`START_WEBUI.bat`**。脚本检查 Python 和依赖，通常创建或复用项目的 `.venv` 环境，再启动本地 WebUI。终端会显示实际使用的 Python 路径和网页地址。

默认地址是 [http://127.0.0.1:7860](http://127.0.0.1:7860)。浏览器没有自动打开时，手动访问终端显示的地址。训练或生成期间保持启动窗口打开。

也可以在项目根目录打开 PowerShell，执行：

```powershell
.\START_WEBUI.bat
```

| 常用命令 | 用途 |
| --- | --- |
| `.\START_WEBUI.bat --check` | 检查环境，不安装依赖、不启动服务 |
| `.\START_WEBUI.bat --cpu` | 使用 CPU 环境启动 |
| `.\START_WEBUI.bat --cuda` | 要求当前 Python 环境能够访问 CUDA；检查不通过会报错 |
| `.\START_WEBUI.bat --port 7870` | 默认端口被占用时，改用 7870 |
| `.\START_WEBUI.bat --no-browser` | 启动服务，由你手动打开网页 |

详细安装、指定 Python 与环境修复见 [Windows 启动说明](docs/WINDOWS_QUICKSTART.md)。

## 2. 第一次生成谱面

在主工作台根路径 `/` 的 **“生成谱面”** 页操作，训练则进入同一工作台的训练页。独立 `/composer` 页面已弃用，新参数只在主工作台维护。

1. **导入模型。** 选择或填写 `.pt` 路径，点击 **“检查生成 checkpoint 类型”**。`checkpoint` 就是保存了模型权重和配置的文件。确认识别结果是 `chart_composer_v1`，页面才会显示对应参数。旧模型会显示它们自己的设置。
2. **导入音乐。** 上传音频，或填写本机音频的完整路径。第一次优先使用你能确认 BPM 和节拍起点的恒速歌曲，方便检查结果。
3. **对齐节拍。** 填写已知 BPM 和首拍偏移 `first`。例如谱面第 0 拍对应音频第 0.5 秒，`first` 就填 `0.5`。暂不清楚时可从 `0` 开始试听校准；BPM 留空会自动估计。
4. **选择等级。** 使用界面的等级基准，再按需要勾选“星星”“Hold”等偏好。第一次先用等级预设，保留高级 Radar / Style 数值。
5. **确认起始生成参数。** 展开 **“Composer 生成参数”**，先使用下面这组便于比较的起始配置。各项作用见第 3 节，配置本身不保证成谱质量。

   - 候选拍位温度：`0.55`
   - 动作配置温度：`0.85`
   - 学习负荷曲线引导强度：`1`
   - 抑制 Touch 历史自强化：开启；Touch 历史放大上限：`1`
   - Touch 组合策略：开放 Touch（按钮仍最多两头）；想复现旧限制时选择旧版双头限制
   - 动机记忆强度：`1`；只有训练时启用了动机记忆的模型才生效
   - 选时历史权重：`1`
   - 动作历史权重：`1`
   - 动作类别温度：`1`；动作类别 min-p：`0`
   - 同键最短间隔：`50 ms`
   - 最大事件数：`0`
   - condition JSON：留空
   - 拦截 Slide 撞尾（TapOnSlide）：保持关闭

6. **点击“生成谱面”，查看任务与日志。** 首次运行可能需要分析音频和建立缓存。比较参数时填一个固定随机种子，例如 `12345`；想尝试另一份结果时可以换种子。
7. **打开生成结果。** 查看 `maidata.txt` 和 `maidata.composer.json`。将谱面与对应音频放入你使用的 Simai 编辑器或播放器，检查节拍、衔接和手法，再编辑、试玩。

**模型选对、时间对齐、先用预设**，比同时改很多参数更容易得到可比较的结果。报告里没有检测到冲突，也仍需人工检查实际手法。

## 3. 生成参数说明

以下以 **ChartComposer 当前生成入口**为准。表中的起始值是操作参考；页面会记住你之前保存的设置，实际值以本次任务摘要和报告为准。

### 3.1 文件、设备与节拍

| 界面参数 | 含义与填写方法 |
| --- | --- |
| 模型 / checkpoint 路径 | 选择兼容的 `.pt` 文件。先检查类型；文件名中的 v7、v8 等只是实验命名，不能代替模型族和合同检查。`composer_last.pt` 保存训练状态，`composer_inference.pt` 是较轻的生成导出；两者可能来自不同保存时刻。 |
| 音频路径 | 这次要生成谱面的歌曲。更换音频后重新检查 BPM 与 `first`。音频特征会自动分析和缓存。 |
| 输出路径 | `maidata.txt` 的保存位置。主工作台会在所选目录下增加任务 ID 子目录，让多次结果各自保存；实际路径会显示在任务中。 |
| 生成设备 | `auto` 自动选择可用 CUDA，否则用 CPU；`cuda` 指定 NVIDIA CUDA；`cpu` 使用处理器。显存不足时可改 CPU。 |
| BPM | 每分钟的拍数，必须大于 0。留空自动估计；已知准确值时直接填写。整首逐渐错拍通常应先核对 BPM。 |
| 首拍偏移 / 秒（`first`） | 谱面第 0 拍在音频中的绝对秒数。`0.5` 表示第 0 拍在音频 0.5 秒；负值表示第 0 拍早于音频开头。它与“第一个实际音符在何时出现”不同，开头还可以有休止。 |
| 手动 tempo map JSON | 歌曲确实变速时填写。`beat` 是谱面拍位，`bpm` 是从该拍开始的速度；必须从 beat 0 开始、严格递增。填写后优先于单独的 BPM。普通恒速歌曲留空即可。 |

例如，从第 32 拍开始由 180 BPM 改为 150 BPM：

```json
[
  {"beat": "0", "bpm": 180},
  {"beat": "32", "bpm": 150}
]
```

固定 BPM 时，可用 `时间（秒）= first + 拍位 × 60 / BPM` 检查对齐。例如 120 BPM、`first=0.5` 时，第 4 拍对应音频 2.5 秒。Composer 在没有手动 tempo map 时使用一个填写或估计的 BPM；旧模型的“Tempo mode 自动变速”选项不控制此入口。

导出会保留完整的手动变速表。即使短跑或模型提前结束落音，末尾 E 也会覆盖保留的最后变速点，因此可能留下空尾；这不表示空尾部分已经完成写谱。

### 3.2 等级与快捷偏好

主工作台提供 **12.0–15.0 的连续等级基准**，按 0.1 档或插值填写相应 Radar / Style。等级是训练条件，不是生成后测得的官方定数；超出模型熟悉的数据范围，效果需要单独验证。

偏好按钮是在等级基准上联动调整多个条件。**偏好力度**越高，偏离基准越多；新手从较小力度开始，每次先改一种偏好。

| 偏好 | 主要调整方向 |
| --- | --- |
| 键盘 | 增加 Tap、和弦与部分连打倾向，减少 Slide / Touch 倾向 |
| 星星 | 增加 Slide、滑条量和连续滑条倾向 |
| 技巧 | 调整滑条复杂度、连续滑条和方向性等统计条件 |
| 和弦 | 增加同拍多音符的倾向 |
| Hold | 增加长条倾向 |
| Touch | 增加触摸音符倾向 |
| 移动 | 调整方向性及滑条量相关条件 |

这些偏好是统计条件的组合。“技巧”“移动”没有对应完整的双手动作标签，实际手法仍要看成谱。

### 3.3 Radar：整体负荷与配置统计

Radar 各项取值为 **0–1**，表示归一化的谱面统计目标。建议先沿用等级预设，再小幅修改。把某项设为 1 不等于效果最佳，也不是要求每拍都使用该配置。

| 界面名称 / 字段 | 数值表达什么 | 调高后请求的方向 |
| --- | --- | --- |
| 整体密度 `note_density` | 每秒音符头数量除以 16；例如 `0.30` 对应统计目标约 4.8 heads/s | 更高的整体起音负荷 |
| 峰值密度 `peak` | 最密一秒内的起音事件组数除以 32；同拍多押算一组 | 更突出的局部密集段 |
| 滑条量 `sweep` | Slide 头比例与路径端点环距的组合 | 更多或端点跨度更大的滑条 |
| 滑条复杂度 `slide_tricky` | Slide 比例与程序判定的复杂路径比例的组合 | 更多复杂滑条相关配置 |
| 连续滑条 `slide_sequence` | Slide 比例与短拍距连续 Slide 的比例的组合 | 更连续的滑条配置 |
| 同键连打 `jack` | 相邻起音组的短间隔同键重复统计 | 更多同键连续敲击 |
| 和弦比例 `chord` | 有音事件组中同拍多音符事件组的占比 | 更多双押或其他同拍组合 |

整体密度按**音符头**计数，双押 `1/5` 算 2 个头；峰值密度按**事件组**计数，同一次双押只算 1 组。前者描述总体物量，后者描述最密一秒的起音节奏，两项都不等于音乐响度。

### 3.4 Style：音符类型与写法倾向

Style 也取 **0–1**。这些值进入模型作为条件，不是生成后强制兑现的配额。类型比例会与等级、密度、历史配置和合法性约束共同影响输出。

| 界面名称 / 字段 | 含义与使用建议 |
| --- | --- |
| Tap 倾向 `tap_bias` | Tap 头占比，包含带 Break 修饰的 Tap。想增加其他类型时，可以配合降低此项。 |
| Slide 倾向 `slide_bias` | Slide 头占比。想增加滑星，先小幅提高此项，或使用“星星”偏好。 |
| Hold 倾向 `hold_bias` | Hold 与 TouchHold 头的占比。 |
| Touch 倾向 `touch_bias` | Touch 与 TouchHold 头的占比。TouchHold 同时计入 Hold 和 Touch，因此这些比例不严格互斥，无需强制加总为 1。 |
| 和弦倾向 `chord_bias` | 与 Radar 的 `chord` 使用同一项同拍多音符事件组比例；建议两项保持一致。 |
| 节奏贴合 `melody_following` | 起音与音频起音附近位置的匹配统计代理；字段沿用英文旧名，没有声部或音高标签，不能用它指定跟随人声旋律。 |
| 模式复用 `pattern_reuse` | 相同的非恒定四拍配置签名重复率。它控制的是局部配置重复相关条件，不直接指定主歌、副歌呼应。 |
| 方向性 `directionality` | 有效单键转移的净旋向一致度。数值更大表示更统一的旋向倾向，但不指定顺时针还是逆时针。 |

想试较多 Slide / Hold 时，可以在等级预设基础上小幅调整，例如 Tap `0.70`、Slide `0.16`、Hold `0.09`、Touch `0.06`。这是试验起点；是否真的改善，需要固定音频、模型和种子做比较。

### 3.5 Composer 采样与约束

| 界面名称 / 字段 | 起始值与范围 | 含义和调节影响 |
| --- | --- | --- |
| 候选拍位温度 `pointer_temperature` | `0.55`；非负数 | 控制下一组音符的落点。audio_grounded_v3在正温度下保留模型预测的时间区间概率，只在区间内部调节随机程度；降低更集中，提高更随机。`0`直接取全体候选最高分。它不是BPM或密度倍率。 |
| 动作配置温度 `action_temperature` | `0.85`；非负数 | 控制同一类中的按键、修饰和时值选择。正温度且下面的类别控件为默认值时，保留音符大类及 Touch 环区概率，仅在组内调温和截断；要调整类型切换，请使用“动作类别温度”。可先试 `0.80–0.90`。 |
| 动作类别温度 `action_type_temperature` | `1`；`0–2` | 单独调节 Tap / Hold / Slide / Touch 四类概率。`1` 保留模型原概率，小于1更集中于当前高概率类型，大于1更分散；`0` 每个槽只保留最高概率类型，但类内仍可随机。STOP结束概率和Touch内部A–E相对比例保留。动作配置温度为0时，此控件不生效。 |
| 动作类别 min-p `action_type_min_p` | `0`；`0–1` | 过滤概率过低的类型；例如 `0.02` 会去掉概率低于最高类型概率2%的类别。`0` 不过滤。它按四类工作，不单独删掉低概率Touch环区；过大也可能删掉合理的稀有Hold或Slide。仅正动作配置温度生效。 |
| 抑制 Touch 历史自强化 `touch_history_guard` | 默认开启 | 限制已生成历史继续抬高 Touch 概率；实际改变提案时额外检查新增报告级 hard 冲突。仅作用于 `audio_grounded_v3` 且动作温度大于 0。主界面可取消勾选做对照；CLI 对应 `--touch-history-guard` / `--no-touch-history-guard`。 |
| Touch 历史放大上限 `touch_history_bound` | `1`；`0–4` | 越小，限制越强。`0` 不允许历史在纯音频分支之上额外提高 Touch 对非 Touch 的赔率；`1` 允许最多额外乘约 2.72。此定义在温度和物理过滤前成立，并非最终 Touch 百分比。保护关闭时不生效。先保持 `1`；Touch 仍偏多时固定音频和种子，比较 `0.5` 或 `0`。 |
| Temperature / 总温度 `temperature` | CLI/API兼容回退值 | 主界面在Composer下隐藏该控件。仅CLI/API没有填写独立温度时使用；主界面请直接设置上面两项温度。 |
| 学习负荷曲线引导强度 `curve_strength` | `1`；`0–2` | 调节模型学习到的负荷、粗规划与历史负荷差引导。`0` 关闭这些引导，`1` 使用正常强度。提高后更强调预测规划，可能让密集处更密，也可能让休止处更疏；不是全曲音符数量乘数。 |
| 选时历史权重 `pointer_history_strength` | `1`；`0–1` | 只控制下一事件的时间选择。`1` 使用完整历史修正，`0` 使用音频选位分支；新手先保持 `1`。 |
| 动作历史权重 `action_history_strength` | `1`；`0–1` | 控制audio_grounded_v3的动作解码上下文。`1` 使用完整历史，`0` 使用音频动作分支；降低它可能削弱跨拍配置关联。旧版此值与选时历史权重绑定；若要复现旧版 `0.65`，需要把两项都设为 `0.65`。 |
| 同键最短间隔 `min_same_head_ms` | `50`；`0–200 ms` | 拦截同一实际键区过快重复的起点；`0` 关闭这一间隔限制。它不要求所有相邻事件都间隔 50 ms，不同键仍可交错。增大可能减少同键密集配置。 |
| 拦截 Slide 撞尾 `intercept_tap_on_slide` | 默认关闭 | 常规提案关闭时对 TapOnSlide 仅报告；开启后在生成与后处理阶段拦截该类冲突。Touch 历史保护实际触发的提案还需通过额外安全检查。它不是全部无理检测的总开关。 |
| 最大事件数 `max_events` | `0`；非负整数 | `0` 使用程序默认的大预算，并依据音频边界和模型结束信号（EOS）停止；正数限制事件组总数。它用于短跑或资源控制，不是目标音符数量。上限过低会截短谱面。 |
| 随机种子 `seed` | 可留空；非负整数 | 留空每次抽一个新种子；填写后便于复测。`0` 也是固定种子。比较参数时保持同一模型、音频、时间设置、程序版本和种子；更换运行环境仍可能有浮点差异。 |
| condition JSON `condition_file` | 留空 | 从文件覆盖部分等级、Radar 或 Style；优先级与格式见下节。新手直接使用界面即可。 |

温度 **0** 表示贪心选择，即直接选最高分候选或音符。两项独立温度都为 0 时，换种子通常不会换结果。动作温度为 0 时按槽依次选择当前最高分原子，直到STOP或无法继续；一拍仍可能选出多押。它可能更偏向模型高置信度的少数配置，不能当作保持类型分布的普通降温。

使用默认类别控件时，正温度下的时间区间、音符类别和Touch环区仍按模型的宏观概率抽样。因此配置温度`0.01`也不等于贪心。类别控件先保持`1 / 0`；本轮固定音频双种子中，“动作历史1 + 类别0.85 / 0.02 + Touch保护关闭”的组合显著推高了Touch占比，不能作为通用推荐。调整类别时应固定其他参数，对照是否损失合理的稀有配置。

**Touch 倾向和 Touch 保护怎样配合？** Style 中的“Touch 倾向”告诉模型你希望什么风格；“抑制 Touch 历史自强化”限制历史额外推高概率。上限填 `0` 仍允许模型按音频预测生成 Touch。任务摘要会区分“已请求”和“已生效”，最终占比仍需查看生成结果。

| 新增生成参数 | 怎样使用 |
| --- | --- |
| Touch 组合策略 `touch_layout_policy` | 默认 `open`：Touch 不再消耗按钮的两头预算，可生成三颗及更多 Touch；重复占用、同头间隔和现有冲突检查仍生效。这不会自动保证所有远距离 Touch 组合都能双手完成。`legacy_two_heads` 恢复旧计数及采样限制，适合复现旧结果。 |
| 动机记忆强度 `motif_strength` | 范围0–2，默认1；0关闭该分支。只有检查点的 `motif_memory_policy` 已启用且经过训练才有效。它从音频相似的先前段落检索已经生成的配置，作为软提示，不强制复制；首个相关段落或没有匹配时没有提示。当前只辅助配置选择，不直接改选拍或结束判断。 |

Composer 使用“候选拍位温度”和“动作配置温度”两个控件。通用 Temperature 在该模型下隐藏；要测试完全贪心，请把**两个独立温度都设为0**。

### 3.6 condition JSON 的优先级

可以创建一个 UTF-8 JSON 文件，在“condition JSON”中填写它的路径。例如只调整等级和部分风格：

```json
{
  "level": 13.3,
  "style": {
    "tap_bias": 0.70,
    "slide_bias": 0.16,
    "hold_bias": 0.09,
    "touch_bias": 0.06
  }
}
```

生效顺序是：**程序缺省值 → 当前界面条件 → JSON 文件中明确填写的字段**。文件未填写的字段保留界面值；文件写了 `level`，它就优先于界面等级。CLI 没有界面条件这一步，会用程序缺省值补齐文件缺省字段。

主工作台会把本次最终条件保存为任务目录中的 `condition.json`，方便复查。调整界面后结果不变时，先检查是否仍被该文件覆盖。

文件还可设置 `difficulty`（1–6，默认 5），指定导出的 `&inote_N` 和 `&lv_N` 槽位。它与目标等级 `level` 不同，不会改变模型的等级条件；超出范围会在加载权重前报错。

### 3.7 手绘强度曲线与旧模型参数的适用范围

**当前 Composer 生成入口尚未接入手绘强度曲线或手工休止区。** “强度曲线”页可查看音频参考，但该编辑曲线不会作为 Composer 生成输入。上面的“学习负荷曲线引导强度”使用模型自己预测的负荷，不能用它把手绘曲线传入生成器。

Top-p、重复惩罚、CFG、token 上限、固定 division、手动 meter map、旧模型 Planner / Motif 和后处理面板也不是当前 Composer 的生成参数。切换到旧 event、song-form 或 stream 检查点时，再按该模型的界面及对应文档操作。Composer 内部的候选截断和物理审计有自己的实现，不受旧模型同名控件统一控制。

## 4. 按问题调参

每次只改一组参数，并固定随机种子。先保存一份基准结果，才容易判断改动是否有用。

| 现象 | 先检查 | 再尝试 |
| --- | --- | --- |
| 全曲始终提前或延后相同时间 | `first`，以及播放器是否使用同一份音频 | 校准起点后重新生成 |
| 开头对，后面越来越偏 | BPM、真实变速点和 tempo map | 修正时间设置；采样温度解决不了时钟漂移 |
| 大多是 Tap，滑星或长条少 | 实际 Style、condition 文件覆盖、所用检查点 | 小幅提高 Slide / Hold 倾向并配合降低 Tap；保持动作温度为正数后比较 |
| 节奏随机、碎音较多 | BPM、首拍、候选拍位温度 | 将候选拍位温度从 `0.55` 小幅降到 `0.50`；仍需检查模型和输出报告 |
| 配置单调 | 两项温度是否都为 0、风格条件是否过于保守 | 固定拍位温度，略提高动作温度，或尝试另一种子 |
| 音符类型频繁跳换 | 动作历史权重、类别控件、Touch保护 | 类别先保持1 / 0，开启Touch保护；每次只改一项并固定种子，低类别温度也可能放大高概率Touch |
| 同键重复太快 | 同键间隔、报告中的拦截和冲突 | 小幅提高同键最短间隔，检查是否损失合理配置 |
| 中途结束或后半段很空 | `stop_reason`、最大事件数、音频边界和模型 EOS | 若触发 `max_events`，恢复 `0` 或提高上限；其他情况需检查具体报告 |
| 画了曲线却没有影响 | 当前模型族 | Composer 尚未接入编辑曲线；对支持的旧模型查阅[曲线说明](docs/CURVE_DENSITY_FEEDBACK.md) |
| 改了参数却没有变化 | 任务中记录的实际条件、独立温度和 seed | 检查 condition 覆盖；主工作台改独立温度，不只改总温度 |
| 显存不足 | 是否同时运行多个训练或生成任务 | 停止自己不需要的任务，或选择 CPU；训练时另行减小 batch size |

类型更丰富、没有语法错误或自动检测冲突更少，都不能单独证明谱面更好玩。保留固定歌曲的对照，并检查对音、段落写法和实际双手动作。

## 5. 输出文件在哪里，怎么看

### 主工作台与命令行的保存区别

主工作台通常写入类似目录：

```text
webui_workspace/generated/<任务ID>/
├─ maidata.txt             可导入 Simai 工具的谱面
├─ maidata.composer.json   生成参数、事件数、停止原因和审计报告
├─ condition.json          本次实际使用的等级、Radar / Style
└─ tempo.json              使用手动变速表时保存
```

如果指定其他输出目录或文件名，以任务显示的实际路径为准。

- **主工作台：** 为每次任务创建独立子目录，并额外保存本次的 `condition.json`；使用手动变速表时再保存 `tempo.json`。
- **命令行（CLI）：** 直接写入指定路径，输出谱面 TXT 和 `.composer.json`，不自动增加任务 ID 目录或上述两个独立配置文件。
- **原音频：** 生成器不会自动复制音频。在播放器中使用时，按播放器要求放置或选择同一份音频。

### 阅读 `.composer.json` 报告

`.composer.json` 重点查看：

- **实际参数与条件：** `seed`、两项温度、`condition`、模型保存轮数、权重指纹等，用于复现和确认设置。
- **停止原因：** `stop_reason`，区分预算触顶、模型结束与音频范围耗尽。
- **生成过程约束：** `guard` 的拒绝原因和跳过候选数，帮助判断哪些配置被拦截。
- **物理审计：** `playability`，查看检测、修复及残留问题；不同类别可能执行报告或拦截策略。
- **学习负荷曲线与粗规划：** 支持的检查点会记录模型预测及实际生成的负荷统计。这些是诊断信息，不是音乐质量评分。

旧模型可能输出 `.chart.json`、`.quality.json` 或 `.stream.json`，请按对应模型阅读。Composer 当前直接输出的主要结果是 TXT 与 `.composer.json`。

## 6. 准备数据和训练

已有兼容 checkpoint 时，可以直接生成；下面用于从头训练或继续改进自己的模型。

### 6.1 准备原始数据

每首歌一个目录，放原谱和对应音频。新手建议使用 `track.mp3`、`track.wav` 或 `track.ogg` 命名，避免自动匹配不明确。

```text
dataset/
├─ song_001/
│  ├─ maidata.txt
│  └─ track.mp3
└─ song_002/
   ├─ maidata.txt
   └─ track.wav
```

`maidata.txt` 中的 `&lv_N` 和 `&inote_N` 要对应同一个难度槽，BPM 与 `&first` 应与音频对齐。保留原始文件；只保留预处理缓存不够。`manifest` 是程序生成的数据清单，记录训练需要读取的文件和元数据。

`examples/maimai_training_demo.zip` 是小型合成示例，可以测试导入、预处理与训练流程，不能代表真实音乐上的成谱质量。

### 6.2 在主工作台训练

1. 进入 **“训练模型”**，选择模型族 **`chart_composer_v1`**；新训练的架构选择 **`audio_grounded_v3`**。
2. 上传数据集 ZIP 或填写原始目录，点击 **“预处理当前目录”**。第一次分析音频可能较慢，观察任务进度。
3. 通过 **“选择本次训练来源”** 勾选数据集，点击 **“应用勾选的数据集”**，再 **“检查所选训练来源”**。确认显示的实际训练清单是本次希望使用的数据；切换“当前预处理数据集”不会自动替换既有训练勾选。
4. 选择训练方式和新的 checkpoint 输出目录。先用小批次、有限步数验证缓存、前向计算与保存流程，再增加训练时长。
5. 开始训练，查看准备进度、实际学习率、有效槽位数、loss 和速度。loss 是模型在训练目标上的误差；它变低也不代表自由生成一定更好。用固定歌曲及种子比较后续检查点的实际结果。

**怎么看loss：** “累计总loss”是当前轮、本次运行截至目前的平均值，后期变化会被摊平；“最近约250个有效batch”单独显示近期误差，遇到不同歌曲仍会波动。总值是选位、精确动作和辅助任务的加权和，没有统一的“必须小于1”标准；判断训练进展应比较完整轮或固定输入，并查看动作、音频动作等分项。详见[本次loss诊断](docs/COMPOSER_LOSS_DIAGNOSIS_20261025_ZH.md)。

| 训练方式 | 适用场景 | 注意事项 |
| --- | --- | --- |
| fresh 从头训练 | 没有兼容模型，或建立新架构 | 从随机权重开始，需要足够训练数据和时间 |
| resume 继续训练 | 严格延续同一训练合同和优化器状态 | 使用可续训的训练 checkpoint；合同、数据与结构需通过检查 |
| finetune 微调 | 加载兼容旧权重，开展新的训练阶段 | 使用新输出目录，保留父模型；词表和主干尺寸仍需匹配 |

这里的**训练合同**是程序对模型输入、数据处理和训练目标的一组约定。合同变化后，旧权重可能仍能生成，但不能直接当作完全相同的训练继续 resume。

**目录版本号与训练合同版本号是两回事。** 本工作区保留的 `Prism_composer_v7` 属于旧 v8 合同，`Prism_composer_v8` 属于旧 v9 合同，`Prism_composer_v9` 属于旧 v10 合同；当前合同为 `chart_composer_training_v11_history_relation_mask`。这些旧文件仍可生成或显式 finetune，不能直接 resume 到新合同。已有模型的实际尺寸是384维、6层、8头、前馈维度1536，与表单的新训练默认值不同；CLI / API 会继承未显式填写的父模型主干参数，显式填写时仍需兼容。

动机分支另有训练约定：启用了动机、但没有`motif_training_policy=symbolic_masked_archive_v1`的旧实验模型，仍可生成；继续训练请选finetune和新目录。检查点检查会说明原因。没有开启动机的模型不受这项迁移影响。

本机此前的v9 / 20轮目标及64×6重分批属于历史实验，记录见[原始训练排查](docs/COMPOSER_V9_FRESH_DIAGNOSIS_20261025_ZH.md)和[显存与续训修复](docs/COMPOSER_GPU_RESIDENCY_FIX_20261025_ZH.md)。v11已另存第5轮 / 17,500更新点；v12后续在第5轮发现退化，现已停止，并保留15,500、16,000、17,000完整点。保护修复与实际短训结果见[最新复核](docs/COMPOSER_SDPA_STABILITY_FIX_20261026_ZH.md)。

当前已加载本轮修复的主工作台为[7871](http://127.0.0.1:7871/)。本轮旧7860服务保持原版本；日后重新启动服务，以启动窗口显示的地址及后端能力为准。

### 6.3 常用训练参数

| 参数 | 初学者需要知道的含义 |
| --- | --- |
| Epochs / 训练轮数 | Composer 本次运行的轮数。resume 包含尚未完成的当前轮：第4轮中途恢复，希望到第20轮应填17；第4轮已经完成则填16。finetune 从新阶段第1轮开始。实际结束轮次以任务运行信息为准。更多轮不保证更好的自由生成效果。 |
| Batch size | 每批训练样本数。越大通常占用更多显存；显存不足先减小。默认小批次用于开始验证。 |
| 梯度累积 | 多个小批次后再更新一次参数，用于控制单批显存需求；会改变更新频率。 |
| CPU 算子线程 `cpu_threads` | 控制PyTorch的CPU算子线程，0保留环境/PyTorch设置，范围0–256；与采样准备线程不是同一个参数。GPU训练的小数组处理可试2–4。本机实测2更合适；resume会回填保存值，仍可明确修改。CLI为`--cpu-threads`。 |
| 允许轮中重分 batch 续训 `rebatch_resume` | 主界面仅 resume 可勾选，默认关闭。先检查已有检查点，再勾选并调整 batch 与梯度累积，保持乘积不变（如96×4→64×6），且 `max_steps=0`。程序保留当前轮剩余样本顺序；取消勾选会恢复检查点的批量。CLI 对应 `--rebatch-resume`。已重分批保存后的检查点，后续按相同64×6普通 resume 即可。 |
| 普通 dropout `dropout` | 模型内部随机丢弃的概率，默认 `0.1`，范围 `0–1`。只有 fresh 可修改；resume / finetune 继承模型配置。它与历史、台账或符号分支的遮挡参数分别控制不同部分。 |
| 音频辅助监督权重 `audio_pointer_weight` | 默认0.15，范围0–1。audio_grounded_v3中同时乘在音频选位与音频动作两项辅助损失上，字段名为兼容旧配置而保留。它不是只调整动作分支的独立开关；调低会直接减少总loss，不能据此判断学习改善。更改需finetune。 |
| 历史键位锚定 `history_anchor_policy` | 仅audio_grounded_v3使用。fresh自动为 `parsed_geometry_v3`：读取真实音符头，中心C不占外圈角度，D/E按相邻两键各半表示。已有模型自动继承legacy或v2；resume不能更换。想尝试v3，用finetune与新目录。 |
| 历史记忆幅度策略 `history_memory_policy` | 限制读出的历史特征幅度，避免少数巨大历史向量压过音频。audio_grounded_v3的fresh自动使用“逐事件RMS上限”；旧模型自动继承“兼容旧无约束”，启用保护须明确选择“逐事件RMS上限”并finetune到新目录。 |
| 历史记忆RMS上限 `history_memory_rms_bound` | 默认8，范围1–64；仅“逐事件RMS上限”生效。越小限制越强，过小可能削弱有用历史；不是历史事件数。小于上限的向量保持原幅度，不能据此保证所有内部层都不会放大。resume固定继承。 |
| 历史跨注意力后端 `history_attention_policy` | audio_grounded_v3的fresh自动使用“Math数值保护”，避免本机已复现的BF16融合反向误差；仅保护读取历史的注意力，整体BF16与dropout保留。旧模型自动继承“兼容自动选择”，启用保护须明确选择“Math数值保护”并finetune；生成按检查点继承。 |
| 持续动作状态 `action_state_policy` | fresh自动为 `committed_causal_v2`，在最后已提交拍位查询状态。实验选项 `selected_prefix_v3` 保持选时输入不变，只在动作解码时把同一个已提交前缀推进到选定拍位，每样本增加一次查询。`candidate_prefix_v2` 为所有候选查询，成本更高，且会改变选时输入。旧模型缺字段时按 `committed_legacy_v1` 解释；更换需显式finetune与新目录，不能直接resume。 |
| 跨段落动机记忆 `motif_memory_policy` | 默认关闭 `off`。实验选项 `audio_recurrence_archive_v1` 按音频重复段检索普通历史窗口以外、已经提交的配置。开启会增加新分支，需训练或显式finetune；原模型仅调生成强度不能获得此能力。 |
| 动机档案事件数 `motif_max_events` | 默认16，范围1–32，表示每次配置决策最多读取多少个历史事件组。不是保留多少首歌，也不是强制重复次数。更大可能增加成本；resume继承原值。 |
| Slide 分支因子 `slide_factor_policy` | grounded fresh自动使用 `branch_joint_v2`，把每条分支的路径、终点和时值绑定起来共享学习。`marginal_v1`保留旧解释；新分支迁移时从零贡献开始，仍需微调学习。 |
| 恢复采样 Touch 策略 `touch_layout_policy` | 控制训练中的短程自由采样，fresh自动开放，旧模型自动继承旧双头策略。resume固定继承；改变需finetune。它与本次生成时选择的Touch策略分别记录。 |
| 学习率 | 每次更新参数的步幅；过大可能不稳定。比较微调时同时观察实际学习率和生成效果。 |
| 数值精度 | `auto` 在 CUDA 支持 BF16 时使用 BF16，否则使用 FP32；CPU 也使用 FP32。首次先用 `auto`。 |
| 模型宽度、层数、注意力头、前馈宽度 | 决定模型结构与资源需求。宽度需能被注意力头数整除；继续使用已有权重时要匹配。 |
| 历史事件数 | 每次读取多少组已提交事件；不是秒数。改变训练结构前检查 checkpoint 合同。 |
| 候选数 | 下一事件的候选拍位预算，当前常用 96；修改会改变训练输入与候选覆盖。 |
| 动作槽位 | 同拍动作表示容量，程序可根据原谱自动扩展；不是要求每拍写这么多个音符。 |
| 每轮最大 batch 数 / `max_steps` | 短跑上限，`0` 使用整轮。它按每轮 batch 计数，不是整次训练的优化器总步数。 |
| 准备 workers / `prepare_workers` | 启动时解析谱面、检查缓存的线程数，与训练时逐 batch 准备样本的线程数不同。 |
| 样本准备线程 / `sample_workers` | 训练时准备 CPU 特征的线程数，范围 1–8。更多线程不一定更快：Python 线程争用、同音频源互斥均会影响速度。本机这次选 1；换机器后应短跑测量。 |
| 音频缓存预算、预取 batch 数 | 控制 CPU、内存和供数效率。内存不足时不要一味增加缓存或线程；结合 `data_sec`、`compute_sec` 与主机内存判断瓶颈。 |
| 检查点保存间隔 | 按优化器更新步数保存进度。训练输出还可包含供生成使用的 inference 导出。 |

`allocated` 是活跃张量占用，`reserved` 是 PyTorch 保留的显存，两者不相同。GPU 100% 也可能受到显存驻留压力影响，应同时看**样本/秒**和两种显存数值。训练现在会在完整更新边界按需回收过量闲置缓存，不会每个 batch 清空。全量每轮约94.9万个样本，当前64微批需要14,829次前后向；正常一轮仍可能约一小时。

质量权重和局部标注可在“训练素材”中管理。调整标注或数据分布后使用新的微调阶段；Composer 的具体训练合同与旧模型的反例训练教程并不通用。

**本机下一阶段怎样选：** 若从保留的v12第15,500点启用本轮保护，选择finetune和全新输出目录，明确选择“逐事件RMS上限”、上限8、“Math数值保护”。其他状态和动机设置先继承父模型；本轮短训使用学习率`0.00002`、batch64、梯度累积4、CPU算子线程2、样本准备线程1、预取2。先核查单项loss和固定probe，再延长训练及比较完整歌曲；这些值尚未证明是最优参数。fresh可保持两项策略为“自动”、上限8，不需要照搬微调学习率。不要仅为让总loss数字变小而削减监督或遮挡。

## 7. 命令行生成与常见问题

### 不打开网页，也能生成

在项目根目录的 PowerShell 中，用启动脚本显示的同一个 Python 环境执行。若使用默认项目环境，可参考下面的一行命令；先替换模型和音频路径：

```powershell
.\.venv\Scripts\python.exe -m maichart.composer.generate --checkpoint "checkpoints\my_composer\composer_last.pt" --audio "songs\track.mp3" --bpm 180 --first 0 --level 13.3 --pointer-temperature 0.55 --action-temperature 0.85 --seed 12345 --output "webui_workspace\generated\first_chart\maidata.txt" --device auto
```

查看完整命令行参数：

```powershell
.\.venv\Scripts\python.exe -m maichart.composer.generate --help
.\.venv\Scripts\python.exe -m maichart.composer.train --help
```

CLI 没有填写两项独立温度时，会回退到 `--temperature`，默认 `0.8`；它与主工作台独立温度 `0.55 / 0.85` 的起始组合不同。需要对照时显式填写。

已有条件文件时添加 `--condition-file "condition.json"`；已有变速表文件时添加 `--tempo-map "tempo.json"`。两者的 JSON 格式见前文。TapOnSlide 拦截用 `--intercept-tap-on-slide` 开启、`--no-intercept-tap-on-slide` 关闭；不填写时默认关闭。

本轮新增CLI参数为`--action-history-strength 1 --action-type-temperature 1 --action-type-min-p 0`。主工作台已提供同名含义的控件。默认保留原类别概率；旧选时权重小于1的任务若要严格复现，需显式设置相同的动作历史权重。

### 常见问题

**没有模型能直接生成吗？** 不能。先获取兼容 checkpoint，或准备数据训练。仓库源码与演示数据不包含训练好的正式模型。

**端口被占用、打开的像旧界面怎么办？** 查看启动窗口地址，用 `--port 7870` 改端口。更新源码后重启自己使用的 WebUI，再强制刷新浏览器；同机可能同时运行不同启动时间的服务。

**`unexpected keyword argument 'history_anchor_policy'` 怎么办？** 先更新项目，再重启正在使用的WebUI后端并刷新页面。该字段是当前模型配置的一部分，旧进程或不同目录的代码可能不认识它；不要直接从检查点中删字段。检查点不兼容时页面现在会提示核对代码并重启。

**路径为什么找不到？** 文件选择应指向实际存在的本机文件。命令行里含空格的路径加双引号；界面的路径输入框直接粘贴路径。先确认模型与音频文件，而不是只填它们的目录。

**为什么重新打开还保留上次参数？** 主工作台会保存在浏览器中。先查看本次摘要；“恢复生成默认值”只用于生成设置，“清除全部保存”还会清除训练和路径设置，使用前看按钮说明。

**为什么“训练中”“准备中”很久没有 loss？** 音频、谱面和缓存准备先于第一个训练 batch。查看准备阶段与完整任务日志；重复运行可复用有效缓存。若出现异常，保留日志中的第一处报错及实际参数。

**显示输出目录已被占用怎么办？** 先等使用该目录的训练真正结束，或给另一任务选择不同目录。同目录保护覆盖不同WebUI端口与CLI。`.composer-training.lock`文件保留是正常现象，是否占用由操作系统锁决定；不要靠删文件绕过运行中的训练。

**取消失败怎么办？** 主界面会保留“尚未确认停止”的状态和错误，允许点击“重试取消”。请求在途时按钮暂时禁用；只有任务实际退出后才显示“已中断”。

**检测通过就可以直接发布谱面吗？** 自动检查覆盖语法、边界和部分物理冲突；对音、乐段呼应、手法舒适度与实际难度仍需人工审查和试玩。

## 8. 架构与开发入口

ChartComposer 将生成拆成两步：**选择下一事件时刻，再组合该时刻的音符**。模型读取音频、等级与风格、历史事件和持续动作状态；生成过程中检查占用与冲突，最后编译为 Simai。

```text
音频 + BPM / first / tempo map + 等级 / Radar / Style
  → 音频特征、局部听音与四拍粗规划
  → 候选拍位指针：选择何时落音
  → 同拍动作槽位：选择按键、Hold、Slide、Touch 等
  → 生成约束、MiaCode 审计与 Simai 编译
  → maidata.txt + maidata.composer.json
```

```text
simai_transformer/
├─ START_WEBUI.bat           Windows 启动入口
├─ tools/start_webui.ps1     环境检查与启动脚本
├─ src/maichart/
│  ├─ composer/             当前 Composer 模型、数据、训练与生成
│  ├─ generation/           共用条件、Simai 编译与物理检测
│  ├─ form/                 音频查询、原谱数据及旧 song-form 路线
│  ├─ stream/               旧 stream 路线与部分共用状态组件
│  ├─ training/             其他模型训练及共用工具
│  └─ webui/                主工作台、API 与前端
├─ configs/                 示例配置
├─ examples/                演示素材
├─ tests/                   自动化回归
└─ docs/                    当前功能说明与历史交接记录
```

模型、完整训练数据、缓存、历史生成结果等大型本机产物不随 Git 源码提供。`checkpoints`、`cache` 和 `webui_workspace` 按使用情况生成。

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

需要 Node.js 的前端检查可单独运行：

```powershell
node tests/test_composer_generation_ui.js
node tests/test_composer_training_ui.js
node tests/test_composer_intensity_ui.js
```
