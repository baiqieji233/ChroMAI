# Composer 深入根因排查与修复（2026-10-31）

## 核心发现

上一轮补全有序短句记忆后，模型仍不一定能把短句意图落实到输出。本轮沿着“原谱答案 → 训练 → 类型选择 → 具体配置 → 物理检查 → 重试 → 验证界面”继续检查，发现了几处真实断路。

### 1. 短句意图参与了具体配置，却不能直接决定音符类型

原 `audio_prior_transition_v3` 把事件概率拆成“类型组合的概率”和“这一类型内具体配置的概率”。后者能看 decoder 和短句意图，前者主要看音乐与上一事件类型。把某一类型的所有配置概率加起来，具体配置头的影响恰好消失。因此，即使短句分支有了计划，也不能直接决定这段更多使用 Tap、Hold、Slide 或混合配置。

新训练默认使用 `audio_state_phrase_v4`。保留原来的独立音乐判断，再用一个小网络结合音乐、稳定的短句意图、候选时刻还有哪些持续动作、这次离上一事件多远，修正类型分布与“继续/切换”倾向。没有把上一键的完整符号历史重新当作类型分支的捷径，也没有标注固定左右手。

新修正输出从零开始，升级时保留旧音乐 prior。纯音乐辅助损失仍独立；新修正不能一起被 detach 掉。训练、正常生成、恢复训练三条路径都接入相同输入。STATE50 的剩余时间和开划等待会推进到真正的候选时刻；不会用当前时刻的占用冒充稍后仍然占用，也不会假装能从摘要精确还原未来整条滑轨。

### 2. 不适合当前状态的类型被锁住，重试可能反过来改坏拍位

原流程先采一次类型和配置保持意图，然后最多换八次具体配置，最后才换起音。假如选到当前不适合的持续动作，重试主要在同一类型里找位置、形状和时值，而没有及时重新考虑类型本身。这会让物理过滤影响音乐选择。

现改为同一起音上的完整联合拒绝重采，保留原音乐概率与温度。一次失败不能证明整个类型或整个非单一 shape/phase 不可用，尤其不能把字面量配置整族封掉。

温度为0另有确定性问题：简单“再采一次”仍会得到同一个错误答案。本轮补上有界的决策前缀搜索。第一提案保持原 greedy；被拒绝后，按原有条件概率探索其他时值、细节、位置或类型。最多八个完整提案、三个起音，备选前缀队列上限64。不暗改温度、不加重复惩罚、不重跑音频和历史主干，也不声称这是精确的全局最优搜索。

报告新增首次提案、最终提案、换类型/换配置/换拍位次数，以及有限数量的失败示例。统计涵盖所有试写候选，不能当作最终谱面的逐音符概率。

### 3. 增强训练的长 Slide 判定仍丢了中间交互

正常生成已修复过这一问题，但循环历史增强的检查仍只保留活跃 Slide 本身和最近约0.3秒事件。原生判定需要持续期间的其他输入来还原过程；丢掉它们会误判增强样本及其后续答案是否合法。

现在增强检查和它上游的快速前缀准备都保留相同交互窗口，避免检查阶段已经无法找回上游丢掉的事件。它还改为直接调用 `guard.enforced()`，不再用一个忽略策略差异的简化判断。训练增强与生成不再对同一个静态撞尾提示使用两套执行标准。

### 4. 最终物理报告与真正执行的守卫不是同一设置

旧生成先用守卫检查，最后另建默认配置输出报告。部分 `SlideHeadTap` 在守卫中是 report，在报告里却是 enforce；部分静态 `TapOnSlide` 又属于运行时策略有意保留的参考提示。不能把这些统一说成“没有发现”，也不能把运行时来源都说成静态提示。

最终检查和报告现在共用实际守卫设置，只做一次完整判定。报告保留原生发现及来源，另列实际拦截项、仅报告的硬提示和引擎原动作。没有为了得到零冲突而删掉发现或收紧成新的硬手顺规则。

## 验证与界面中的真实问题

此前主界面承诺留空验证清单会自动留出，但整拍集合路线实际上没有切分，也就没有执行轮末验证。现在先按训练路线的槽位与等级范围筛选可用谱，再按歌曲身份和音频内容分组，把总计约5%的组留给开发集与最终保留集。当前2578首源记录中，2358首具备符合范围的谱，220首不应占用验证名额。显式验证也检查相同歌曲和复制音频的重叠。来源哈希复用已有缓存，避免反复完整读取全量音频。留出为0且没有显式验证清单时，明确表示不验证。

另一个评估偏差是：原验证批数上限总取数据开头，可能一直只看前几首歌。现在有限批次会确定性地分散到整个验证集。验证集若没有可信监督目标会明确报错，不能以零loss冒充优秀结果。

验证生成以前只接收温度、种子和曲数，其他短句搜索设置固定为默认。现在可以使用与手动生成相同的搜索、物理策略、预算、跟随和独立温度设置；条件仍来自每张验证谱，节拍来自歌曲，不自动套入外部强度曲线。抽检曲数按不同音频来源选择，避免两张难度谱占用同一首歌的抽检名额。

界面也修正了以下行为：

- 所有19项学习策略可访问，单项高级设置明确覆盖预设，不再出现两份互相覆盖的短句控件。
- 微调和续训的结构继承项正确锁定并说明原因；续训回填实际恢复参数，不能静默忽略新选择的数据。
- 整拍集合的训练轮数明确为总目标轮数；目标已完成时提示需要增大目标。
- CPU线程0可以执行自动选择；FP16在这条路线不再作为可用选项展示。
- 专用采样温度留空时继承总温度，填0明确表示greedy。
- 参数按用途分为基础、学习与短句、恢复、验证、模型结构、性能与诊断，高级选项收进次级菜单。

操作说明见[主界面参数指南](COMPOSER_STREAM_PARAMETER_GUIDE_20261031_ZH.md)。

## 检查后没有误改的部分

phase损失与细节项中的 `joint - independent` 合起来是完整联合概率，不是一次错误抵消；本轮没有重写它来让loss数值下降。有序目标只在loss中使用，未发现被forward偷读的路径。动作头在真实下一起音上训练，是条件概率分解，也不能单独叫作未来泄漏。

持续动作撤回仍以真实StreamStep日志为准，重建全部状态；保留尾段是上一候选真实采出的延续。本轮修正了日志中“所有候选完整前缀相同”的说法，没有把正常的尾段保留误删。

## 验证结果与范围

Python全量回归4410项通过、13项跳过；最后的验证抽样调整相关55项通过。前端193项通过。隔离浏览器中检查了19项学习策略控件、六组菜单和真实v4检查点读取，未出现JavaScript异常；验证高级参数已改为组内第二级菜单，不与常用项混排。

两组短训使用同一个上一轮有序短句权重、64张真实谱、相同顺序与种子73，batch16、学习率0.0001，各96更新，只切换v3/v4类型策略。第一批主配置损失均为1.4961058；结束累计主配置损失为2.75799/2.75530。新分支出现有效梯度，末尾输出RMS约0.183，均无非有限更新。这个规模证明新通路在学习，尚不能证明整体音乐质量胜出。

### 细节loss是否挤掉常规配置学习

另做了两个真实batch的梯度探针，而没有只根据loss数值调整权重。单歌batch中，细节项/shape＋phase对共享decoder的梯度范数约0.195/0.320，音频侧0.391/0.258；跨8歌batch中分别为0.556/0.614和1.716/0.505。梯度方向接近正交，没有出现压倒共享decoder或明显反向抵消的证据。音频侧确有细节预算较重的信号，应继续观察，但这两个batch不足以支持直接降权。本轮没有借缩放loss改善显示数字。

完整证据见[数值与运行记录](evidence/COMPOSER_DEEP_CAUSE_AUDIT_20261031.json)。原v36两份检查点哈希复核不变。用户随后确认**从头fresh训练50轮**，正式任务使用新目录 `checkpoints/prism_composer_v37`；模型512维、8层、8头、前馈2048、历史128、展开16，batch32、累积1、学习率0.0002、BF16，原有损失与恢复默认预算保留。

正式任务已从主界面后台启动，任务ID `d9f00da7e58f`，入口 `http://127.0.0.1:7860`。启动记录确认不是resume或微调，新策略为 `ordered_phrase_v2 + audio_state_phrase_v4`，开发集实际启用。训练1700个歌曲组、开发45组、最终保留45组。记录时已到第一轮1000更新，没有跳过更新，两份v37检查点已生成；这只是启动快照，不代表50轮已完成。参数、数据划分、日志路径和当前快照见[正式任务记录](evidence/COMPOSER_V37_FRESH_START.json)。

### GPU利用率表述更正与剩余性能问题

此前进度消息中约95%是单次整卡瞬时读数，不能作为持续训练利用率。随后141次逐秒整卡采样的平均值约30.8%、中位数24%，范围5%—95%；另一个稍后的12次Windows训练进程主GPU引擎采样，平均约34.8%，范围20.4%—46.6%。这与用户观察到约40%的情况一致。

同期供数等待很低，尚不能把这次低利用率归因于缓存建立或样本等待。日志中的compute_sec包含CPU发射、同步、恢复采样和数值检查等主循环工作，不能解释成纯GPU忙碌时间。模型内部的串行开销仍值得进一步剖析，本轮不宣称训练效率问题已经全部解决。训练保持运行，未为采样调整batch或停止任务。

这些修复解决的是可定位的学习与执行断路，不能据此承诺所有音乐质量问题都已排尽。短句压缩、音乐关系检索、训练覆盖和人工手感仍需要完整谱面验收。当前软评价主要服务音乐取舍、轨迹与衔接，并非经过人工偏好校准的整段配置评审器；默认单候选时也没有选优作用。
