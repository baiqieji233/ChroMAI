## 2. Touch 集中在 E 区：确认了什么

重新统计本次实际选中的 1,787 张官谱，其可信上下文内有 72,827 个 Touch / TouchHold 头：A 7,382、B 23,726、C 7,451、D 5,200、E 29,068。E 约 39.91%，B 约 32.58%。这是上下文计数，不等于经过质量权重、batch 归一化后的梯度占比，也不能规定某一首音乐应当采用这些比例。

上一完成模型固定音频双种子中，E 占 Touch 的 **67.35% / 91.06%**；用户观察到的集中现象成立。

进一步在种子 `709835971` 的真实生成链路中记录了 1,052 次 slot 0 提案（包含重试）。对相同的掩码 logits：

- 采样前，Touch 条件概率质量中约 **62.05%** 在 E 区；
- 经过旧版组内温度和截断后，E 升至 **71.35%**；B 从 10.56% 降到 5.75%；
- 有 108 次提案原本给 B 区超过 1% 的总概率，却在截断后将其整区清零；C/D 也出现同类情况。

**已修复的采样放大效应：** 原先把所有 Touch / TouchHold 合并后进行 top-p / min-p / top-k。现在保留模型在 T=1 下预测的 A/B/C/D/E 各区概率质量，仅在每区内部选择按键、修饰和时长。Tap、Hold、Slide 的既有大类概率保持方式不变；贪心温度 0 的行为不变，物理掩码继续生效。

这不是等量分配或强行增加某区。模型预测的区域概率仍决定区域选择。回归测试与真实轨迹均验证了每区质量保留；新两条轨迹中“原区概率超过 1% 却被截断清零”的计数均为 0。

**没有据此改动的假设：** Touch 因子没有单独的角向共享字段、C 历史锚到按钮 4、动作历史分支可能继续强化类型重复等，均存在可讨论的结构限制；但原始 ID 嵌入及因果键区特征仍传递信息。本轮未把它们直接当成已证实的主因，也没有为追求环区数量强行改模型、重采样或修改 Style 目标。

## 4. loss 与训练效率

旧 v8 合同将大量 STOP 填充槽纳入平均，旧日志里的 `action_loss≈0.44` 与有效槽合同下的 `≈2.45` 不是同一个标尺。最近阶段实际是从旧 v7 权重微调：第 1 / 2 / 3 轮总 loss 约为 **4.212 / 4.056 / 3.950**，动作 loss 约为 **2.651 / 2.525 / 2.448**，没有观察到停止下降或学习率意外变为零。慢下降与复杂长尾配置、多种可行配谱、旧权重偏好有关的解释仍属于假设，不能用这些日志独立确认。

本轮未通过随意加大学习率、降低损失权重或删除监督目标来制造更低的数值。fresh 训练使用明确的 `1e-4`；早期累计 loss 的下降只证明训练在学习目标，不证明成谱质量。

### 保留的性能修复

1. **历史空槽裁剪。** 原历史输入常为 `[96,128,33]`，真实 batch 最后占用列只有 4。STOP 嵌入本来会被置零再求和，却仍先展开全部嵌入和因子。现在仅裁去 batch 中完全为空的尾部列；内部空位、空历史、33 头满容量都保留。模型结构与权重尺寸不变。
2. **声学查询复用。** 0.5/2/8s 窗口的积分边界合并查询，滞后窗口复用共同终点，区间起点只计算一次。随机数据、空源、单点源、越界/空查询及旧实现对照均保持结果一致。
3. **按本机实测选运行参数。** `sample_workers=1`、PyTorch CPU 线程 4；不是无条件增加线程数。

测量范围及结果：

- 同一个真实 batch、BF16、排除供数：稳定计算均值约 **300ms → 180ms**，峰值分配显存约 **4.47 → 3.74 GiB**。这是隔离测试，不能直接外推端到端。
- 声学三个查询的 1,000 次组合调用约 **0.63 → 0.48s**；特征结果逐元素一致。
- 真实数据端到端短跑：保守的暖缓存基线约 **2.50 batch/s**，最终配置的稳定段约 **2.75 batch/s**。冷缓存重建基线约 2.22 batch/s；应避免用不同缓存状态夸大收益。最终 64 batch 消费 6,144 样本，完成 16 次更新及一次实际恢复采样，last/inference 权重一致，模型与优化器均有限。
- 正式训练 batch 450 快照约 **2.72 batch/s**；`data_sec=67.87`、`compute_sec=94.91`，仍有明显 CPU 供数等待。峰值分配约 4.23 GiB，主机空闲物理内存约 10.88 GiB。初期 12 次瞬时 GPU 采样在 12–85% 之间，**没有证明 GPU 已持续吃满**。

### 测试后撤回的改动

确认了“同源样本成组提交时，线程先争抢同一音频源锁”的调度现象，试做了每源一个任务的并发准备。虽然能够增加不同源的并发，端到端却降到约 **1.54 batch/s**；缩短 Python 线程切换间隔后约 2.00，双线程约 2.21，仍不如单线程。Python 调度/GIL 与主线程发起 GPU 运算之间的争用是有实验支持的解释，但没有完成独立的 GIL 时间剖析。

因此撤回该共享预取器改动和试验性线程切换设置，保留原预取实现。没有把“并发更多”当成性能成功。后续若继续优化供数，应优先评估按歌曲批量查询/矢量化，或有内存上限的多进程方案；不要在运行中的训练上直接改共享加载器。
