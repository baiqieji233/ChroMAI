# Training Monitoring Semantics

This monitoring update preserves the existing validation checkpoint-selection rule: `validation_loss` remains token cross-entropy, so an in-progress run does not suddenly compare its current epoch to a different objective. New epoch metrics expose the auxiliary objective beside that compatibility score.

`loss` and `token_loss` are aliases for token cross-entropy. `planner_loss` is the continuous planner loss; `configuration_loss` is the categorical configuration loss. `objective_loss` reports the combined per-batch objective averaged by window count. `configuration_accuracy` reports the predicted planner class accuracy. These metrics describe training behavior; they are not chart playability scores.

`optimizer_steps_attempted`, `optimizer_steps_successful`, and `amp_skipped_steps` count accumulation-group optimizer attempts and actual `optimizer.step()` calls. The post-step hook fires only if GradScaler permits the update. `amp_scale_end` samples the scaler once at epoch end. `global_step_semantics=successful_optimizer_steps_v1` identifies new checkpoints. When resuming an older checkpoint with no step semantics, the saved counter is retained as an unverified legacy baseline; `global_step_legacy_before_resume` records it, while subsequent increments count successful steps.

Every validation pass resets only the validation dataset's condition-mask RNG to seed 0 before starting its loader/prefetch thread. It preserves the configured mask probability and therefore the expected mask distribution; training RNG is untouched. Validation windows receive the same mask decisions on each epoch. Checkpoints and metrics use `validation_mask_schedule=fixed_seed_0_v1`. Older checkpoint epochs used fresh random validation masks; their expected distribution is the same, but their individual scores are not strictly comparable with the fixed schedule. Resume retains the existing best metric and scheduler state.

The epoch loop logs a lightweight progress line every 60 seconds with phase, consumed batch count, elapsed seconds, and optimizer attempts/successes. It performs no tensor-to-host synchronization for those progress lines. If a prefetch producer fails while reading a dataset item, the original exception is forwarded to the training thread; `run_epoch` closes the iterator on normal max-step completion and producer failure so the background thread cannot keep consuming dataset RNG or appear to complete a partial epoch.
