# Composer 训练数据链路优化交接 · 2026-10-22

## 当前证据与原因

审查基线为 `4428c35`。用户最新任务 `a0bb32b73b71` 已自行停止，
没有结束其他进程。该任务 batch 725 时，累计等待数据 144.08 秒、
计算提交 40.36 秒、总阶段 187.14 秒；约 77% 的阶段时间在等待数据。
此为主机计时，不是精确 CUDA 内核计时。

当时物理空闲约 10 GiB、提交额度空闲约 35 GiB，特征缓存的实际预算
仍是配置的 3 GiB，因此不是上一轮低内存保护把缓存关掉。4 GiB 音频
预算分给 Composer 75% 后，大约容纳 805 个节点库，而语料有 1787 张
谱面。725 批累计驻留命中 14593、未命中 8610。原路径每次未命中
都会重新加载压缩 RationalAudio NPZ、验证全部数组，再重建整曲
120 维节点库。随机事件采样反复驱逐不同歌曲，导致持续解压和磁盘访问。

另有 CPU 热点：首次访问每个事件时，持续动作快照扫描整曲 marker；
首次接触每首谱面还要构建原子、历史特征与 future 标签表。

## 已完成修改

- `composer/audio_bank.py`：把与原 `composer_audio_nodes` 逐值一致的
  float32 特征和 float64 时间写成一个不可变结构化 NPY 文件。
  后续驻留缓存未命中时，直接只读 mmap，不再反复解压重建。
- 缓存身份包含版本、音频路径、音频 NPZ 文件状态、BPM/tempo、first、
  meter、extent；沿用原特征内容，不将目标谱面事件注入音频。
  发布为临时文件原子替换，Windows 并发读者占用目标时复用有效胜者。
  写入失败保留原内存路径，并计数；损坏头或形状不匹配会重建。
- `composer/data.py`：缓存逐曲特征键和映射路径；保留现有 LRU 与内存
  保护，不扩大用户预算，不改变 RandomSampler、样本次序或 batch。
- `SustainStateIndex` 增加秒级粗索引，仅缩小 marker 候选集；精确 onset、
  include_current、end+release、未来头的因果释放判断、排序和上限
  仍由原 `at()` 执行。跨很多事件的长 Slide/Hold 不会被截断。异常或
  极长区间回到原扫描路径；旧 preparation cache 对象可惰性建索引。
- 增加音频查找、标签表、动作快照 CPU 累计时间及映射命中/新建计数。
  主界面显示这些指标，区分驻留 miss 与真正需要重建，不再将二者混淆。
  逻辑数组字节不等于映射文件实际占用的物理内存；后台细分与消费者
  等待有重叠，不能把这些计时直接相加。

没有修改模型参数、特征值、监督目标、损失、候选集合、训练语义与
checkpoint schema；原检查点继续 resume，不需要因此重训或 finetune。
备份为 `backups/composer_speed_before_20261022_155824.zip`。

## 修改完成后的集中验证

37 项检查首次通过，新增两项边界测试因测试输入使用负拍位而失败；
将输入改为有效非负拍位并保留负 first 后，整个持续动作等价文件
8 项通过。合计涉及 39 项不同 Python 检查通过，包括 mmap 逐值一致、
预算为零时跨驻留 miss 复用映射库、损坏恢复、时钟身份、CPU 训练与
生成、精确 CPU resume、独立全扫描参考和 include_current 边界等价。

同一实际数据集、固定 2048 个随机事件、相同 3 GiB 驻留预算，清空驻留
LRU 后对比音频节点获取：

| 路径 | 用时 | 驻留命中 / 未命中 | 映射复用 / 构建 |
| --- | ---: | ---: | ---: |
| 原 4428c35 路径 | 22.794 秒 | 981 / 1067 | 0 / 0 |
| 新路径首次构建 | 22.814 秒 | 981 / 1067 | 53 / 1014 |
| 新路径已建库 | 0.535 秒 | 981 / 1067 | 1067 / 0 |

这是音频获取局部约 42.6 倍提升，不是整轮训练提升 42 倍。
随后用原 batch 32、BF16、384 宽、双 6 层、FFN1536、词表18454、
fused AdamW 运行实际 32 次更新并保存 scratch 检查点，全部通过。
32 批耗时 14.875 秒，数据等待 9.833 秒；仍包含 165 个此前未见节点库
首次构建和标签表惰性初始化。峰值 CUDA 已分配约 2.07 GiB。
这不能替代完整热缓存 epoch 基准，也不能承诺 GPU 将始终满占用。

本地证据：`.scratch/composer_data_speed.log`、
`.scratch/composer_speed_results.json`、`.scratch/composer_data_speed.py`。
未覆盖用户正式检查点，未启动正式长训练。

## 操作与边界

- 重新启动训练子进程即可读取新数据代码；主界面刷新显示新增计数。
  后端训练 API 参数未变，不必为此结束 WebUI 服务。
- 首轮遇到每个新音频/时钟组合仍需建立映射库；后续访问和后续任务
  复用同一缓存目录才会明显受益。标签表仍在每次进程启动后惰性构建。
- 映射用未压缩文件换取读取效率，会增加磁盘缓存，当前验证生成了
  1179 个约 4.39 GiB 节点库；完整语料实际大小依曲目/时钟组合而定。
  文件可以重建，清掉后首次访问成本也会回来。
- 保留 batch 32、累积1和4 GiB缓存先作真实对照；本轮没有通过同曲
  聚类、减少历史/候选或放大 batch 改变训练分布和更新节奏。
- 若持续动作 marker 被原地修改而不替换列表/改变长度，应同时使
  索引失效；正常训练中的 marker 是不可变的，与既有 release 索引
  使用的假设一致。
