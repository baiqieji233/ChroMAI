# Composer compact 改动交接（2026-10-30）

**同日后续更新：** v26已停止并保留原检查点。最新两次产出揭示了密度、粗细选时和负担到物量的进一步断路；本文件下方训练状态为历史快照。当前修复、失败实验及训练状态请从[休止与微步续修交接](COMPOSER_V26_REST_MICROSTEP_REPAIR_20261030_ZH.md)接手。

本轮把 Antigravity 审查中有源码依据的建议接入新训练路径，统一使用 `action_head_policy=compact_grouped_v3`。目标是让模型更直接地学习“什么时候该停”“每个按钮刚承受了多少连续击打”“接下来八拍是什么声音”，同时减少重复计算。这里记录的是实现与训练计划，不是生成质量已经改善的结论。

审查原文：`docs/explanations/COMPOSER_REST_DENSITY_ANTIGRAVITY_REVIEW_20261029_ZH.md`。实现、统一测试与真实数据运行检查已完成；v26 已开始 fresh 训练。原文中的效果预期与验收门槛属于建议，不能当成本轮实测结果。可复查的参数、检查点摘要与结果保存在[证据 JSON](../evidence/COMPOSER_COMPACT_REVIEW_IMPLEMENTATION_20261030.json)。

## 先分清 v25 已有的内容

以下机制属于 v25 基础，本轮继续沿用，不应记成本轮新成果。

- 选时使用事件率形成生存分布：先估计某段时间内会出现多少事件，再计算下一事件落在各候选区间的概率。
- 候选点代表的时间宽度纳入计算。不是把候选点上的事件率简单做 softmax；每个时间单元使用 `1-exp(-区间风险)` 计算事件质量，再乘前面一直没有事件的概率。候选变密不会凭空获得同等数量的新概率质量。
- 保留“当前候选窗口里没有下一事件”的尾部概率。这表示继续向后找，不等于歌曲已经结束，也不是 EOS。
- 均匀时间探针通过 Poisson 计数监督覆盖整曲，包括休止段，避免只在密集事件附近学习。
- survival 路径取消旧的 long-rest 屏蔽和粗时间桶 min-p 裁剪，避免采样规则再次压掉模型学出的休止概率。相关旧函数仍服务旧模型，不意味着所有历史路径都被删除。

这些机制本身也不能证明休止段已经生成正确，仍要检查实际输出。

## 本轮增加什么

### 把真实事件之间的空白直接作为监督

每个正常训练样本，从上一个已提交事件到目标事件前留出安全边界，在这段已知没有事件的时间里放四个等分区间的中心探针。代码在目标前保留 25ms 边界，使用整段标注可信度，不能因为中心点可用就把整段未知内容算成休止。

四个探针复用事件率预测器，目标计数为零；区间越长，预测出多余事件受到的惩罚越大。四点是对空隙积分的数值近似，不应称为对任意变化事件率的解析精确积分。没有有效空隙或标注可信度不足时，不产生这项监督。

这些探针的位置依赖真实目标，只能用于辅助损失。`empty_gap_audio` 经独立事件率预测产生 `empty_gap_rates`，不会拼进主选时、选键或候选上下文。这样可以教模型识别空白，而不会把“答案在哪里”偷偷告诉主模型。生成端也不需要知道真实目标。

### 从“上次打过多久”扩展到“每个按钮最近累积了多少负担”

旧按钮特征保留十维；compact 使用二十三维：原十维，加四个秒尺度的逐键累计击打、四个尺度的双押成员负担、一项逐键连续游程，以及四个尺度的相邻键负担。秒尺度为 0.08、0.18、0.45、1.2 秒。双押同时给两个成员计入负担，不把共同按钮的贡献平分掉；连续包含同一按钮的双押换了搭档，也仍能累计这个按钮的游程。

历史秒龄通过真实歌曲时钟计算，用 `history_second_ages` 传递。不能把历史拍龄乘当前每拍秒数来冒充秒龄，因为变速曲会算错。指数衰减按历史与候选分别计算，避免展开候选数乘历史长度的大中间张量。

新 `PerButtonLoadV2` 给每个解码位置输出三组八键分数，分别对应 tap、hold、slide。输出层从零开始，分数在可见键内居中；符号信息关闭时该分支为零。它是可学习的软偏好，不是增加一条固定手速禁令。

这些分数与其他几何信息在 compact 宏观层合并，同类音符内重新分配位置概率，并保留该类原有总概率。不能把这个性质扩大为“任何采样和 guard 之后都保持原分布”：守恒约束只覆盖相应模型头内部的调整。Touch 与 STOP 不因此获得额外质量。

### 同拍动作不再永远从小编号开始

训练使用 `action_order_policy=symmetric_v1`。对每个样本，依据 seed、epoch、样本编号稳定决定是否反转动作目标的非 STOP 部分，以约一半规范序、一半逆序训练。这里是两种顺序，不是枚举整组动作的所有排列。只改目标的副本，缓存 `atom_ids`、已提交历史与 STOP 填充保持原样。验证集关闭增广，固定使用规范序。

compact 生成与恢复采样取消 `canonical_order` 的字典序截断。例如第一个位置已选 5，第二个位置仍有机会选 1。去掉顺序截断不代表允许同一动作重复，也不代表跳过原生合法性检查。

生成的官谱尾部重复惩罚在 compact 下按逐键连续游程识别持续负担，继续沿用原官谱尾部阈值和软惩罚强度；不另加更苛刻的硬速度上限。旧版默认保留原行为。

### 精简选键头，但保留动作组合的表达能力

compact 去掉全词表的平面 `action_head`，保留轨迹、时值等组合细节。先独立决定音符类别与起始位置，再在这个组内决定具体动作，避免重复的大词表投影与重复的位置修正。旧平面头的组公共分量确实在归一化中抵消，但它仍能学习组内细节，不能说它所有梯度都为零。本轮选择共享细节参数来替代独立原子参数，是结构取舍，后续尤其要检查少见滑条是否受损。

音频分支拥有独立的宏观分类器，不再依赖被删除的平面头。共享的类别、位置等宏观因素也改为读取同一份归一化后的上下文，避免一条分支归一化、另一条分支直接吃原始尺度。compact 将按钮负担、前后事件关系及同拍几何合并后统一进入宏观调整，减少同一种位置偏好的重复叠加。当前完整词表有11,520种音符，主动作宏观组为91组；音频参考按既有不含位置的类别、修饰、时值等划分为1,039组。组数从实际词表生成，没有假定为260。终点相关偏置仍在组内处理；不是取消所有全词表运算。

### 向前看八拍，不靠候选点恰好铺得够密

compact 在每个候选之后读取十个真实音频位置：+0.25、0.5、0.75、1、1.5、2、3、4、6、8 拍。通过歌曲时钟换算时间，越过歌曲末端的探针由 mask 排除。读取结果在选时之前并入音频上下文，因此不仅是在已经选好时刻之后帮助选键。

主界面的“未来音频视野”仍可关闭这条新增读取；旧音频编码的跨候选上下文保留。收尾已修复 compact 忽略该关闭选项的问题，开启状态的 v26 不受此修复影响，无须因此重新训练。

这替代 compact 路径中候选互相注意的 C² 前瞻，以及重复的候选间未来间隙证据。即便当前候选分布不均，较晚的候选也能直接读取自己后面八拍的声音。当前固定探针模块直接读取音频并汇聚，不应描述成已经实现审查建议中的所有声学加事件率探针方案。

仍保留 128 个已发生事件的历史。128 事件回答“前面发生过什么”，八拍前瞻回答“后面将听见什么”；事件数量与拍长是两种尺度，不能因为增加八拍前瞻就把历史缩短。

## 审查建议中没有直接照做的部分

- 没有把曲线 `active_gate` 下限从 0.15 直接改成 0.02：现有相关公式自身最小值为 0.35，仅改外部 floor 不会让输出降到 0.02。若需要改变曲线，应先验证真正生效的公式与路径。
- 没有把模型预测的休止强制转成硬 `rest_regions`。预测可能有误，不能用未经验证的硬屏蔽替代事件率学习。
- survival 路径的粗桶温度没有简单跟随极低指针温度。它承担时间跨度的概率分配，已取消阻碍休止的粗桶 min-p；再次锐化粗桶会改变已学习的时间风险分布。现有温度仍控制桶内选择。
- 没有删除 `legacy_history_attended`。它仍参与 pointer 的历史上下文，删除会改变选时输入，不能因为选键路径做了精简就认为它无用。
- 没有硬衰减最近一拍的全部符号信息。按钮累计负担与保留的历史机制负责表达近期关系，不再增加一个未经验证的统一遗忘规则。

## 下一步怎样验收

使用保留的 v25 与 v26 checkpoint，对同一首音频、同一难度和相同生成设置，分别跑两个固定种子。保存 checkpoint 身份、配置、种子、生成谱和诊断日志；不能只挑一份看起来好的输出。

1. 对照真实休止段：是否仍密集出音，是否误删应有事件，长空白之后是否正常恢复，而非提前 EOS。
2. 对照原问题片段，包括 190 BPM、48.63s 附近共享按钮的双押续写：记录逐键实际秒间隔、连续击打与双押成员负担，检查是否只是换搭档而共同按钮仍持续承压。
3. 检查第二位置能否选择小于第一位置的按钮，同时确认未出现重复动作或原生 guard 失效。
4. 检查类别、位置和谱型多样性，防止通过过量休止、偏向某类音符或单一按钮来换取表面好看的负担指标。
5. 听音并实际试玩，检查八拍前瞻是否改善乐句进入、空拍和段落衔接。代码检查、loss 下降和 guard 通过都不能代替这一项。
6. 对照相同训练窗口报告 samples/s、数据准备与计算耗时、prefetch 等待、主机/GPU 内存。没有实测前，不宣称删去 C² 模块已经带来固定百分比加速。

是否保留本轮设计，应依据这些对照结果，而不是仅依据模型能运行或某项辅助损失下降。
