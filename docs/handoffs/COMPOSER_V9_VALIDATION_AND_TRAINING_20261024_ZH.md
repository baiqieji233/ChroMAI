## 1. 已确认的问题及修复

| 问题 | 修改前的复现证据 | 已实施的修复 |
| --- | --- | --- |
| 最简微调命令无法启动 | 从真实 v7 权重初始化，未传结构参数时出现 `d_model=384 differs from requested 192`；API 同样传入默认 192 维、3 层、6 头、576 前馈、8 槽位 | CLI 与 API 在未显式提供主干参数时继承父模型；显式参数仍保留，交由兼容校验检查。微调目标 profile 不被父模型覆盖 |
| API 续训隐式覆盖学习率 | 模拟当前合同的可续训元数据，保存学习率 `1e-4`，请求未指定 `lr`，适配器却明确传入 `--lr 0.0002` | API 的 resume 请求未提供 `lr` 时不传该参数，由训练器恢复优化器实际学习率；显式传值继续生效 |
| 无监督填充槽位仍参与昂贵投影 | 真实 v7 解码器输出 `[2,33,18454]`；单音样本仅音符及 STOP 两槽有监督，后 31 槽梯度为零，纯音频动作分支也重复计算全部槽位 | 在 CPU 批处理时，只保留本批最长有效配置及首个 STOP；解码器按目标宽度投影。历史张量、词表、检查点容量和满 33 槽事件均保留 |

原始复现结果保存在 `.scratch/composer_v9_followup_preflight_20261024.json`。槽位裁剪的回归比较了裁剪前后的总损失及每个解码参数梯度；另覆盖零动作、单音、双音、32 音和满 33 槽边界。该优化不改变 v9 的监督目标，因此没有另起训练合同。

另将原来未单独记录的 `audio_action_loss` 加入日志和主工作台，便于确认纯音频动作辅助目标实际参与训练。

## 6. 剩余问题与后续验收

1. **等待正式训练完成并复测。** 至少复用上述双种子条件，另外增加不同音乐、等级和更均衡 Style 条件。短程结果不能代替跨歌曲或独立验证集评估。
2. **Touch 条件服从性和整体物量。** 单曲双种子已观察到 Touch 偏高；第一颗种子的音符数也由 972 增至 1,348。需看完整数据训练后是否改善，不能把增加物量当成质量收益。
3. **报告类物理冲突。** 当前尚未完成全可玩性验收。不要只报告 actionable hard 为零，也不要未经逐条确认就把所有检测类别改为全局拦截。
4. **音乐与手法评价。** 尚未人工试听或试玩这四张谱；段落呼应、长条及滑星手法、实际等级仍未确认。
5. **采样覆盖边界。** 原谱参考历史召回率不等于自由生成可达率；生成相位掩码仍有回退路径，不应宣称特殊细分在所有情况下绝不出现。
6. **训练性能。** 实际观察约 2 batch/s，尚无匹配条件的长期端到端加速比测量。后续应结合供数、计算、内存和 GPU 利用率，而非依据历史估算承诺速度。
