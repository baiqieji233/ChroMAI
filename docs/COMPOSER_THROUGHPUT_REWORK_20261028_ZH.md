# Composer 训练供数与计算优化

更新：2026-10-28。适用于当前`chart_composer_v1 / audio_grounded_v3`。

本轮完成了实际的训练路径修改。真实32谱、完整11,521类词表的GPU对照中，中位吞吐从约276升到305样本/秒，提高约10.4%；每批传输的普通张量从约81.3 MiB降到27.6 MiB，峰值已分配显存从约5.96 GiB降到5.56 GiB。这里没有把局部算子节省比例当作整轮提速。

## 改了哪些实际工作

**大块音频切片在GPU生成。** 原先每个样本都在CPU构造局部音频、不同宽度的平均音频、历史窗口和两次事件之间的音频描述，再拼成大批张量上传。现在训练线程按曲目缓存这些查询所需的基础数组，只上传查询时刻，在GPU完成插值与积分。保留原来的不规则时间轴、边界掩码和计算公式；时间与积分使用float64，模型输入仍为float32。

设备缓存上限为256 MiB，按最近使用顺序淘汰。没有把全语料常驻显存。CPU模式、生成及恢复采样继续使用已有查询方式；恢复中的生成前缀不会误读训练真值状态缓存。

**动作分类只处理有监督的槽位。** 两套动作头都只计算需要的槽位，包括结束当前事件的第一个STOP；不会重新补出巨大的`batch × 槽位 × 词表`零张量。损失统计只还原小的逐槽误差表。旧目标和新目标所需的槽位并集都保留，同拍/跨拍键位关系、音频辅助监督和各项权重不变。槽位索引在CPU拼批时产生，避免GPU用`nonzero`确定行数时额外等待。

**同批相同的规划只算一次。** 对同一音频来源、相同条件与掩码的样本，规划器前向共享，然后把结果按原顺序分配给每个样本。开启条件遮挡时，仍保留原来的逐样本随机抽样，再按实际有效条件区分。梯度按样本累计，没有跨参数更新复用旧规划结果。

**数值检查集中到更新边界。** 前向输出、loss及反传loss的异常标志先留在设备上；一个梯度累积窗口结束时，与梯度状态一起读取。异常窗口丢弃更新和指标，恢复对应的恢复采样状态。更新后的参数检查仍保留，并复用参数/缓冲区列表，避免每步重新构建完整`state_dict`；保存前依旧完整检查。

另外保留并核实了此前的声学查询向量化、结构查询缓存、音频库别名、动作组合去重和同曲预取任务合并。修正了声学插值的算术顺序和末端处理，使既有精确对照通过。`CPU算子线程=0`恢复其原含义：继承环境；本轮没有添加隐藏的线程改写。

## 对照怎样进行

从v18第16000步完整检查点复制独立快照，使用相同数据、样本顺序、初始权重、Adam状态与随机种子。每次单独启动进程，先热身12批，再测32批，顺序为“旧路径、新路径、新路径、旧路径”。batch128、梯度累积2、BF16、CPU算子线程4、样本准备线程1、预取4。

| 指标 | 旧执行路径 | 新执行路径 |
| --- | --- | --- |
| 两次吞吐，样本/秒 | 270.18 / 281.81 | 316.38 / 292.85 |
| 中位吞吐，样本/秒 | 276.00 | 304.61 |
| 普通输入张量/批 | 81.3 MiB | 27.6 MiB |
| 峰值已分配显存 | 5.96 GiB | 5.56 GiB |
| 消费者累计等数据时间，44批含热身 | 10.15 / 10.60秒 | 0.76 / 1.01秒 |
| 有效动作槽占原密集槽位比例 | 50.3% | 只投影这些有效行 |

每批张量字节数不包含首次上传曲目基础库的成本；其上传与查询耗时已包含在实际运行路径中，缓存受256 MiB限制。两种对照采用相同的数值检查方法，计时不含正式训练每次更新后的完整参数扫描、检查点保存与恢复生成，因此10.4%是这一受控窗口的结果，不是所有歌曲或整轮的保证值。

补充拆分实验中，仅压缩动作槽位而保留CPU音频查询约256样本/秒，数据等待仍超过10秒；CPU算子线程改2的一次新路径测量约295样本/秒，没有显示稳定优于4，因此正式任务保留4。减少GPU无效计算必须同时疏通数据供给，不能仅看GPU利用率百分比判断效果。
