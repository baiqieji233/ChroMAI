其中最有价值的两处不是「新增功能」，而是**发现并修掉了第一批实现里的真实错误**：

**Slide 星星几何**。首版把 `2-6` 这类正好 180° 的直线滑条按「最短路径」处理，而两个方向等长，代码随机走了经过 1/8/7 的那一条，于是把中段按键判成被星星占用。同一谱面因此报出 172 条冲突，逐条核对后确认绝大多数是假的。修正后剩 13 条（3 硬 + 10 软），3 条硬冲突人工核对全部为真——Tap 落在 Slide 落点按键上，两者抢同一次按键判定。

**和弦被当成跳跃**。同一时刻按下的两个键被算成「0ms 内跨 1.85」，每个和弦都报一次。这类误报会让一个检测器看起来在工作、实际无法使用，因此修掉它比新增一类检测更重要。

## 三、真实数据上的验证

目标文档只要求「代码可运行」，但工具是否能跑真实数据是更硬的证据。用 `composed_28256cf5024305b7`（939 首可用、1712 个音频缓存、2.26 GB）实测：

- 数据集构建：`segment_beats=16, context_beats=16, audio_margin_beats=8, context_tokens=320` 下得到 **24166 个窗口**，耗时约 103 秒。
- 细碎节奏窗口（阈值 0.25）占 **7.7%**（1863 个）。
- `fine_rhythm_oversample=3` 时总窗口 24166 → 27892，细碎窗口在采样分布中的占比从 7.7% 升到 **19.9%**；`=6` 时升到 **31.6%**。

也就是说这条维度是**真实生效**的，而不是只在单元测试的小样本上有效。同时它也说明了一件事：默认阈值下只有约 1/13 的窗口算「细碎」，所以倍率不需要很大就能显著改变学习分布——3 已经接近把这类段落翻倍。

## 四、还没做到的地方

**1. 标注脚本与实际数据结构不符。** `scripts/annotate_rhythm_patterns.py` 按 `manifest["segments"][i]["events"]` 读取，而真实 manifest 是 `manifest["songs"][i]["difficulties"][j]` 且有 `event_usable_for_training` 标记。它现在跑任何一个真实数据集都会得到「没有 segments 字段」。更要紧的是：**它本不该存在**——`fine_rhythm_oversample` 在训练时直接读取谱面音符节拍计算占比，不依赖任何离线标注。这个脚本是早期设计的残留。

**2. 节奏倾向参数只做了门控，没有生效。** `--rhythm-bias` 与 `--fine-note-strength` 会被校验、会打印「该 checkpoint 不支持，已忽略」，但没有任何路径把它们转成条件向量。好消息是这个门控本身是正确的：**能识别、能告警、不误用**，比默默塞一个分布外的提示给模型安全。但它确实还没成为一个功能。

**3. `local` 修复模式未接入。** `conflict_repair.py` 能删除冲突音符，但 `event_cli` 里只传配置、不调用修复，所以 `local` 与 `none` 行为一致。

**4. 检测器只做段内检查。** `detect_chart_conflicts` 每次看的是一个窗口的点集，跨窗口边界的长条与星星不参与判定，因此边界上的冲突会被漏掉。

**5. 采样维度与规划器目标没打通。** 这是最关键的一条。`music_structure_v2` 的规划器已经预测 `count/density/chord/slide/touch/hold/intensity`，但**没有细碎节奏这一维**。而训练侧新增的过采样只能让模型更多「看到」细碎段落，不能让它学会「这种音乐局部该用细碎采音」。强度曲线之所以可控，是因为 `intensity` 是规划器的训练目标；细碎节奏现在缺的正是同一个位置。

## 五、下一步规划

按「先让它学得会，再让它可控，最后验收」排列。

### 阶段 A：补完规划器目标（✅ 已完成 —— 见 [MUSIC_STRUCTURE_V3.md](MUSIC_STRUCTURE_V3.md)）

**为什么先做这个**：上面第 5 条是唯一一条影响模型能力的缺口，而其它三条都是「工具未接通」。不先补它，过采样只是在放大一个模型还没有表示能力的方向。

具体改动：

1. `music_plan.py` 的 `CONTINUOUS_KEYS` 增加 `fine_rhythm` 一维（沿用现有 8 维连续量的归一化约定，目标取自窗口内小于四分之一拍的起音间隔占比，与 `event_ctx_dataset._fine_note_ratio` 用同一套算法，保证训练与生成口径一致）。
2. `PLAN_DIM["music_structure_v3"] = 13`（9 连续 + 4 配置）。保留 `legacy_v1` 与 `music_structure_v2` 的定义不动，让旧 checkpoint 仍按原 profile 解码。
3. `event_dataset.py` / `event_ctx_dataset.py` 的 `plan_target` 与 `_window_plan` 补这一维；`train_events` 的 planner MSE 自动涵盖它（目标已归一化到 [0,1]，无需改损失结构）。
4. 生成侧：`fine_note_strength` 在 `planner_enabled` 且 profile 为 v3 时写入规划器控制向量，写法与现有 `_curve_plan_controls` 注入 `count/density/intensity` 一致。
5. 门控更新：`FeatureSupport._SAMPLING_BIAS` 的判定条件从「`fine_rhythm_oversample > 1`」改为「合同记录 planner profile 为 v3 或更高」。这样能力位与真实能力对齐，不再做过采样就等于支持的推断。

**风险**：新 profile 必须 fresh 重训，不能 resume 到 v2 checkpoint。合同比较会拦住，属于预期行为。

**验收**：固定同一首歌，`fine_note_strength` 取 0.2 / 0.5 / 0.9 生成三份，比较细碎音符占比与复杂段落的密度方差。若 0.9 与 0.2 无差异，说明规划器没学到这一维，需要检查目标是否被归一化压扁（7.7% 的窗口占比意味着该维目标普遍偏低，可能要改用分位数或 sqrt 缩放）。

### 阶段 B：把修复与检测补成闭环

1. **修复接入生成链路**。`reject` 模式从「放弃候选」改为「重解码该窗口」：保留已生成的前半段上下文，换一个采样种子重新解码冲突窗口，最多重试 N 次（N 可配，默认 2），仍失败才放弃候选。理由：单纯放弃会让越靠后的窗口越容易导致整首失败，而局部重解码能利用已有的上下文。删除式修复（`local`）作为兜底，只在重解码也失败时启用。
2. **跨窗口边界检查**。在 `event_cli` 完成 merge 之后、编译之前，对合并后的完整点集再跑一次检测，专门覆盖跨窗口的 Hold/Slide。段内检测保留，两者结果分开记录，便于判断问题出在局部还是接缝。
3. **修复结果写回产物**：修复后的谱面与原始谱面都要落盘（`*.repaired.txt`），质量报告记录删改数量与位置，方便人工核对修复是否合理。

### 阶段 C：清理与对齐

1. **处理标注脚本**。二选一，不要留着跑不通的东西：
   - 删除 `scripts/annotate_rhythm_patterns.py`，并在文档说明「细碎节奏统计在训练时在线计算，不需要离线标注」；
   - 或者改写成只读分析工具，输入真实 manifest，输出**统计报告**（各难度带的细碎窗口占比、节奏模式分布），用于决定阈值该定多少，而不是写回 manifest。
   
   我倾向于后者：定阈值 0.25 目前是我按「四分之一拍」这一直觉选的，只有 7.7% 的窗口命中，这个比例合不合适需要数据支撑才能判断。
2. **`rhythm_analysis.py` 的多声部估计**标注为近似实现，或在阶段 A 之后用 `fine_rhythm` 规划器目标替代它在生成侧的作用；目前它只被分析脚本使用，不在关键路径上。
3. **难度预设（P1 4.2）**：在阶段 A 完成后做，因为预设里的「技巧谱」本质上就是 `fine_note_strength` 高 + `slide_tricky` 高的组合；现在做等于给一个不生效的参数做预设。

### 阶段 D：验收

目标文档 4.3 的完整版验收，需要一次真实训练与对照：

1. Stage 1：full 训练集，fresh，`music_structure_v3`，15 epochs，独立输出目录。
2. Stage 2：`--init-checkpoint` + `fine_rhythm_oversample=3`，5–10 epochs。
3. 固定 10 首歌生成对照：baseline（当前 v2 checkpoint）vs Stage 1 vs Stage 2，以及约束开/关两组。
4. 指标按目标文档 5.2 记：细碎音符占比、复杂窗口密度方差、硬冲突数、软冲突与人工审核的一致率。人工侧至少核验「是否有无理配置」与「复杂段是否仍被压平」两项。

`hard_conflict_threshold` 这类超参数目前是我定的，验收阶段的真实数据应反推回它们是否合适——目标文档里「硬冲突检出率 <1%」这个指标，只有在有真实生成样本之后才有意义。

## 六、一句话总结

工具层已经基本完备（识别、检测、门控、过采样、WebUI 都在，且有真实数据验证），**但模型能力层还没有变化**：细碎节奏既不是规划器的训练目标，也没有任何参数能实际改变采音。所以下一步的重心不是再写检测器，而是把 `fine_rhythm` 加进规划器目标，然后用一次训练把「过采样让模型看到」变成「模型学会按音乐局部选择采音」。
