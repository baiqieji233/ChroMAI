# Prism_Re_v7 训练速度修复（2026-10-17）

## 现场与恢复点

用户授权查找并修复低 GPU 利用率，必要时停止并恢复训练；用户随后确认端口为 **7860**。没有项目进程监听4860。训练是 `Prism_Re_v7`，原子进程46548，WebUI21488；tailscaled.exe 的非回环7860监听不是项目，没有停止。

原参数：384宽、8层、1280前馈、160 Planner，batch8、累积4、BF16、15秒计算上限、640记忆、增强音乐证据；audio resident、预算12GiB、loader_workers0、prefetch_factor2。**本轮不改变数据、模型、损失权重、随机扰动、batch 或优化器合同。** 原局部负荷损失0.2按用户当前设置保留。

停止前原断点及 train.py / sustain_state.py /现场参数已备份到 `backups/training_speed_20261017_v7/`。断点 epoch0、Planner529更新、本轮配置batch0；原进程已跑的约340配置batch（85更新）尚未保存，需要重跑。通过 `/api/cancel` 仅停止训练，不关闭WebUI。

## 已确认原因

- 原270个配置batch累计：数据等待 **260.447秒**、计算 **61.829秒**，吞吐 **6.52样本/秒**。停止前340batch约 **6.56样本/秒**。数据准备占数据+计算约81%，不是显存不够。
- 音频驻留1722项、5.64GB，无淘汰，disk_loads不再增长。resident保留原始音频证据，不代表完成每段的音频查询、Fraction几何、历史、持续动作、辅助标签和拼批。
- loader_workers0原来在训练主线程同步执行 `next(DataLoader)`；prefetch_factor只影响多进程worker，对当前模式不起预取作用。
- 开启扰动时完整样本缓存有意关闭，防止冻结扰动。不能通过加大样本缓存或关闭扰动来冒充等价加速。
- SustainStateIndex.at先对已过期长音查release，又在每次查release时扫描整张marker表。多数历史长音早已结束，这些重复扫描不会改变状态。
- 新位置辅助并非主瓶颈：B4/L2048/E128/T1024的logits约2MiB，CPU单独loss约7ms。也未发现新的逐token GPU→主机同步。默认BLAS多线程与1/2线程对5120音频查询都约0.17–0.21秒，未证实过量线程是主因，因此不擅自改全局线程数。

## 修复

1. `layout_prefetch.py`：loader_workers0时单后台生产线程，有界提前准备batch，共享驻留音频；主线程保持唯一CUDA训练与已消费游标。默认深度使用现有“预取批次数”2，CLI `--layout-prefetch-batches 0`可用于关闭对照。退出或报错时等待生产线程结束后才切换epoch随机种子。
2. `train.py`：将配置循环放进预取上下文；不更改任务顺序、每样本独立扰动种子、梯度累积或checkpoint游标。日志增加layout_prefetch的准备耗时、消费者等待、准备批数及缓存张量字节。
3. `sustain_state.py`：先排除即使加最大release也已过期的动作；按lane/trace时间延迟建立索引，二分查找可能影响尾部释放的后续Slide/Wifi，仍保留原来的head<boundary、key、严格时间容差与因果条件。旧准备缓存无需重建。
4. WebUI现有“预取批次数”说明更新，明确worker0也使用同进程预取。没有让用户额外开启新的子页面。
5. 另发现恢复启动的旧缓存索引扫描会读取10,621个JSON、约2.34GB，大部分是与身份索引无关的markers/result。`preparation_cache.py`现只解析标准文件开头的identity；旧字段顺序、超64KiB身份或不完整前缀回退完整解析，真正加载时仍完整校验schema/identity/数组SHA。32个真实缓存7.13MB扫描166.96→3.78ms，身份一致。此项在当前进程已完成准备后落盘，下一次启动生效，无需为它再次打断训练。
