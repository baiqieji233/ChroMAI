# song_form_v1 训练前准备速度调整

日期：2026-10-13。

## 日志中的阶段

`form_prepare {"stage":"chart", ...}` 不是 epoch，也不是 GPU 训练。它表示 `FormDataset` 正在把一张谱面准备成 song_form 的训练样本，包含：

- 解析并检查指定难度的 maidata；
- 读取或建立音频特征缓存；
- 按拍号和音乐结构建立计算片段；
- 分析重复段落关系；
- 建立前置 Hold/Slide 状态；
- 构建局部负荷曲线和训练 token。

原实现的主要热点是 `build_load_curve()`：每个两秒区间都重新扫描整张谱面，并重复进行精确 Fraction 拍位到秒数转换。这使准备耗时近似随“区间数 × 音符数”增长。

## 修改

- 负荷曲线现在先对每个事件计算一次绝对时间，再按区间累加。算法结果和原有边界、四个通道保持一致，复杂度从重复全表扫描降为单次事件遍历。
- song_form 训练新增 `--prepare-workers`，WebUI 中对应“准备进程数”。
- `1` 是兼容且稳定的默认值；`0` 表示自动选择最多 4 个线程；也可填写 2–4。
- 并行只处理互相独立的歌曲准备任务，主线程仍按 manifest 顺序写入 `songs`、`items` 和 audit，因此不会改变训练样本顺序、质量权重或 checkpoint 合同。
- 并行模式使用线程池，避免 Windows 进程启动和完整段落对象跨进程序列化；每个线程使用独立的音频缓存视图，缓存文件仍通过原子写入。
- 使用自定义 `audio_loader` 的测试/外部调用会自动回退串行，避免把不可序列化的测试对象放入并发路径。

## 实测

同一份 full 训练清单、相同缓存、前两张谱面：

- 优化前：约 12.0 秒；
- 优化后串行：约 2.0 秒；
- 20 张热缓存串行：约 6.7 秒；
- 20 张热缓存 4 线程：约 9.4 秒。

因此并行不是固定加速器：热缓存、小数据或 CPU 已接近满载时，串行更快；首次建立大量音频缓存时，2–4 线程可能更有收益。默认不自动打开并行，避免普通短跑变慢。

## WebUI 使用

在训练模型的 `song_form_v1 专属训练参数` 中设置“准备进程数”：

- 首次冷缓存、全量数据：先试 `2` 或 `4`；
- 已有完整音频缓存：保持 `1`；
- 短跑、限量测试：保持 `1`；
- `0`：自动，当前最多使用 4 个线程。

准备阶段日志会显示 `stage=preparation`、`workers`、已完成歌曲数和总歌曲数；每张谱面的 `stage=chart` 也会包含 `elapsed_sec`。看到这些日志时，GPU 尚未进入正式 epoch 是正常的。
