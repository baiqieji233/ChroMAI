# 短句记忆与撤回流程：完整测试和效率修复

日期：2026-10-31。对应上一轮实现提交 `15d0f75`，本轮修复在其基础上继续。原检查点保留，没有启动正式训练。

## 目前可以确认什么

短句记忆的加强测试没有发现未来真谱泄漏。撤回测试发现了一个需要修复的问题：原来为了撤回 Hold／Slide，会把同拍的其他音符一起删掉。现在只撤回涉事音符，同拍的其他音符保留，再重建后续。

真实歌曲还复现了一个预算问题：普通当前事件重采被计入全曲历史编辑预算，后半首用完预算后便失去当前重采机会。现在每次短句搜索仍最多重采两次，独立计数；全曲历史编辑和撤回预算只负责相应操作。后一次重采也会从已经推进最远的有效前缀继续，避免反复回到过早的失败点。没有提高默认预算或改变温度。

训练效率确实曾明显退化。本轮消除了逐查询创建大量小张量、重复读取相同时值区间、重复准备歌曲时钟等开销。相同真实样本下，完整新功能吞吐从约 31 提高到约 55 个短段／秒；关闭新增功能仍约 70 个／秒。**尚有约 21% 的吞吐差距，不能说已做到零开销。**

## 短句记忆怎样检查

不能只检查零初始化模型，因为新增接口全为零时，即使输入有错误也可能看不出来。本轮把短句模块权重实际置为非零，再检查：

- 同一段音乐、相同已写前缀，后面换成不同的真谱，当前短句输入必须逐值相同；未来辅助标签确实不同，证明对照没有做空。
- 同一个训练窗口里，改写后面的历史音符，改写点以前的隐藏表示、选时和短句意图逐值一致；之后的表示确实改变。
- 修改未来短句标签、标签权重、标签掩码，甚至把标签改成 NaN，前向输出仍逐值不变。
- 真实 Dataset 取出的行，与只提交同一前缀的增量 InferenceContext 一致。
- 增强、恢复和编辑前缀后，短句档案必须重新对应新前缀，长程辅助标签关闭；主目标预算保持。
- CPU 优化后的批量读取，与原逐查询读取逐值一致；追加和编辑后的缓存失效正确。

这些测试允许读取歌曲后面的音频：音乐本来就是输入。检查禁止的是未来原谱音符进入当前输入；等级和风格条件也属于显式控制项。

相关用例在 `test_stream_phrase_causality.py`、`test_stream_phrase_data.py`。它们覆盖实际数据和模型接口；尚不能据此证明学得的呼应具有音乐价值。

## 撤回后哪些状态必须一致

新增多轮事务测试复用实际生成中的 `replay_stream_prefix`，重建后检查：

| 状态 | 检查方式 |
|---|---|
| 音符、等待、拍位与秒时钟 | 与新建上下文逐张量比较，包含变速 |
| Hold／Slide 持续占用 | 与修改后前缀重新解析的状态比较 |
| 逐传感器最近触发时间 | 与新守卫重放结果比较 |
| 曲线物量计数 | 清空后只按修改后的记录重计 |
| 连续配置和短句档案 | 与从头构建的相同前缀比较 |
| 候选随机数和守卫 | 各分支独立，不改变全局 RNG |
| 已选尾段和旧评分 | 撤回后旧尾段不再沿用，受影响评分标记失效 |
| 同拍其他音符 | 保留，包括受保护的其他音符 |
| 预算 | 当前重采和历史编辑独立计数；真正无可行候选时明确失败 |

覆盖了普通 Hold、简单 Slide、复合 Slide 替换后的占用重建，以及候选数 1、2、4。物理反证仍采用原生判定器；软手感分不作为硬拒绝理由。

## 效率为什么退化，如何修复

第一处在 CPU。每个短句查询原来都会创建多个小 Torch 张量；一批有上千个查询，即使有预取线程，也会争用 Python 执行时间，拖慢主线程向 GPU 提交任务。修复后先用 NumPy 一次分配整批数组，按音乐区间批量检索，最后每个字段只转一次张量。已完成的参考概况可以批量复制，同时每次保留严格的“事件索引小于当前查询”筛选。

第二处在持续动作读取。只差修饰符的音符可能具有完全相同的等待时间和持续时间，原来仍重复读取九个音频点。现在在静态表中合并相同区间，读取后再映射回原候选，表达能力不变。

第三处是每个形状／槽位都重新准备整首歌的插值时钟。现在一次前向只准备一份，各形状、槽位和相位展开共用；不会把可变状态缓存到另一批数据中。

同时修正一个精度问题：持续动作时间系数始终保持 FP32，不随 BF16 动作分数一起量化。物理检查仍使用原生时值。

## 真实数据测速

使用现存 `interaction400/composer_inference.pt` 只读加载，512 维、8 层、历史 128、展开 16、BF16、batch 16，RTX 5070 Ti Laptop。选择同一份真实训练集的前 8 张谱，按固定样本顺序比较。每组预热 3 批，计时 12 批，共 192 个短段、3036 个有效目标，正反顺序各一轮，表中为两轮中位数。

包括预取、传输、前向和反向；**没有优化器更新、恢复训练和随机增强**。因此这是可比的训练主路径测速，不是整轮正式训练的速度承诺。准备缓存 8 次全命中，没有重建准备产物。

| 开启的能力 | 修复前短段／秒 | 修复后短段／秒 |
|---|---:|---:|
| 关闭两项新增学习模块 | 70.36 | 69.77 |
| 仅短句记忆 | 38.50 | 59.88 |
| 短句记忆＋持续区间读取 | 30.99 | 54.88 |

完整功能计时窗口的 `compute_sec` 从 6.116 降至 3.409 秒。这里包含主线程提交计算的耗时，不能都解释为 GPU 在做数学运算。`data_sec` 约 0.010 秒，显式等待很短，不代表 CPU 预取没有争用；预取生产耗时的变化才能看出原来的问题。

最终完整功能的 CUDA 已分配峰值约 3.05 GiB，关闭新增模块约 2.91 GiB。主机常驻内存约 3.5 GiB。原始记录保留每轮的样本编号、`data_sec`、`transfer_sec`、`compute_sec`、预取统计、主机与显存峰值及缓存统计。

性能剖析仍显示大量小算子的 CPU 发射开销；没有以关闭新功能或减少有效训练样本来换取这次提速。后续如继续优化，应优先合并这些调用，并保留相同样本、相同目标和数值对照。
