# 本轮核心修复：让音乐、当前配置与训练目标真正接起来

日期：2026-11-04。新训练合同为 `stream_causal_choice_recovery_v14`。

本轮只处理已经确认的核心缺口，没有重写整个输出词表，也没有再加重复惩罚、Touch配额、最长Hold限制或强制补音。旧检查点仍按原合同使用。

## 一、与前几轮设计是否冲突

| 前几轮核心目的 | 本轮处理 |
|---|---|
| 一份概率同时决定出音、落点和休止，避免几个分支互相否决 | 保留。仍使用统一首次到达分布及无事件尾概率，没有恢复独立休止倍率 |
| 保留音乐仍在响时的主动留白 | 保留。真实WAIT／EOS监督继续存在，没有空白长度上限或强制重入 |
| 先组织整段草稿，再逐事件落实 | 保留。整句联合证据目标、跨句时间／配置归属、已提交模式的保持不变 |
| 防止WAIT历史反过来鼓励继续WAIT | 修正实现手段：不再把完整历史全部排除在选时之外，改为主干只将真实NOTE与BOS作为可读取记忆 |
| 错误前文不应被强迫照抄唯一的原谱配置 | 保留。没有可信对应时只学习原谱的粗类型参考，不监督键位、形状、时值和STOP |
| 音乐直接参与类型选择，Touch同拍按集合学习，Hold有时值校准 | 保留v13实现，不回退这些改动 |

因此，本轮纠正了此前“为了避开WAIT而同时削弱整段历史”的做法，但没有放弃避免休止自强化的目标。

## 二、具体改了什么

### 1. 选时重新读到当前配置，复用现有一次主干计算

新版 `unified_first_arrival_v6` 在现有解码器中只允许NOTE与BOS成为历史注意力的键和值。WAIT仍可作为当前查询，但不会成为下一次休止判断的记忆内容。

真实音符输入改用NOTE到NOTE的时间、拍距及NOTE序号；不再通过虚拟WAIT的个数和最后一段WAIT长度描述真实音符。选时查询复用最近NOTE的主干表示，并加入当前音乐、距最近NOTE的真实时间、当前持续占用和按钮负荷。

新增计算主要是线性规模的索引、时钟计算和一次归一化。没有第二个Transformer、没有额外逐候选历史编码。旧短句选时读出在此模式下不创建；可选谱面预训练直接复用原因果时间头。

已经验证：时间损失能向主干回传；未来目标配置与落点占用不会改变选时；同样真实NOTE前文、同样当前时刻下，细分WAIT不会改变最终选时输出。对于截断窗口丢失了不同真实前文的情况，不作完全相同输出的承诺。

主要文件：`stream_model.py`。

### 2. 时间先验按真正使用的概率定义初始化

此前用类别频率的对数初始化偏置，却在执行时将其当发生率，再乘候选时间宽度。两者不是同一种量。

新版在已编译谱面上按真实秒数计算候选曝光：NOTE监督目标之前的空隙与目标单元内的到达；WAIT／EOS监督窗口内没有事件。用每个节奏组的实际事件与曝光估计基础发生率，再转换到模型使用的softplus输入。音乐发生率通道从零修正开始，之后仍可正常学习。

实现按256行批量处理，不读取音频、不增加GPU前向，也不为每个候选运行Python循环。这里校准的是静态组先验，不能声称初始化后的完整随机模型已精确复现官谱概率。没有禁止任何细分。

主要文件：`stream_timing.py`、`stream_train.py`。

### 3. 整曲写法选择得到实际续写结果的反馈

此前整曲选择主要学习统计控制量；事件损失训练被选中的执行分支，却不能直接告诉选择网络这次选择是否合适。

新版 `event_credit_v1` 使用本次真实执行得到的事件代价，给所采样的整曲选择补上缺失的选择梯度。执行器本身的损失只计算一次。不同整曲选择产生不同控制时，仍实际执行被选择的控制，没有用同一份hidden假装执行了另外几种控制。

为减少随机波动，使用同批其他谱面的平均代价作参考；单谱面批次使用此前批次的平均值。不增加可学习评分网络，不跑多套主干。已经固定的恢复整曲选择不重新收取选择代价。

数学测试确认：按采样概率平均后的选择梯度，与实际执行代价的期望梯度一致；它不会重复训练执行器。真实模型在关闭profile辅助损失后，选择概率仍能收到事件梯度。

此方法仍有采样方差，需要后续正式训练观察。没有加入强制各模式均匀使用的正则，也没有改变整句联合证据为旧平均目标。

主要文件：`stream_song_profile.py`、`stream_phrase_execution.py`、`stream_model.py`。

### 4. 保留真正的第一步恢复，补上粗类型监督

新版 `first_step_phrase_v6` 不再把错误前文后的第一步移出损失、只保留桥接后的目标。真实前文后的第一个已知NOTE会获得同音乐时刻原谱的粗类型参考，例如应该采用按钮类还是Touch类。

这不是认定原谱的具体位置是唯一正确答案。没有可信配置对应时，键位、形状、时值、Touch具体位置和STOP仍不获得标签；认证后的接续才恢复完整配置监督。后续教师桥接明确作为教师前文，不冒称模型自己完成了恢复。

整条轨迹仍共享一份预算，新增桥接时间目标不会成倍增加恢复权重。没有另跑一轮生成，也没有放宽物理合法性检查。原有受控错拍课程继续保留。

本轮已验证首步类型输出有非零梯度，同时不会为该首步新增位置／细节监督。它补上了实际缺失的学习信号；是否在生成中减少Touch连刷、改善完整配置衔接，仍需新阶段学习后验收。

主要文件：`stream_recovery.py`、`stream_data.py`、`stream_phrase_training.py`、`stream_model.py`。

## 三、GPU为何周期性冲高后回落

被停止的实际任务是v52：批大小24、累积6、音频缓存8GB、预取4批、学习率0.001，并且关闭了验证。它不是此前推荐的16×4配置。

日志与低扰动系统观测表明：

- 第5轮一段1993秒窗口里，预取等待仅0.748秒；继续增加准备线程不是主要方向。
- 恢复训练每25次更新运行一次，内部是逐步生成与物理检查，比普通并行教师训练更容易出现GPU忙闲交替。保存检查点也会暂停更新；第1000次保存附近约有12秒间隔。
- GPU峰值已分配约8.80GiB、保留约10.32GiB，设备总显存约12GiB。
- 一次系统快照中，提交内存约67.35/70.25GiB，Python私有提交约31.24GiB，存在换页活动。不能把所有系统换页都归给训练，但这说明增大缓存和批次的空间很有限。
- 温度读数达到84–86°C，但当时热降频标志没有激活，不能据此宣称温度是根因。

代码中确认的一处可避免负担是张量生命周期：主批输出会与下一批前向重叠；恢复批输出还可能一直持有到下一次恢复。现在在反向和已分离的指标入账后立即释放这些引用。没有改变梯度累积、采样顺序、恢复频率或必要的非有限检查。

默认恢复16×4、1GB缓存、预取2批、CPU算子线程2。GPU瞬时利用率不是吞吐的替代指标。

用全部2479张谱面的编译数据、同一v52第1365步父检查点和相同样本顺序做两个104批窗口，各1664个样本、26次更新，均执行了一次恢复训练。结果如下：

| 指标 | 旧v13目标 | 新v14目标 |
|---|---:|---:|
| 窗口耗时 | 131.45秒 | 90.03秒 |
| 样本／秒 | 12.66 | 18.48 |
| 有效目标预算 | 57523.5 | 57523.5 |
| 有效目标／秒 | 437.60 | 638.93 |
| 数据等待 | 0.853秒 | 0.375秒 |
| 传输计时 | 1.550秒 | 0.953秒 |
| 计算段计时（含恢复及CPU工作） | 127.70秒 | 87.29秒 |
| GPU峰值已分配 | 4.276GiB | 4.270GiB |
| 跳过更新 | 0 | 0 |

此窗口新目标吞吐高约46%，没有出现新增计算导致的速度退化。两次按旧→新顺序运行，复用了已编译数据，后一次可能受益于热缓存；不能把46%全部归因于某一处代码，也不能承诺完整轮次持续同样增幅。两次都使用新的张量释放逻辑，因此这不是该内存修复单独的A/B。

真实恢复中，两条轨迹新增2个原生首步类型目标，保留16个认证后的完整配置目标。原本11个不具备完整配置标签的步骤中，2个现在有类型参考、其余9个仍只有时间监督。后续日志已经把family-only与time-only分开计数，避免混淆。

## 四、WebUI与训练状态

当前fresh默认：50轮、批大小16、累积4、固定学习率0.0005、BF16；自动留出比例0.05。正式训练不再默认关闭验证。

“出音与休止判断”“自主生成恢复”“整曲写法选择学习”的自动选项，分别解析到v6、v6、event_credit_v1。自动解析由后端最新策略表决定；用户明确选择的旧策略和旧检查点resume不会被偷偷替换。“应用重训默认值”会将策略重置为自动。

修复了“模拟自动补全的谱面比例”被显示白名单误隐藏的问题；当前可以在整曲风格训练中调整。隔离浏览器实际检查到114个展开后的有效控件，无页面脚本错误，重训默认值和提交payload一致。

旧任务 `295e0c6406b7` 已在第5轮1365次更新完成保存后停止。原文件位于 `checkpoints/prism_composer_v52`，包括完整 `composer_last.pt` 与推理点。本轮没有启动新的正式训练。
