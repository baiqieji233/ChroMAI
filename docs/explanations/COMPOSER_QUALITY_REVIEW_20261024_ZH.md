## 1. P2：未提交搜索游标可能绕过相位保护

- 位置：`src/maichart/composer/generate.py:363–366`、`370`、`470–474`。
- 触发：所有尝试的配置均未通过，或候选暂时全部被占用，代码把 `previous` 推进到 `candidates[0]`；这只是搜索游标，尚未提交音符。
- 机制：相位检查却用这个游标计算 `(beat-previous).denominator`，而音频特征及历史仍以最后提交事件为基点。游标进入 `/16` 相位时，canonical 绝对拍位和游标的差值会含 `/16` 或 `/48`，使 `phase_playable` 全空；随后回退到 `base_playable`，重新开放本应过滤的候选。
- 独立反例：已提交拍位仍为 0，搜索游标为 `1/16`，BPM 200、音频边界 20 秒、96 候选。相位候选为 0，回退后重新暴露 68 个非 canonical 绝对拍位，包括 `7/48`、`3/16`、`11/48`。数量随边界和候选集合变化，不是固定常量。
- 质量后果：在该条件下，防微距策略失效，可能重新产生细碎切分。尚未证明它在实际输出中的频率；本次查看的两个近期生成报告 `skipped_candidates=0`，不能把此路径当作那两张谱的已证实原因。
- 建议验证：记录最后提交拍位与搜索游标两套状态，强制一次完整候选失败，检查下一轮是否仍遵守原定相位策略。不要以“某次 A/B 微距为零”推断所有分支已覆盖。

## 2. P2：低正温度下，整类音符概率会被清零

- 位置：`src/maichart/composer/generate.py:137`、`147–154`。
- 触发：动作温度为较小正数，例如 UI 允许的 `0.05`，且某类单原子 logits 明显低于最高原子。
- 机制：先对整个词表执行 `softmax(logits/T)`，再取出每类子分布；小概率类全部下溢为 0 时，`sub_sum<=0` 跳过整类，最后归一化到其余类别。结果仍全是有限值，非有限值检查无法发现它。
- 独立反例：一个 Tap logit 为 8、1,000 个 Slide logits 为 0。温度 1 下 Slide 总质量为 **25.1196%**；`T=0.85/0.1` 能保留，`T=0.05/0.01` 时变成 **0%**。
- 质量后果：有效参数范围内会重新压掉 Slide / Hold 等大词表类别，违背“大类质量按 T=1 保留”的采样合同。
- 边界：这不是默认动作温度 `0.85/0.90` 下的已证实主因。温度 0 是显式贪心模式，另有语义，不能与此数值缺陷混为一谈。
- 建议验证：按类独立计算稳定的细概率，与原实现比较类别质量；在极低正温度加入质量保持测试，而非只测试输出是否 finite。

## 3. P2：合法零时长 Hold 因写法不同而不可采样

- 位置：`src/maichart/composer/generate.py:99–101`、`169`。
- 机制：字符串包含 `[1:0]` 等模式时，头尺寸被直接置为 0；采样器要求 `sizes>0`，使这些原子不可达。
- 独立反例：`1h[1:0]` 与 `2h[4:0]` 都被现有解析器接受、时长均为 0，但前者头尺寸为 0，后者为 1。即使给前者最高 logit，贪心采样也会改选普通 Tap。`EventGuard` 接受 `1h[1:0]`，它不是解析或通用物理规则自动拒绝的语法。
- 范围：当前真实词表中有 **31 个原子**命中该屏蔽模式；抽样原谱也包含 `5h[1:0]`、`2hb[1:0]` 等写法。
- 质量后果：模型训练可见的部分 Hold 写法在生成中被静默删除。但数量有限，不能据此解释整体 Tap/Touch 分布。
- 建议验证：如果确实要限制某类动作，应按解析语义建立一致且公开的策略；不能仅按一种文本写法过滤等价表示。

## 4. P2：未来变速点可能导致整个导出失败

- 位置：`src/maichart/composer/generate.py:514–516`；`src/maichart/generation/event_compile.py:97–106`。
- 触发：使用手动 tempo map；生成因 EOS 或 `max_events` 在后面的变速点之前结束。
- 机制：导出末拍只根据最后音符起点计算 `ceil(last_beat)+1`，但编译时传入完整变速表。编译器要求末拍不能早于任何变速点。
- 独立反例：一枚 beat 0 的 Tap，变速点为 beat 0 / 200 BPM 和 beat 32 / 150 BPM，调用端末拍为 1。编译器抛出 `ValueError: end_beat must be after every note and not before any tempo change.`
- 后果：前面已经生成的有效事件无法写出 TXT，后续报告也不会保存。属于导出可靠性问题，不是旋律或配置审美问题。
- 建议验证：将带未来变速点的短跑/EOS 截止纳入集成测试；导出结束与保留变速表需要满足同一个时间合同。

## 5. P2 条件问题：同权重批次会抵消图级正质量权重

- 位置：`src/maichart/composer/train.py:171–177`，以及 `SongLocalBatchSampler` 的单曲批次路径；权重输入位于 `data.py:174`、`782` 附近。
- 触发：例如 `sample_locality=1`，整批来自同一张图，所有样本共享同一个非零图级质量权重。
- 机制：每批损失除以该批权重之和；整批乘上的常数同时进入分子和分母，完全抵消。若希望在整个数据集上让好图贡献更多、差图贡献更少，这种批次安排会使预期效果消失。
- 主代理独立复现：采样器产生 `[[0,0],[0,0],[1,1],[1,1]]` 的单曲批次；同一批权重全部为 `0.1` 或 `10` 时，总损失均为 **3.3322396**，指针梯度最大差为 **0**。
- 边界：零权重的排除仍有效；不同权重同时出现在一批时仍有相对作用。当前正式配置是 locality 4，实际训练权重分布未在本轮重建，不能用本项解释当前 Touch 过高，也不能称所有质量加权均失效。
- 建议验证：先统计真实批次中的权重及来源分布，再决定使用何种全局归一化或采样方案；不要仅凭该反例改动现有训练目标。

## 6. P3：报告中的难度槽与 TXT 可能不一致

- 位置：`src/maichart/composer/generation_settings.py` 的 `difficulty` 合并路径，`generate.py:515` 和 `event_compile.py:43`。
- 反例：条件中 `difficulty=6` 被接受并保留；生成调用未向编译器传入 difficulty，实际仍使用默认 5，输出 `&inote_5` 而非 `&inote_6`。
- 后果：影响导出槽位和报告一致性，不改变模型的 16 维生成条件，也不是当前配置单调的主因。

## 7. 有量化证据的策略差异，不直接判为实现错误

当前生成同时限制绝对拍位与相邻偏移分母为 `{1,2,3,4,6,8}`，训练样本只使用共享候选与边界掩码。比如 `1/8 → 1/3`，相邻偏移 `5/24`；共享候选包含目标，但生成策略拒绝它。

主代理对 manifest 做系统抽样：**119 张可用原谱、65,916 个事件**中，发现 126 个两端绝对拍位满足白名单、相邻偏移却不满足的转换，其中 **108 个目标属于共享候选集**。这是原谱子样本上的覆盖差异，不是全量训练 EventViews 的重新统计，更不是“普遍存在严重质量退化”的测量。

恢复训练也没有使用该生成专属白名单，并按 T=1 做时间采样；部署默认候选温度为 0.55。它可能让恢复监督与部署状态分布不一致，但策略差异本身不足以证明训练有害。应先量化恢复提案/目标被部署规则拒绝的比例，再决定统一规则或保留专门的探索分布。

这是一项防微距与表达能力之间的取舍。不能把原谱里出现过某种切分自动当作所有场景都应放行，也不能把约 99.612% 的参考候选召回当作应用生成掩码后的召回率。

- workload 已使用均匀全曲探针；未知/排除区间有相应监督屏蔽，不应重复旧版“只监督密集事件时刻”的指控。
- prefix ledger 有 `committed_count` 限制；按键时序快照在当前目标之前保存，没有发现这一输入泄漏目标。
- 恢复样本会清零不适用于生成前缀的辅助监督；没有发现新的标签泄漏。
- `max_heads=2`、组合失败后封禁首原子、EOS 可提前结束均存在表达或搜索取舍，但缺少足够证据把它们直接叫作当前质量问题的根因。
- 最后一个长动作超出 `export_end` 是否会被实际播放器截断，尚缺下游证据，本轮不作确定判断。
- Touch 偏高、段落写法单调、滑星手法好坏，仍需固定条件生成干预、独立歌曲及人工试听/试玩；本轮没有这些质量验证。
