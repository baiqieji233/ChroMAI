# 第342拍生成失败：原因与修复

2026-10-31。对应任务 `428f4ed1f70a`。这是生成搜索失败，不是正在运行的 v36 训练退出；本轮没有停止、重启或修改该训练任务，也没有覆盖它的检查点。

## 这次不是预算用完

读取完整日志后，冻结了当时的 v36 第2轮／788更新点。使用原音频、种子1176305701、条件文件、强度曲线和采样参数，旧实现再次在第342拍失败，前700事件的进度拍位与原CUDA日志一致。

由于训练占用约10GB显存，复现采用 CPU 模型前向、仅保留 CUDA 随机抽样，避免再向显卡加载一份大模型。CPU与CUDA浮点计算不能宣称逐位相同，但旧实现确实复现了同一失败位置与具体冲突。

失败现场是：已经试写到350拍，单事件守卫没有报告最后一次提议错误，但整段原生复查发现了 SlideTooFast。历史编辑只用了1/8次，完整撤回0/4次，时间也没有超限。不能把这次说成之前第453拍的预算耗尽问题。

## 真正漏掉了什么

旧守卫会保留尚未结束的Slide本身，以及最近0.3秒的其他音符，却丢掉该Slide持续期间更早的交互。原生判定器需要这些中间输入来还原过程；删掉它们，就可能把有问题的新Tap判断为可接受。等到整段复查读到更多上下文，才发现冲突。

本次现场已缩减为三个事件，BPM205：

| 拍位 | 音符 |
|---|---|
| 63623/192 | `1bx-5[16.2406##0.2256]` |
| 346 | `3/8-4[8:1]` |
| 699/2 | `5` |

旧短窗守卫接受最后的Tap，但完整原生判定报告SlideTooFast；新守卫能在提议时拒绝它。这里遵循当前原生判定策略，没有为了通过测试而隐藏冲突报告。

另一处漏洞在搜索流程：它只会对“当前事件写不出来”重试。遇到“整段已经写完，但复查未通过”，却没有放弃这份临时尾段、重新试写的路径，于是直接进入修改旧持续动作。涉事旧Slide又包含EX标志，按既有保护策略不能随意编辑，最终退出。

## 本轮改动

- **保留完整交互窗口。** 持续动作尚未结束时，保留从其起点附近到当前的中间事件；结束后释放。逐事件守卫和整段复查使用同一窗口算法，旧判定策略不变。
- **允许有限地重写未提交尾段。** 每次短句搜索最多两次，从同一已提交前缀重新试写。临时候选不会占用修改已提交历史的全曲8/4预算；原温度、物理标准和已提交内容保护保留。
- **明确区分旧冲突与新冲突。** 时值编辑的反证比较保留拍位、类型、位置、Slide路径和修饰，只忽略本次允许调整的时值字符串。不能把同键但不同路径的新冲突误认为旧问题。
- **失败诊断实际落盘。** 普通CLI失败时在目标谱面旁保存 `maidata.failure.json`，包含参数、检查点轮次/更新数、失败候选、物理报告和预算。文件写入失败也不会覆盖原来的搜索异常。失败时仍不导出假成功或截短的谱面。
- 生成报告新增“试写回退”计数，与当前重采、历史编辑、完整撤回分别显示。

这些是守卫和搜索的修复，不需要重新fresh。正在运行的训练进程保持原样；新的生成子进程会加载修改后的代码。
