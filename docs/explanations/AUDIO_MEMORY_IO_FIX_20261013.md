# 训练音频驻留与重复磁盘读取修复

日期：2026-10-13。适用于 `song_form_v1`；旧模型的权重与生成路径保持原样。

## 为什么训练持续读盘

这次日志显示，音频内存缓存上限为 1 GiB，能留下约 380 首音频。full 训练集当前 2175 张谱面涉及 1719 个不同的音频缓存，特征数组共约 4.383 GiB。随机取样不断访问已被淘汰的歌曲，因此内存命中后无需读取、未命中时仍需重新读取压缩特征。

在 `20261013_135214_form_train_5da4d24fdcde.log` 中，配置阶段约 5241 个 batch 已累计 33658 次音频加载、33279 次淘汰，数据等待约 878 秒，计算约 369 秒。可确认数据读取占了较大时间，但仅凭任务管理器的磁盘占用不能把所有 IO 归因于同一文件。

还发现一处可避免的重复 IO：原来每次缓存淘汰后的加载都调用通用特征提取器，它为了确定缓存身份会完整读取原音频做 SHA256，即使随后只使用已经存在的特征缓存。

此前 Windows 多加载进程会复制数据集，并各自保存缓存。现场还发现 PID 8612 是已失去父进程 66780 的旧 multiprocessing 子进程，仍保留约 3 GiB 工作集。它采样时没有 IO；不能把当时的磁盘读全部归于它，但它会增加内存压力。系统分页文件历史使用峰值约 6 GiB；硬缺页读也可能来自文件映射和文件缓存，不能据此直接断言全部是分页文件活动。

已确认该旧子进程与当前 PID 72544、worker=0 的训练无父子关系，清理了旧进程，没有中断当前训练。

## 实际修改

1. 普通缓存模式记录每首歌曲已经解析出的磁盘特征路径。源码文件的大小、修改时间和创建/元数据变更时间没有变化时，重载直接读特征缓存，避免重复读取原音频做哈希。检测到来源变化或缓存损坏时重新解析/提取。路径元数据可随 Windows spawn 传递，驻留数组仍不复制。
2. 新增可选“全量驻留内存”：先计算唯一音频的数组需求，再检查缓存硬预算与可用系统内存，最后一次性加载。之后正常训练取样复用同一份音频数组。要求 worker=0，防止整套特征在多个进程中重复驻留。
3. 全量驻留预留至少 2 GiB 或物理内存的 10%（取较大值）供系统和后续开销使用。预算或可用内存不足时明确拒绝，不悄悄开启无限缓存。
4. 修复 WebUI 取消任务只终止父进程的问题。Windows 使用任务进程树终止；POSIX 新任务使用独立会话并结束进程组。取消后不再让其加载子进程继续占用内存。
5. 日志新增全量音频需求、预加载进度和实际驻留量；普通缓存统计新增 `disk_loads` 和 `source_resolutions`，可区分特征缓存读取与来源路径解析次数。

## 推荐操作

主训练页“训练运行与缓存”：

| 设置 | 当前 full 集建议 |
| --- | --- |
| 音频读取方式 | 全量驻留内存 |
| 数据加载 worker | 0 |
| 音频缓存上限（GB） | 6 |
| 样本缓存上限（MB） | 64，可按需要再降低 |
| 准备进程数 | 1～2 |

6 GiB 是允许使用的预算；本次音频数组实际约占 4.383 GiB，不会为了用满预算而分配额外内存。这还不包含谱面索引、Python 对象、样本、模型及系统的内存需求。

系统内存不足以容纳全量特征时选择“按预算缓存”，仍会受益于消除重复原音频哈希读取的修复。维持默认值不强制全量预加载。

CLI 对应 `--audio-cache-mode resident --loader-workers 0 --audio-cache-gb 6`；默认 `--audio-cache-mode lru`。

这些是运行时选项，能在 resume 时修改，不改变模型形状、训练样本或优化器合同。当前已运行进程不会自动换成新读取逻辑；重启 WebUI 后，下次训练或继续训练才使用新代码。不要为了更新 WebUI直接终止仍在训练的进程，先按正常方式保存/停止任务。
