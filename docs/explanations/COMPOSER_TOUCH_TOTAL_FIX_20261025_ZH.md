## 已确认的来源

两名默认配置子代理完成 CPU 探针和独立复核，主代理复现并核验；工具未返回实际模型名称，因此不声称验证了具体模型。

| --- | --- | --- |
| 97.95s | 96.28% | 20.03% |
| 99.00s | 99.57% | 28.55% |
| 100.50s | 94.49% | 16.88% |

这些点的物理掩码影响为 0–0.275 个百分点，远不足以解释上述放大。只改最后两步历史也不能消除高概率；历史编码、按键年龄等因果分支共同作用。条件里的 Touch 比例输入正确，但当前权重对 `touch_bias` 的响应很弱。

因此不能只靠换环区、删除合法性检查或调低界面上的 Touch 参数解决。已证实的是符号状态对动作类别的过度覆盖；音频分支并不因此成为音乐上的绝对正确答案。

## 最终采用的生成保护

`action_guidance.py` 以同一候选、同一已选同拍前缀的音频动作分支为参考，限制符号分支对 **Touch 相对非 Touch 的正向 log-odds** 额外放大不超过 1（赔率额外放大至多 e 倍）。低于该界的输出原样保留。

在物理掩码之前，该变换保留 STOP 概率、非 STOP 总质量、Touch 内部和非 Touch 内部的相对分布。因此不是固定 Touch 配额，也没有删掉 Touch、平均分配环区或重写按键。后续物理掩码仍可改变最终概率，不能声称掩码后仍严格满足同一赔率界。

单独限幅的原型虽降低 Touch，却使第一种子的 hard 从 11 增至 39，故未直接交付。最终版增加替代提案检查：**只有实际触发保护的提案，才额外拒绝其新增的报告级 hard 冲突**；继续通过现有重试寻找合法配置，Touch 本身仍可被选择。

这不是全局开启所有冲突拦截。未触发保护的提案及训练恢复仍使用既有 report/enforce 策略；未来未触发保护的事件仍可能与既有事件形成报告冲突，因此不能保证全曲无 hard。

启用范围：`audio_grounded_v3` 且动作温度为正。WebUI 使用当前源码生成时默认启用；CLI 可用 `--no-touch-history-guard` 回放旧策略。贪心动作温度 0、其他模型族保持原路径。报告记录 `touch_history_guard`、`safe_audio_anchored_touch_odds_v2` 和实际保护/安全拒绝次数。

## 固定音频、条件、权重、双种子的完整对照

均使用完成的 `Prism_composer_v8_resume_20261024/composer_inference.pt`、同一 dingerbox 音频、BPM 200、first 0、Level 14.5、原 condition、温度 0.55/0.9、70ms 同键间隔。**本轮前后均使用 CPU、2 个 PyTorch 线程**，避免改变后端的随机流而误归因。此前 CUDA 的 13.49%/26.97% 不能直接充当这次 CPU 对照的“前”。当前 GPU 训练占用很高，本轮没有抢占它进行 CUDA 整曲复测。

| 指标 | 709835971：旧策略 → 最终保护 | 1696576229：旧策略 → 最终保护 |
| --- | --- | --- |
| Touch / 全部音符 | **21.47% → 7.82%** | **24.27% → 8.11%** |
| Touch / TouchHold 数 | 184 / 3 → 77 / 2 | 229 / 3 → 70 / 1 |
| 总音符数 | 871 → 1,010 | 956 → 875 |

两个最终输出均严格解析成功，无非标准微距，最短同键头间隔满足 70ms。最终版没有后处理删除或修改音符（`repairs=[]`），所以 Touch 降低不是靠删谱实现。

结论限于上述对照：高 Touch 和长串自强化显著减轻；总 hard 也在这两个样本下降。**没有证明比例精确达到输入的 4.1%，也没有完成听音、试玩、多曲泛化或当前新 v9 权重的验收。** 模型本身的条件响应不足仍是后续训练评估项。
