# 训练性能复审与继续优化（2026-10-28）

## 对上一位协作者工作的评价

这轮工作找到了有价值的系统瓶颈，值得保留。最重要的不是多开线程，而是避免样本准备线程打断主线程连续提交 GPU 工作；同时减少了重复音频查询、动态形状操作和样本准备中的无用分配。本轮没有回退这些实现，也没有改变学习目标、采样规则、模型结构或训练精度。

源码能直接支持的改进包括：

- 预取线程在样本之间等待，前向提交阶段暂停、反向传播前恢复；异常路径和退出路径恢复线程。
- 音频积分端点查询合并、斜率和差分预计算、连续同曲行用切片写回。
- Planner 使用固定大小的条件组合，避免前向中的动态去重；时间分箱边界作为 buffer 保存。
- 修复字典默认值的急切求值、提前准备连续时间数组、跳过不用的图边、减少 mmap 子类包装。

文档有两处需要收紧，而非否定工作：

1. **约 3 倍是短程测量结果，不是整轮训练保证。** 上轮测量只有 18 个 batch、3 次更新；冷歌曲准备、周期恢复、保存检查点、验证和生成评测都会影响整轮耗时。GIL 协调是合作式暂停，不能保证所有时刻主线程独占 GIL；正在构造的样本会运行到下一处等待点。
2. **新增 GPU 预计算数组未进入显存计数。** `_DeviceBank.nbytes` 在创建斜率、差分等张量之前计算，使 512 MiB 上限按低估值执行。本轮保留预计算，但改为构造完毕后按实际独立 storage 计数，视图不重复累计。

本轮开始时，v19 日志已经是 `cancelled`，GPU 空闲；没有为复审再停止任何训练。未写入或覆盖正式检查点。

## 本轮新增优化

### 训练指标一起累加

主训练每个 batch 会产生数十项指标。原来每项单独累加，提交成功后再逐项加入累计和近期统计；每个标量都可能成为一个小 CUDA 操作。

新增 `composer/metric_totals.py`，按固定字段顺序把指标放进一个向量，每次统一累加。只有输出报告时才一次性取回 CPU。仍然先保存到当前梯度累积窗口，只有更新成功才提交到总计；失败窗口、条件 CE 的分子/分母、按 batch 平均的历史定义都不变。

### 验证指标一次回传

`evaluation.py` 仍按原先的权重在 Python 中汇总，但把本 batch 的指标和权重一起从 GPU 取回，避免每个指标分别 `.item()`。没有将不同分母的指标混为一种平均。

### 历史先裁剪，再组成 batch

此前先建立最多 33 个音符槽的完整历史张量，再找有效宽度、切片并复制。现在每张谱预存每个事件最后一个非空槽的位置，组 batch 前先裁去末尾空槽。内部空洞、历史事件数、真实音符和 STOP 语义不变。恢复等未携带该元数据的调用仍使用原路径。

### 按类型批量寻找起音中心

现有起音中心监督已经按类型取窗口内最大高斯响应；本轮保留这一质量修复。对同一类型，高斯响应最大的位置就是距离最近的该类型事件，因此可以一次建立各类型时间表，批量二分查找，避免为多个查询点反复切片和求最大值。

音符类型之间不会合并，25ms 窗口、边界容差、未知区域权重和高斯宽度都保持原样。包含近邻 Tap/Hold/Touch 混合的逐项暴力参考测试用于验证，而不是只检查数组形状。

### 缓存预算按真实占用执行

计入新增预计算数组，保留 512 MiB 配置和超大歌曲不驻留的行为。这个修改修正的是内存上限，并不保证每种访问顺序都更快；如果原来依靠超预算缓存获得命中，修正后的命中率可能降低，应以实际显存与吞吐共同判断。

## 验证与测量口径

所有修改先完成，再统一运行测试。未使用子代理。

本轮开始时的完整源码保存在 `.scratch/composer_perf_followup_20261028/baseline_src`，已经包含上一位的全部性能优化。ABBA 基线使用这个快照，而不是很早的慢版本。四个子进程分别运行，使用相同歌曲、词表、初始模型和样本顺序，保留 GIL 协调、精度、更新健康检查。

性能测试使用 batch size 96、6 次梯度累积、BF16、2 个 CPU 线程、1 个样本准备线程和 8 批预取。CPU 表先同样预热；12 批训练热身后计时 72 批。正式权重只读，优化器更新仅存在于临时测试进程内，不保存模型。使用 32 张真实谱、完整 11,521 类词表，基于 v18 权重重新构建相同模型，两侧均开启条件遮挡 0.15，局部音频分块 32；这不是对 v19 全量训练耗时的直接复现。

最终结果：

| 测量 | 对方优化后的基线 | 本轮最终实现 |
|---|---:|---:|
| 第一组吞吐 | 493.84 samples/s | 503.54 samples/s |
| 第二组吞吐 | 482.07 samples/s | 488.69 samples/s |
| 中位数 | 487.95 samples/s | 496.11 samples/s |
| 稀疏起音标签查询，112 点 | 34.27 微秒 | 33.73 微秒 |
| 密集重叠起音标签查询，112 点 | 729.48 微秒 | 57.82 微秒 |

端到端中位数增加 **1.67%**，幅度较小，不能据此承诺稳定的整轮提升。密集标签局部计算约快 **12.6 倍**，但常见样本、GPU 前后向以及其他数据准备限制了总收益。样本顺序哈希四组一致，健康检查未发现非有限更新。

缓存计数从约 **53.27 MiB** 修正为 **89.59 MiB**；实际 GPU 峰值仍约 **4.48 GiB**。计数上涨是把已经存在的数组算进去，不是新增了这么多显存。

记录一次必要修正：第一版“每种类型各查一次”让稀疏样本变慢，短对照吞吐下降约 6.3%。没有保留这个版本。最终沿用对方已有的单事件快速路径，只把多事件重叠部分改为共享查找，既保留了此前优化，也消除了新方案的倒退。初次与最终测量文件均保留。

CUDA 训练没有启用逐位确定性。新旧损失序列最大差约 0.021，同一基线两次运行也有约 0.016 的差异，不能宣称训练轨迹逐位相同。标签与暴力参考逐项相等；历史组批张量、指标聚合和窗口隔离均由回归测试验证。没有用这些短训练数值作音乐质量判断。

统一验证：

- Python 全量：**3508 passed，36 skipped**，约 222 秒。该轮隐藏 CUDA。
- JavaScript 全量：**162 项通过**。
- GPU 音频及本轮专项先通过；起音计算修正完成后再验证所有受影响路径：**25 项通过，包含 CUDA 检查**。
- 未运行正式训练，未修改原检查点；本轮没有使用子代理。

## 下一步优先级

- 先测正式训练恢复阶段、冷歌曲第一次访问、日志与保存开销，再决定是否值得增加整曲状态落盘。不要把所有候选特征无界缓存，规模可达数十 GiB。
- 同一歌曲的精确重复音频查询有共享计算的潜力，但要保留梯度累加、chunk 显存上限和训练随机性，不能直接把训练用 CNN 输出长期缓存。
- 可把只用于显示的分组损失诊断从反向图中分离，但不能切断真正的宏观辅助目标梯度。
- 暂不把 FP64 积分表改为 FP32。累计积分再相减可能放大小窗口误差；需要单独验证长歌曲、短间隔和音频尾部，不能只凭普通 FP32 前向速度作决定。
- `样本准备线程=1`、`CPU 线程=2` 是本机值得保留的起点。不要因 GPU 利用率高就断言吞吐最佳，也不要把提高 batch 或线程数当作默认解法。
