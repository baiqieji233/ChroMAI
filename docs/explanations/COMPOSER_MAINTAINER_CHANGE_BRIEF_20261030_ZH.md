# Composer 近期改动说明：给实际维护人员

日期：2026-10-30。对应代码：`e249083`。本文主要介绍近期的 `event_set_stream_v1` 连续生成路线，以及 v32 到 v33 的修复；旧 `audio_grounded_v3` 路线仍然保留。

2026-10-31又补修了八分回旋：音乐交互有一处被归一化抵消，另一处前后音乐比较实际读了同一点；长错误历史的训练也太稀少。后续设计、固定对照和仍存在的问题见[八分回旋修复说明](COMPOSER_MUSICAL_EXIT_REPAIR_20261031_ZH.md)，不要把本文的旧验证数字当成最新结果。

## 这次主要想解决什么

生成中反复出现三类现象：一次错拍后很久回不来；Touch 越写越多；配置看起来在重复，训练却没有明显报错。

检查后发现，问题涉及模型怎样保留输入、怎样选择音符、怎样接受训练。此次改动的目的是让模型更容易从原谱学到正确写法，并能从自己写错的历史中恢复。

## 具体改了什么

### 1. 按歌曲拍位选落点，让错拍后有路可回

旧模型主要选择“距上一音隔多久”。如果上一音偏了，后面继续走相同间隔，就会一直沿着偏移后的时间轴写。

现在直接考虑接下来两拍内、相对于歌曲节拍的落点。同时，把“走四分之一拍到达整拍”和“直接跳过一整拍”分开学习，避免两者混用同一份统计倾向。候选处的音乐和预测密度也参与选择。

训练时还会轻微移动最后一个历史音符，保留原谱后续落点，并重新计算时间和占用状态，教模型怎样接回去。生成后不会把所有音符强行吸附到固定网格。

### 2. 音乐负责选择类型，历史负责衔接

旧输出把 Touch 和许多复杂写法放在同一个大分支，普通配置却分散在多个分支；类型选择容易受这些分支的组织方式影响。历史输入还会放大“刚写过什么，就继续写什么”的倾向。

现在先决定这一拍包含哪些类型，例如 Tap，或 Touch 加 TouchHold，再选择具体位置、形状和时值。类型选择读入音乐、候选间隔、拍位和预测密度；完整历史继续帮助组织具体配置。

历史对类型的影响改为一个共享的“是否延续上一类型”的决定：不延续时，按当前音乐重新选择。它不能因为上一类恰好是 Touch，就给 Touch 单独增加惯性。默认类型训练预算中，25%用于校准音乐给出的分布，75%用于学习结合延续后的选择。

同一落点的配置失败时，也只在已经选定的类型内重试，避免 Tap 反复失败后最终改抽 Touch。这没有设置 Touch 数量配额。

### 3. 单独学习“写几颗”，避免为了补齐类型不断追加 Touch

旧的逐颗拼写方式要求先补齐所选类型才能结束。如果还缺 TouchHold，模型可能一直追加普通 Touch，直到偶然补上缺少的类型。

现在按类型分块生成，每块分别学习“继续添加还是结束”，再选择具体音符。例如可以先写两颗 Touch，结束该块后再写 TouchHold。训练和生成使用同一种分解，结束概率也不会因为可选传感器多就被稀释。

计算时只处理实际存在的类型块及对应词表，继续共享原来的网络。

### 4. 保住不同输入之间的差异

检查发现，旧主干继续训练后，面对不同历史的输出会变得几乎一样。这会妨碍模型根据不同音乐和前缀作出不同选择。

此次调整了每层内部“归一化”和“累加输入”的顺序，让原输入更容易保留下来；新建模型的各层也改为独立初始化。迁移短训仍保留父模型已有的层参数。

同一组7段前缀中，旧结构继续训练600步后，输出差异量从约0.418降到0.000409；新结构短训后为0.513。这个结果说明本次短训保留了输入差异，不能据此直接判断谱面好听。

### 5. 给密集常规配置足够的学习机会

原训练给每个8秒窗口相近的总权重。窗口里音符越多，每一步分到的权重就越少：4步窗口与64步窗口的单步权重能相差16倍。

现在改为较温和的平衡方式，把窗口间的单步权重比限制在最多4倍，同时保留每张谱原有的总训练权重。目的是让密集 Tap 段得到足够训练，又避免高密度谱面仅靠音符多就占据全部训练。

### 6. 保留连续生成，并减少重复计算

近期新路线把同一拍的配置作为完整事件来学习，一条训练短段同时监督连续16个决定。模型仍逐步生成，能读取自己已经提交的配置；歌曲音频则整首共享，不为每个音符重新提取。

此次修复复用已有音频和密度计划，没有增加另一套大型主干，也不需要新增人工标注或重建原音频银行。不过新增计算确实有成本，不能因为参数只增加少量，就声称训练同样快。

## 验证到了什么程度

两组都从同一个 v32 检查点开始，分别训练600步，再用同一首音频、相同条件和两个固定随机种子生成。

| 指标 | 旧结构继续训练 | 本次修复后 |
| --- | --- | --- |
| 纯 Touch 事件比例 | 63.2% / 62.0% | 12.5% / 10.4% |
| 最长 Touch 连段 | 85 / 76 | 8 / 6 |
| 最长相同间隔连段 | 19 / 29 | 14 / 14 |
| 剩余原生硬冲突报告 | 0 / 0 | 3 / 1 |

代码回归为4197项 Python 测试通过、13项跳过，185项界面测试通过。600步训练没有因非有限数值跳过更新。

**当前不能宣布整体质量验收通过。** Touch 仍偏多，配置重试增加，仍有 Slide 冲突；部分分音是否合拍还需要听音和试玩。局部提交检查会放行、完整谱检查却会报错的 Slide 案例，已保留给后续排查。

性能也有退步：同批计算基准约慢18%，整段600步更新约慢45%。数据等待只占很小部分，后续应重点检查计算与小算子提交开销，而不是继续盲目增加数据线程。

## 维护时应注意什么

界面总 loss 是选时、类型、配置细节、计划和恢复等多项损失的合计。多颗音符需要累计多个决定，训练权重和输出分解也已改变，因此不能只凭总 loss 高低判断模型是否学会；应同时看各项损失、固定生成结果和试玩反馈。

主界面的“连续生成训练修复 → 自动”会为新训练或微调阶段启用新版策略；续训继承原检查点。更换源码不会让旧权重自动获得新能力，结构迁移应使用新目录并保留原点。

`checkpoints/prism_composer_v33` 是从 v32 迁移后训练600步的验证点，不是从头训练完成的成品。v32 原完整点和推理点均已保留。

主要修改位置：

- [stream_model.py](../../src/maichart/composer/stream_model.py)：主干、类型选择、配置生成与损失。
- [stream_timing.py](../../src/maichart/composer/stream_timing.py)、[stream_literal.py](../../src/maichart/composer/stream_literal.py)：落点分组、类型块组织。
- [stream_data.py](../../src/maichart/composer/stream_data.py)、[stream_augmentation.py](../../src/maichart/composer/stream_augmentation.py)：样本权重与错历史训练。
- [stream_sampling.py](../../src/maichart/composer/stream_sampling.py)、[stream_proposal.py](../../src/maichart/composer/stream_proposal.py)、[guard.py](../../src/maichart/composer/guard.py)：重试与提交检查；训练恢复和正式生成共用相关逻辑。
