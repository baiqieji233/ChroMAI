# song_form_v1 条件参数与具体数值审计

日期：2026-10-13。固定检查点：`checkpoints/Prism_Plus_v1/form_epoch_001.pt`，512 宽、6 层，完成 epoch 1。审查代码基线：`e6b9eda`。运行中的后续训练没有中断或修改。

后续补充：同日增加了免重练的 Planner 类型软指导和类型比例纠偏，详见 `PLANNER_TYPE_GUIDANCE_FIX_20261013.md`。下文的统计单位与 16 维模型输入不变；第 5 节前向探测不包含这两个新解码旁路。

本轮同时核对名称、数值定义、真实训练分布、预设组合以及实际代码传递。**保留同样的参数名字，不代表新旧架构的控制方法、强弱或所有旁路设置相同。**

## 1. 模型读取多少数值

条件向量严格是 **16 个标量**，顺序不变：

```text
0: level / 15
1..7: note_density, peak, sweep, slide_tricky, slide_sequence, jack, chord
8..15: tap_bias, slide_bias, hold_bias, touch_bias, chord_bias,
       melody_following, pattern_reuse, directionality
```

当前配置模型线性投影为 16→512，全曲规划器为 16→256；二者均接收完整向量。输入构造为 float32，当前训练在线性运算中使用 BF16 autocast。`difficulty=5` 等槽位是元数据，不是第 17 个条件。

与 event_ctx 事件模型相比，向量顺序和谱面统计单位沿用共享实现，改变的是控制接入方式：旧事件模型使用两层条件投影，并按 checkpoint 合同采用条件记忆 token 或逐帧偏置；song_form 配置模型使用独立条件 token，条件还参与 Motif 门控，全曲 Planner 另有自己的条件投影。因此同一组数值可以沿用其统计含义，却不能沿用“旧模型调到某值就有某效果”的经验强度。旧 frame 模型另有目标统计公式，不在这次 song_form 结论的适用范围内。

还有独立输入：音频 token 每行 120 个特征、段落描述每行 507 个特征、负荷曲线每行 4 个通道、持续动作每行 50 个特征、段落关联 4 项、任务 ID、Motif 强度及谱面 token。BPM、first、tempo map 通过音频/拍位时钟及相关特征生效，不是漏传的 Radar 项。

模型没有“每项滑条专门控制一个输出比例”的分支，也没有保证参数单调影响输出的损失。固定字段会改变隐藏状态；是否学会按目标生成相应配置，仍需实际控制扫描。

主模型条件随机丢弃 0.15 时，15 个 Radar/Style 值改为 0.5 并添加 learned null embedding，等级保留。Planner 仍接收完整条件。这个 null 数值不是日常生成应使用的默认值，也不是把这 15 个控制永久关掉。

## 3. 每项的真实单位与关系

来源：`generation/event_quality.py:_condition/_statistics`，不是官方机台雷达公式。

- `note_density = 音符头总数 / 原音频秒数 / 16`，上限 1。0.3 约为 4.8 heads/s；多押的每个头都会计入。
- `peak = 一秒窗口内最大起音事件数 / 32`，上限 1。实现数的是时刻组而非全部头；同一时刻三押算一个事件。源码相邻注释存在措辞冲突，以实现为准。
- `sweep = Slide 头比例 × 平均路径端点步数 / 4`。步数来自路径部件起终点的环形距离，不能完整反映实际描线长度、圆弧或体感运动。
- `slide_tricky = Slide 头比例 × 被判作复杂 Slide 的比例`。复杂条件包括多分支/部件、短时值及部分路径符号，不是只看视觉难度。
- `slide_sequence = Slide 头比例 × 相邻 Slide 间隔满足 0 < 间隔 ≤ 2 拍的比例`。同刻 Slide 不计入连续；它不是与 Slide 量独立的“连续度百分比”。
- `jack = 间隔不超过 0.5 秒的相邻起音组同键重复头数 / 所有可比的后继按钮头数`。分母不限制时间间隔，因此长间隔也会稀释该比例；不等于所有 Jack 技巧或每秒手指负荷。
- `chord = 同刻两个及以上 note 的起音组 / 有音符的起音组`，包含 Touch 等类型，不只统计实体按钮的两押。
- `tap_bias`、`slide_bias` 为对应 note 头比例；break 是修饰，不是独立类型，所以 Tap 比例已包含 break Tap。
- `hold_bias = Hold + TouchHold`，`touch_bias = Touch + TouchHold`。不能把它们当作完全互斥的比例。
- `melody_following` 为谱面起音在音频特征起音附近 ±80 ms 的匹配比例；没有声部、音高或人声/钢琴选择标签。训练中有 1751 个不同值，离线等级预设却固定为 0.9。
- `pattern_reuse` 统计完全相同的非恒定四拍配置签名重复率；不是主歌/副歌高级结构呼应。三拍子音乐也不会让这个统计自动改成三拍窗口。
- `directionality = |顺时针次数 - 逆时针次数| / 有效单键转移次数`。只衡量净旋向一致度，不指定顺时针或逆时针，不包含所有双手运动。

以全局默认值为例，Slide=0.140 是全部头中约 14% 为 Slide；slide_tricky=0.114 相当于其中约 81.4% 满足程序的复杂 Slide 条件，slide_sequence=0.066 相当于约 47.1% 的相邻 Slide 间隔不超过两拍。因此这两项看似很小，也不是“只有 11.4% 的 Slide 复杂”或“只有 6.6% 的 Slide 连续”。提高 melody_following 不能指定钢琴、鼓点或人声声部，也不能保证增加细碎采音。

## 4. 单项合理不代表组合合理

### 重复与相关维度

1859 张谱面的 `chord == chord_bias` 完全相同。人工设成 0.2/0.8 会产生训练中没有的组合；正常预设已经强制相等。删掉其中一维会改变旧权重列顺序，当前不这样改。

`slide_tricky` 和 `slide_sequence` 应不超过 `slide_bias`。例如 Slide=0.14、复杂度=0.5，意味着全部 note 的 50% 是复杂 Slide，但全部 Slide 只有 14%，数值关系不成立。不是将复杂度 0.5 解释成“Slide 中的一半较复杂”。

### 类型份额的中位数拼接问题

对一张非空真实谱面必有：

```text
tap_bias + slide_bias + hold_bias + touch_bias = 1 + TouchHold头比例
```

全局默认合计 0.976，相当于负的 TouchHold 比例 -0.024，不是可由一张真实谱面产生的统计向量。当前 31 档预设也都略低于 1，例如 13.3 档为 0.972791、15.0 档为 0.98691。原因是各项中位数独立汇总；不是 0.001 四舍五入足以解释的误差。

这属于轻度的组合分布外条件，不等于会直接生成坏谱，更不能拿它独自解释大量 Hold。偏好叠加保存原 baseTotal，因此也保留了这个问题。**不建议简单强制归一为 1**，因为真实 TouchHold 会使总和大于 1。更合理的后续预设算法应从原始互斥类型比例联合统计，包含 TouchHold，再映射成当前四项，或选实际代表谱条件。

当前全体 1,279,828 个头中：Tap 930,000、Slide 168,654、Hold 104,809、Touch 74,038、TouchHold 2,327。按 note 总量汇总的 TouchHold 重叠为约 0.182%，不是每张谱面都有这个固定比例。

### 预设来源与目标模型不完全一致

静态预设记录 1858 张，manifest SHA 为 `64d434…`；当前训练使用 1859 张，manifest SHA 为 `f3ca6c…`。代码会校验 schema/31 档/数值边界，但不会核验当前素材 SHA。这证明预设已不是当前训练来源的精确校准，并不说明所有数值都不能用。

13.3 档有 107 张直接小数标签，支持较好；15.0 仅 3 张直接样本，主要依赖邻档平滑。等级基准是每档条件统计，不是实际谱面官方定数预测器。

静态默认与自动等级预设不同。例如 13.3 预设密度 0.292、峰值 0.344、Slide 0.153，而 fallback 为 0.305/0.375/0.140。页面实际值还受已保存设置和偏好影响，不能将代码常量当作当前屏幕上的唯一数值。

## 5. 当前检查点的有限响应验证

固定 epoch 1、固定音频、CPU 只做前向，不生成整曲、不改变权重。在 13.7 基准上，把每个单项改为该档 P10/P90；等级另试 12/15。

- Planner 起音 logit 的最大 RMS 变化约 0.200。
- 一个固定片段/前缀的配置下一 token logit 最大 RMS 变化约 0.000347。
- 该测试中条件对 Planner 的响应较明显，对这个配置前缀很弱；不能据此宣称所有曲段配置都忽略条件。
- melody_following 的预设 P10/P90 都是固定 0.9，本次该项没有实际数值变化，不把它的零差异当作未接入的证据。

前向变化验证“参数确实到达运算”，不能证明实际 note 类型比例、密度或难度随之单调变化。16 项仅通过学习到的投影与门控进入模型，没有字段专属的配额/单调性损失；部分输出弱于参数、互相代偿是可能的。

此外 BF16 训练会量化数值：13.30、13.31、13.32、13.33 的 `level/15` 都可落到同一 BF16 值 0.88671875；13.40 对应 0.89453125。生成用 float32 输入不代表模型训练时掌握了界面每个 0.01 定数的区别。每 0.1 的预设也只是插值参考，不是精准体感难度控制。

## 6. 其他设置的数值是否对得上

| 设置 | 新架构实际行为 | 数值评估 |
| --- | --- | --- |
| Temperature | note 字符合法候选上的 softmax 温度，0 为 argmax | 0.65 是可试的起点；0.4～0.6 更保守，但低温不保证质量且可能重复 |
| 起音选择阈值 | 正类加权训练分数经过峰值/门控后筛选 | 0.5 是经验起点，不是校准的 50% 概率；仅调此值不能准确控制 NPS |
| 起音合并范围 | 小范围内保留最强峰 | 40 ms 抑制近邻；大量真实 32/48/64 分时应结合 BPM 调小。50 Hz 局部峰本身也限制了起音分辨率 |
| 峰值与分辨率 | 大部分原始局部峰需隔一帧，40 ms 合并还限制近邻 | 约 25 次独立起音/秒的尺度，与 peak=0.9 所请求约 28.8 次/秒存在能力张力；多押可增加头数，但不改变该峰值统计的事件口径 |
| 分音近似 | 容差内移动到选定网格，默认关闭 | 15 ms 是起点；超过容差保留原音。勾选 64 并不会恢复已经被合并掉的峰 |
| Motif 强度 | 参考 token 乘 learned gate 与该强度，0 遮掉参考 | 默认 0.6，训练取样默认 1；0.6 尚无专门效果校准，不等于 60% 配置重复 |
| 规划类型指导强度 | Planner 类型概率对合法候选解码加有界软偏置 | 新增默认 1.0；0 关闭，不强制执行 argmax，不改起音拍位 |
| 类型比例纠偏强度 | 按全曲已完成 note 头与 Style 偏好差异纠偏 | 新增默认 1.0；0 关闭，非精确配额，内部互斥采样偏好投影单独记录 |
| 曲线强度 | 调整选择分数倍数，并将曲线基值送入配置模型 | 0.65 不是 65% 音符遵从；0 时基曲线仍输入、休止仍生效，完全关闭用启用开关 |
| follow + span | `1 + strength*(clip(2*intensity,1-span,1+span)-1)` | 强度 0.65、幅度 0.5 → 倍数范围 0.675～1.325 |
| hard | 跳过 span 倍数裁剪，没有逐段密度硬上限 | 强度 0.65 → 0.35～1.65。不是旧架构“超密度立即停止”的 strict 模式 |
| 曲线四通道 | 密度通道是局部 heads/s÷8，其余为类型/动作比例 | 与全局密度÷16不是同尺度；当前将强度倍数乘全部通道，类型比例也一起变，数值语义仍需单独优化 |
| 音频上限 | 限制单次配置音频范围，Planner 仍看全曲 | 14 秒不等于 16 拍；不直接增加或减少难度 |
| token/记忆 | 生成继承所选 checkpoint 的上限 | 当前 2048/512；训练页的数字不会临时扩大既有生成模型 |
| 修复预算 | 检测次数、编辑数、墙钟时间停止条件 | 24/4/10 秒只代表资源预算，不等于全部无理已经清理 |
| BPM/first/map | 显式时钟与采样对齐 | 是确定的数学关系，与 Radar 软控制不同；错误时钟不能靠增加 melody_following 补救 |

旧 Top-p、CFG/guidance、重复惩罚、逐窗口强度、尾部衰减、细碎辅助头等没有对应的新解码实现，不能套用旧搭配册。正确带 family 标签的控件会隐藏；目前新模型不能通过这些旧数值获得额外控制。

## 7. 本轮修复范围

确认温度控件与 payload 接线错误：界面 `#temperature` 可见，但新模型请求读不存在的 `#formTemperature`，总退回 0.7。其它明确的接口问题包括 auto 设备被前端转成 CUDA、候选份数显示但未实现、空种子被改成固定 0，以及曲线兼容模式说明与新实现不符。

修复后，主页面空种子交由后端每次随机选择一个整数，显式填写 0 仍是固定种子；任务状态和 `.form.json` 都记录实际种子。生成报告增加 16 维条件的顺序、float32 实际值和等级除数 15，避免把归一化后的第一维误认作原始定数。condition-file 的等级覆盖 CLI 等级时，导出谱面等级也采用实际条件等级；改稿操作保留原谱的等级元数据。

本轮只修正这类接口/说明错误，并让生成报告记录实际使用的条件向量、温度、种子、曲线与资源参数。没有删除/重排 16 维，没有改标签缩放、模型形状、训练目标、静态预设数值或正在运行的训练。

修改前源码备份：`backups/condition_control_audit_20261013/source_before_fix.zip`。生成报告与导出等级修复已提交为 `1fc6a09`；界面与审计说明单独提交，避免把已有的其它工作区改动混入本轮。

外部 condition-file 只填少数字段时，当前共享 from_dict 会给缺失的 Radar/Style 填 0.5。这与完整 WebUI 请求不同；它仍是待改进的输入默认策略。高级 CLI 暂应提供完整条件，而不要把“字段未填”当成自动采用当前语料默认。

## 8. 当前建议与后续顺序

1. 普通生成先按等级预设，单项保持同等级 P10～P90 内，避免把各项都填 0.5 或 1。
2. chord/chord_bias 同值；tricky、sequence 与 Slide 比例一起调，不让子集比全集大。
3. 不把 type-bias 四项当互斥份额；TouchHold 重叠与现有预设轻度失配必须区分。
4. 起音数量优先结合阈值、曲线和合并观察；配置类别再看 Style。保存同一模型/音频/seed，单次只改一组。
5. 接下来先同步当前训练素材的联合条件预设和来源校验，再做固定歌控制扫描。之后才考虑独立控制损失、Planner/布局软引导和新增风格标签。

需要改变维度顺序、原有单位或训练目标的优化必须版本化，并对旧模型保留原生成方式。数值合法、在分布内、代码接入、实际效果可靠是四个不同层次，不能互相替代。
