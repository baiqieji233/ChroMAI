# Composer 训练供数优化（2026-10-29）

## 为什么准备数据已经加快，训练仍然慢

开训前准备负责解析歌曲、读取音频缓存。进入训练后，每个样本还要查询96个候选拍点、滑条当前经过的感应区、近期配置、物量标签和周期结构。此前这些查询大多按单个样本执行，邻近样本会重复计算。

v22 的现场记录显示，第一轮约47.9分钟，其中约574秒直接在等下一批数据。供数线程占两次 Python 持锁采样的88%和89%。这些百分比是持锁栈样本比例，不能解释为总训练耗时；它们与空预取队列、等待数据的日志一起，定位到了供数和主线程争用这条路径。

## 本次改了什么

1. **滑条计算一次处理多个时刻。** 保留原有等待时间、分段时长和 Wifi 分支，用一次数组计算判断感应区；非常接近感应区边界时仍使用原来的距离判断。
2. **相邻样本复用滑条结果。** 每个状态索引最多缓存1024条精确时刻的几何结果。缓存不保存整份样本，不改变时间精度；可见前缀仍先检查，未来谱面事件不能通过缓存进入输入。追加、替换标记或修改相关几何字段会使旧结果失效。
3. **同首谱面的查询合并。** 数据集新增批量读取入口，将音频插值、物量、周期结构、占用标签和前缀统计合并查询，再按原顺序返回样本。每个样本的候选拍点、随机探针相位、标签权重和已提交前缀仍独立保留。
4. **供数让出模型前向的提交时间。** 沿用已有暂停机制，在传输和前向提交阶段暂停后续供数；提交完成后恢复供数，与原生反向计算重叠。每次供数最多处理8个样本后重新检查暂停状态，异常退出时也会恢复线程。
5. **CUDA 的CPU自动线程数不再放大。** “CPU 算子线程”设为0时，CUDA训练最多使用2个Torch CPU线程；CPU训练仍保留环境设置。明确填写的线程数保持有效。
6. **不再强制高频切换Python线程。** 删除训练循环强制设置的0.5毫秒线程切换间隔，保留运行环境的正常设置（本机新进程为5毫秒）。已有供数暂停机制负责给前向提交让出时间，无需再靠频繁交接执行锁解决争用。

模型结构、训练目标、采样规则和质量分支保持原样。这次主要改变计算方式和执行顺序。

## 参数怎样选

沿用主界面的默认值：“CPU 算子线程”2，“样本准备线程”1，“预取 batch 数”2。它们是起点，实际收益以同一批样本的测量为准。增加预取深度不会自动增加生产速度，增加供数线程也可能重新带来争用。

v22原始完整检查点和推理检查点已额外复制到 `checkpoints/prism_composer_v22/archive/performance_before_cpu_batch_20261029/`。修改开始时，原训练任务已处于取消状态，没有对其发送停止请求。

## 验证记录

全部实现完成后执行了统一回归：**1030项 Python 测试通过，1项跳过；57项界面测试通过**。测试覆盖批量与单样本输入逐张量一致、同一批内不同前缀不泄露未来、滑条分段与Wifi、缓存失效和容量限制、预取顺序、随机状态、异常及提前退出。

真实数据对照使用10首官谱、固定96样本一批、128事件历史、96候选点、33动作槽；先预热6批，再测48批。三组使用同一v22推理检查点、相同样本顺序和BF16，开启与正式训练一致的紧凑音频查询。对照在独立进程中顺序执行，没有其他回归测试并行抢占CPU。

| 受控GPU流水线 | CPU算子/样本准备线程 | Python切换间隔 | 样本/秒 |
| --- | --- | --- | ---: |
| 修改前快照 | 16 / 4 | 原代码强制0.5毫秒 | 147.9 |
| 本次修改，保留原线程数 | 16 / 4 | 环境默认5毫秒 | 338.0 |
| 本次修改，使用界面默认线程数 | 2 / 1 | 环境默认5毫秒 | 392.8 |

同线程设置下约为原来的**2.29倍**；使用默认线程数约为**2.66倍**。这不是把新模块关闭后的结果：三组首个完整对照批次的全部张量哈希一致，48批平均loss均为 `7.162450313568115`，所有loss有限。

这项测量包括供数、传输、声学查询、模型前向、loss和反向；**不包括优化器更新、恢复训练、验证及保存**，因此不能据此承诺整轮训练也快2.66倍。前述纯CPU供数短测的475→613样本/秒约提升29%，使用的是非紧凑音频查询，只作为独立的供数诊断记录。

为单独检查线程切换设置，还用旧输入实现、相同16/4线程和非紧凑查询对照过0.5毫秒与5毫秒，得到约164与245样本/秒。它支持移除强制高频切换，但不应把这项比例与批量计算收益直接相加。

随后通过实际训练入口，在独立测试目录完成12个CUDA batch、**2次AdamW参数更新和完整检查点保存**。运行日志确认“CPU算子线程=0”实际取2线程，Python切换间隔为5毫秒，未出现非有限损失或保存失败。该测试是从头初始化的10首歌功能验证，不用于判断谱面质量或对比原v22的loss。

原v22的完整点与推理点均与额外备份的SHA256一致。原长训没有重启，测试产物只在 `.scratch/composer_cpu_optimization_20261029/training_smoke/`，不能拿这份两次更新的测试模型替代v22。

诊断与基准脚本保存在 `.scratch/composer_cpu_optimization_20261029/`；修改前的源文件快照也在该目录。稳定保存的结果、源文件哈希和检查点校验见验证证据（本地开发资料，不随源码发布）。有一份与回归测试重叠的预备测量已标记排除，没有用于以上结论。

吞吐测试只证明计算效率。输入等价检查用于确认本次优化保留了训练信息，不代表已经证明谱面音乐质量提升。
