# 开头空白与错过入口后的恢复：原因和修复

> 后续已补回基于真实音符前文的主动留白与句尾收束，最新合同为 v11，见 [主动留白与 v48 微调](COMPOSER_ACTIVE_REST_20261103_ZH.md)。下文 v10 的纯音乐判断是前一阶段记录。

## 为什么会空写

已有输出 `38900d7238e6`、`9463b9f752ff` 的第一颗音分别在 26.53 秒、24.00 秒；原音频约第一秒后已有明显声音。另有输出先在 1.30 秒放一颗，随后空到 9.41 秒。生成记录显示是模型主动反复选择两拍 WAIT，没有发生强制休止或撤回音符。

音乐事件率和解码器原来各有一票。音乐分支已判断未来两拍应该出音，解码器仍可用很大的反向得分推翻它。v47 step 3504 的只读探针中，音乐分支给出约 74% 的出音概率，合并后仅剩 0.44%。同一歌曲第 8 拍，仅把连续休止历史换为已有输出中的出音历史，出音概率从 0.52% 升到 84.29%。生成报告使用 step 3000，两者不是同一次权重回放。

## 新的分工

新版 `audio_hazard_v3` 直接复用现有音乐事件率，不增加编码器。累计未来两拍的预计事件数为 Λ，则“这段没有音符”的概率是 exp(-Λ)，“有音符”的概率是 1-exp(-Λ)。到曲尾时，同样的无事件概率交给 EOS。正常休止仍有完整的概率和真实标签，不插入音符、不限制最长空白，也不改变温度。

解码器继续决定具体拍点、配置及衔接；历史和短句模式不再另外否决出音。整曲数值风格仍影响音乐事件率。出音、休止误差现在直接训练事件率，而非只训练一个能绕开它的符号分类器。原来的逐时间格计数监督保留；NOTE、WAIT、EOS 的误差分别报告，不另加一份重复损失。

## 让模型见过“已经错过入口”的历史

新训练配方 `musical_entry_recovery_v9` 在原有 15% 历史增强预算内加入两类样本：删除部分过去音符、用真实两拍 WAIT 到达原有决策位置，继续预测下一颗真实音符；以及用相同方式构造历史，但真实答案仍为休止或结束。只删除过去内容，不把未来答案塞进输入，不回填已经错过的音符。

这些样本训练真实出音与拍点。被改过的配置历史不能唯一确定官谱的键位，因此不强迫它复制一个失去依据的配置答案。所有持续动作状态和短句记忆按实际保留的前缀重建。

增强替换已有样本，不加大 batch，不增加音频主干前向次数。原样本的事件预算、音乐计划预算、谱面身份和整曲风格权重保持一致。原有正常样本和配置循环恢复仍保留。

## 使用与检查点

主界面新训练或微调的“学习方案”保持“自动”。高级选项“出音与休止判断”默认 `audio_hazard_v3`，“错误历史构造”默认 `musical_entry_recovery_v9`。旧权重仍按原合同生成；本次训练侧修复需要在新目录建立新阶段，不会自动改变旧权重。

v47 step 3504 原始完整点、推理点另存于 `.scratch/rest_reentry_20261103/parent/`，原目录不覆盖。训练目标版本改为 `stream_audio_hazard_entry_recovery_v10`，旧优化器阶段不能直接冒充新版续训。没有启动新的正式训练。

另保存了只迁移接口、尚未训练的推理权重 `.scratch/rest_reentry_20261103/migrated/composer_inference.pt`，供生成验证或作为新阶段的初始权重。它沿用 v47 的其余参数，改用新版出音概率，更新步数为 0；父权重步数为 3504。它不是已经训练好的 v48，也不能把验证探针的概率改善当成整谱质量结论。更早期使用“每格计数”单位的权重不能直接套用新版速率合同，应 fresh；v47 使用每秒速率，不受这一限制。

## 验证

全部修改完成后，1021 项相关 Python 回归、34 项界面 JavaScript 测试通过。包括：

- 相同音乐和时钟下，把历史改成连续 WAIT，不改变新版出音概率；极端短句模式偏置也无法重新否决出音。
- NOTE 标签推动音乐事件率上升，真实 WAIT 和 EOS 标签推动它下降；曲尾没有另外一套固定结束概率。
- 恢复历史不读取下一颗音符的内容；变 BPM 后保留的旧 Hold 状态与正常前缀重放一致。
- 替换样本后的事件、计划及整曲风格预算一致；真实数据生产流程实际接入了漏写入口样本和真实休止对照。

冻结同一份 step 3504 权重，不更新参数、不生成新谱，在原音频上只切换出音接口：

| 位置与历史 | 原出音概率 | 新出音概率 |
|---|---:|---:|
| 第一首，第 4 拍，此前全休止 | 0.44% | 74.15% |
| 第一首，第 8 拍，此前全休止 | 0.58% | 77.88% |
| 第二首，第 8 拍，此前全休止 | 0.52% | 59.61% |

第一首第零拍的新休止概率仍为 91.14%。修复不是把所有位置都变成“必须出音”，而是不再让历史把音乐判断压掉。

使用一首真实开发曲目的 16 条完整窗口，序列最长 173，BF16，比较相同数据的完整前向、损失和反向：旧版平均 0.397 秒，新版 0.388 秒；有效监督预算吞吐约 1394 → 1427 步/秒，峰值已分配显存 2.531 → 2.548 GB。两侧梯度和损失均有限，没有执行优化器更新。这个约 2% 的差异不能宣称长期提速，但没有观察到计算退化；也不能与整轮吞吐混称。

在相同真实窗口和增强比例下，数据生产／拼批的热身后中位耗时约 0.098 → 0.073 秒。新旧配方随机抽到的增强种类不同，这只能排除本次样本上的明显准备退化，不能据此承诺普遍加速。额外的覆盖检查中，真实生产流程生成了 2 个漏写入口、4 个正常休止对照；一个入口样本删除了此前 23 个事件、经过 14 拍等待后，仍监督原先第 44 拍的下一颗音符。

主界面后台已在原端口 **7861** 重载，确认没有运行中的任务后才重载。实际 HTTP 检查确认新控件已提供，旧 v47 可初始化新阶段、不可直接按新目标 resume；迁移预览点可识别为新版。原始完整点和推理点与备份的 SHA256 相同。
