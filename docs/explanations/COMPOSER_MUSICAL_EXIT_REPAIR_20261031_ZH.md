# 八分回旋自强化：原因、修复与验证

2026-10-31。适用路线：`event_set_stream_v1`。本轮没有修改生成温度来冒充修复，也没有增加重复次数上限或重复扣分。

实现中的音乐与选时接口缺口已补齐，固定对照中的持续回旋明显减轻；**“音乐能稳定推动配置变化”尚未通过验收**。原v35保留，未启动正式长训。下面分别说明实现事实、对照结果及仍需解决的问题。

## 为什么v35在贪心下绕圈

第8000步的实际输出有854个事件，其中853个Tap、1个Hold；连续310次八分间隔，同方向最多连续98次转动。配置重试为0，不能解释为复杂配置被守卫删掉。

邻近8274点的CPU探针显示，进入这些前缀后，模型对八分间隔和沿原方向接下一个键的概率已经很高。贪心把这种倾向变成确定轨迹。探针来自另存的8274点，不冒充原8000点精确复现。

这次找到三处具体缺口：

1. **音乐比较进不了关键选时决定。** 候选音乐与上下文的交互分数原来只参与同一拍位组内的选择。八分候选常独占一组，减去组内归一化值后，音乐交互被完全抵消，无法改变该组总概率。
2. **训练没有覆盖这种错误历史。** 原扰动主要是同键、ABAB、Touch等4～12事件短循环，没有持续顺/逆回旋。主要恢复样本只替换2个事件，长池最多64事件，且主要用随机采样，覆盖不到实际出现的百步贪心循环。
3. **“出口损失”没有单独表达应该改变什么。** 原实现把节奏、方向、类型等出口合为一个标签，再给整套事件预测额外加权。改变类型和改变方向不是同一件事；多个具体出口的概率加起来很高，也可能因分散而在逐项贪心时输给单个继续选项。

另一个怀疑已经排除为本次主要原因：移除动作融合后的历史、负担和运动附加通路，六处探针都没有改变键位首选。清空当前音乐反而让原键位更确定。音乐已经在减弱惯性，不能据此声称模型完全没用音乐，也没有因此重写这些通路。

## 改动方式

### 把音乐交互接回拍位组选择

先试验 `query_pool_v2`：保留原组内选择，把候选音乐交互按合法候选数量归一后，另外送进组选择。候选多的组不会仅因数量多获利；独占一组的候选也重新获得音乐监督。

不过它仍把交互压成一个分数，再通过从0开始学习的单标量。三个400步试验中，这个系数只学到约0.0023～0.0026。最终改用 `query_pool_v3`：直接把已有的32维音乐特征与32维上下文逐项比较，再学习各维对拍位组的作用；按合法数量取均值，避免候选多的组占便宜。新投影从0开始、学习尺度放大8倍，旧V2投影保留用于已有权重迁移。只增加32个参数，不增加音频编码器或注意力。音乐交互在初始时不会改变原概率，后续也不再只依靠一个共同系数。

这里没有只看系数大小就下结论：在同6处固定前缀中，V2新增交互项对拍位组的实际贡献绝对值最大约0.0054 logit，旧的线性候选音乐项则可到0.95～2.69。已有音频通路确实工作；弱的是新增的“结合当前上下文解读候选音乐”交互，二者应分开看。

### 一套小网络，学习三个继续／退出决定

最终使用 `music_exit_v3`。共享一个32宽的小网络，分别预测：是否沿用当前间隔、是否沿用当前运动、是否沿用当前配置模板。模板指忽略整体旋转后的配置形状，例如各个键上的单Tap属于同一种模板。

输入包括当前与上一音对应的音乐差异、接下来八拍内的六个固定音乐探针、当前模式持续次数/时长、实际相对运动和带音符类型的键位布局、拍位及用户条件。它知道自己在延续哪种配置，而不只看到一个抽象的“重复长度”。不输入未来原谱音符。复用已有32维音频键，不增加另一套大型编码器。

V3还补齐了时间参考：选时决定发生在当前音之后，比较当前音与严格前一个音对应的音乐；配置决定发生在选定的未来落点，比较未来落点与最近已写音。V2在前一种情况下读了两次同一点，音乐差和经过时长退化为0。没有更早音时用当前音乐作参考；经过WAIT后仍找最近的真实音，不虚构音乐变化。

原来选择每个音符的网络仍负责组内细节。新分解同时学习继续和退出，不是只在长串出现时加罚分。训练、恢复和正式生成使用同一概率结构。

一个简单例子：继续原写法占40%，换写法合计60%，但后者分散成很多个10%。逐项贪心会选40%的继续。现在先比较“继续40%／改变60%”，再决定具体怎样改变。这解释了为什么逐步预测看起来不错，整首严格贪心却可能不停沿同一路走；例子是概率结构说明，不是对某首歌的实测比例。

贪心顺序也同步改为：先决定继续还是退出，再在选中组里选择。选时进一步保留网格组→具体落点的层次；配置先选模板意图，再选类型和具体写法。重试固定本次意图，避免反复换类直到变成Touch。

对称双押的等价旋转会放在同一个运动组，避免“选择退出”后仍导出同一物理配置。没有规定转几圈就必须停；持续长度只是可学习的输入。

### 补上真正会遇到的长循环

默认使用 `musical_loop_recovery_v7`，保留同键、交替、顺逆回旋及可达的固定间隔回旋历史，长度分档覆盖4～128事件，多数仍是短历史。原谱后续目标保持不变，时间、占用与连续状态一起重建。边界不允许时跳过，不插入WAIT硬凑。

新增 `greedy_mixed_v4`：保留三份短恢复对一份长恢复的比例；短尾至少4事件。长槽交替使用持久生成和直接构造的错误历史，最长128事件。直接构造可以改变历史事件数，但光标结束时间、原谱目标和音乐不变，所以不受“128个原音符的时长不够放128个一拍音符”的限制；目标也覆盖真实休止与结束。持久生成每次推进8步，另一种长槽不增加模型前向，不重新提取音频。

“支持128事件”是上限，不代表400步短训中的持久轨迹已经走满128。短训主要补到了构造的长历史；真实自产轨迹的长度要看每条episode的推进记录。后续若仍存在长循环，应优先用冻结旧模型在训练歌曲上生成的真实长错误前缀做离线回放，配原谱可达后续，避免只继续增大构造样本的出口偏置。回放可预先生成、训练时读缓存，无需每个主批额外展开128次。

V6/V4的第一次400步试验里，变事件数的长历史只实际训练到3行，仍会出现240音的十六分单Tap。因此V7把同类错误历史也接入普通批次：在原有15%扰动比例内分配一种模式，约1.7%的原始短段尝试替换。替换后只学习原短段第一个可信目标，把该短段原有的总权重集中到这个决定；整批损失预算和歌曲密度监督预算保持不变。既不再额外跑一次模型，也不把这些样本无上限加权。这样模型会更频繁地遇到“音乐已变、自己却写了很久相同配置”的输入。

V7实际覆盖到90行，却仍生成234个连续十六分间隔；零更新迁移后的贪心对照也有240个。它增加了错误历史数量，但不能证明已经学会长节奏出口。一个具体不足是：随便取后续目标时，目标本身可能仍是单Tap，无法针对真正的换写法位置建立足够训练。

另外试验了V8：在这些长历史样本中，每四份约三份优先取**原窗口里真实换模板、换间隔或进入休止/结束的位置**，并让错误历史延续该位置之前的真实简单配置和间隔，最后一音与真实上一音对齐。另一份仍保留普通后续，包含应该继续的例子；没有可用出口时沿用普通样本。目标仍来自原谱，没有新增人工标签，也没有规定“重复多少次就结束”。

持续Hold/Slide等旧配置无法合法重复时，会退回普通错误历史或原行。日志分别记录选中了真实出口、实际对齐成功，以及时间/模板是否真正需要改变，避免把“尝试过”当成“训练到了”。

**V8没有设成默认。** 它在400步里训练到94行长历史，67行选中真实出口、49行成功对齐，但贪心变成196音ABAB和418音十六分间隔；不能因为同向回旋缩短就推广。实现、参数协议和失败产物保留，便于后续协作者复核。本轮最后的架构试验改回V7课程，单独检验32维音乐交互。

### loss没有额外叠三套分类

新继续／退出决定属于原事件概率的分解，直接进入原选时和配置损失。时间、运动、模板的decision loss另列为诊断项，不重复加到总loss。已有音频类型预算和真实出口位置的加权仍保留。

最终版把新头作为原组概率上的修正，而不替换主干已有判断：新继续log-odds = 原继续log-odds + 8 × 音乐/状态修正。原分布也继续接受梯度。修正初始为0时，概率及原学习路径保留；分层贪心本身仍可能与旧平面argmax选不同动作。系数8用于让新小头及时修正原来约4以上的过强log-odds，不是固定重复惩罚，修正既可增加也可降低继续概率。更换分解与错误历史配方仍必须进入新训练阶段，不能作为原模型精确续训。

## 为什么没有采用首版结果

首版 `music_exit_v1` 用一个独立的小头直接替换组概率。虽然同向长串明显缩短，但它在短训中破坏了主干原有判断：第一个采样种子的非四分之一拍落点升到约21%，重试668次；贪心又变成一拍连续200次。这不是稳定的质量提升。

最终版改为保留原组概率及其梯度，再学修正。同时确认并修复：旧运动特征把同键不动放在STAY通道，KEEP通道为空；首版没有给这类循环提供运动出口。V2将这种实际停留也纳入继续组。V6/V4进一步覆盖不同间隔和可变事件数的长错误历史，避免只处理特定八分回旋。

首版的点、训练日志和三个输出全部保留在`.scratch/musical_exit_repair_20261031/repair400`及同名前缀文件中。`residual400`、`timeline400`是中间试验，`anchored400`是未推广的V8课程；最终32维交互试验是`interaction400`。这些目录互不覆盖。

## 如何启用与怎样看结果

主工作台的“连续生成训练修复”选“自动”，新阶段使用 `music_exit_v3 + query_pool_v3 + musical_loop_recovery_v7 + greedy_mixed_v4`。“循环历史训练比例”仍为0.15，“转折学习权重”仍为0.5，没有增加一排反复读滑块。内部学习尺度及课程版本写入检查点配方，不靠记忆区分不同算法。

旧v35要采用这些改动，应选“训练方式 → 已有模型加强训练（finetune）”并使用新保存目录；“从断点继续（resume）”会保留旧策略。原点继续保留，验证点不自动替换正式模型。目前没有启动新的正式长训。

400次更新只消费6400个短段，不能与原v35“批次32、梯度累积8”的400次更新当成同样训练量。总loss仍包含选时、配置、密度计划及原有出口/恢复预算；新增的三个decision loss是拆开的诊断项，不会再加三遍。不同错误历史课程改变了学习难度，不能用短训总loss更低来代替闭环验收。

## 物理报告的口径也要分开

例如V7第二种子的最终报告有11条硬问题：10条SlideTooFast在生成守卫中原本配置为“只报告”，最终检查却按“执行”统计；另1条是Tap恰在Hold结束点，守卫允许结束点，最终静态检查仍含结束容差。不能把这些描述为新网络绕过了同一套守卫，也不能直接称为误报或全部可玩。本轮保留原检测结果和策略，没有为了让数字好看而隐藏报告或临时收紧规则。

对应入口是 `guard.py` 的 `EventGuard.config / enforced_native_hard_conflict` 与 `stream_generate.py` 导出后的 `PostProcessConfig`。后续协作者应先说明采用哪一种约束口径，再讨论是否需要改变，不要把两份数字混为一谈。

### 同权重消融没有证明新交互直接推动了这张贪心谱

进一步加载最终400步点，仅在内存中把 `query_interaction_projection.weight` 置0，其他权重、音频、种子、温度、守卫都不变。结果623事件及整份谱面文本**逐字节相同**，SHA256均为 `835543faa923aeb7f59359dce6cd76073fc94edc97fa4d308e3b947b549228ae`。

因此不能把本轮改善单独归功于新增32维交互。它在6处固定前缀的宏观贡献已到约0.044 logit，通路和梯度可用，但本次还没有改变这张贪心谱的选择。训练过程可能产生间接影响，这一点本轮没有单独证明。“音乐已经能稳定推动配置变化”仍是未通过的验收项。

后续优先验证真实自产长历史的离线回放，并在真实换写法边界与正常续写位置比较音乐干预后的出口概率。不要继续只提高出口样本比例：V8已经展示了循环从回旋转移成ABAB的风险。也不要把同一模板长度做成硬上限；合法长段也需要保留。
