# Composer v2 连续事件改造说明

日期：2026-11-04。仍是主界面的 `chart_composer_v2` 模型族；新训练目录为 `checkpoints/chart_composer_v2_v3`。

后续实测：[第400／900步时间前缀修复与长空白诊断](COMPOSER_V2_TIME_PREFIX_REPAIR_20261105_ZH.md)。已修复可用相位耗尽后的数字死路，并补齐普通涉冲突事件的撤回；逐字符绝对拍号造成的大跨度采样风险仍未解决。不要把本文的结构验收当作生成质量结论。

## 为什么这次要改

之前v2把16拍同时当作训练目标范围、生成结束位置和整段提交单位。它继承前文，但仍要求每个窗口输出一次结束符。这不符合选择流式路线的初衷：非常规拍子、五等分／七等分、跨拍配置不应被固定计算边界切断。

本轮取消的是这个绑定，不是把16换成1。新的音乐时间从整首歌起点连续编号，生成一次提交一个完整同拍事件。没有每拍WAIT，也没有每16拍EOS。

## 现在怎样写谱

一个完整事件包含：绝对整数拍、精确的分数相位、同拍各个音符、同拍事件结束标记。事件结束只表示这一拍的配置写完，下一步继续选下一个事件；它不结束音乐段落。

例如 `15 + 6/7` 后可以直接写到 `16`，再到 `16 + 1/7`。经过16拍时，不重新计数、不补齐、不换分音。长休止表现为下一事件在更远的位置，例如直接从20拍选择到50拍，不需要重复输出30次等待。

时间分数来自明确的节奏相位词表和训练谱实际位置，不从BPM浮点误差生成。默认包含分母1～32及48、64、96、128、192的相位，并合并训练谱的其他精确相位。原谱不吸附、不删掉非常规位置。固定检查点遇到词表之外的源相位会明确报错，不能用静默四舍五入伪装支持。

选时不再只有“上一颗音符再加多少”：整数拍和相位最终都落到整曲坐标。模型看到已经选定的整数拍后，会读取那一拍附近的局部音乐，再决定具体相位与配置。整曲音乐摘要继续可读，跨过长休止也不会只剩旧窗口的音频。

## 上下文仍然有限，但不规定音乐结束

默认保留最近16拍的实际音符，以及仍在持续的Hold／Slide和更早的参考片段。组件预算不足时，先舍弃远处参考，再移除最旧的完整历史事件；未结束的持续动作不能随之丢失。

默认每16个已提交事件整理一次历史，或在组件预算不足时提前整理。**这是事件数的计算上限，不是16拍的输出边界。** 整理时不输出EOS，也不要求配置收束；具体拍位和持续动作照常继承。可在高级设置调整“历史整理间隔（事件数）”，小值会增加重算。

局部音乐输入也有分块，但这些块只是可复用的音频读取范围。各查询只访问自己已知拍位对应的音乐块；共享存储不代表可以读取未来谱面位置。全曲音乐本来就是可用输入，不属于未来谱面泄漏。

## 训练目标怎样改变

- 按完整事件及组件预算组织计算切片，不再按固定拍数切目标。
- 中间切片结束时停止该次计算，不追加假EOS。
- 只有一张真实谱面写完，才监督一次真正的结束。
- 同拍多押不能切成两个训练片段；时间和时值保持精确。
- 训练与生成使用同一套前文整理、时间编码、局部音乐读取和持续状态规则。
- 延续上一轮的Radar／Style已知值／自动状态区分。验证采用默认自动条件，避免把答案谱面的统计当作验证输入。

目标仍是下一组件交叉熵，不新加一套草稿、类型规划或密度强制损失。时间编码变化后，每个事件的组件数也变化，因此新旧总loss不能直接比较。

## 冲突与候选怎样处理

每个同拍事件完成后立即做原生检查。失败先重采当前事件，合法前文保留；确实需要撤回持续动作时，撤回它的准确起点事件及其后缀，不再向16拍边界取整。

默认仍单候选。当前连续实现的2／4候选在同一落点、相同原子数量下比较配置；多事件远期试写尚未在此新路径实现，不能把当前选优描述为整句质量评分。没有最低密度、空白长度限制、重复惩罚或强制副歌加密。

预算耗尽且尚未完成一个事件时，重试该候选，不会截出半颗音符。只训练几步的模型可能持续生成不完整参数，耗尽重试；这不应被报告成“请盲目增加token上限”。

## 效率修复与实测

最初的查询局部音乐实现存在重复工作：相邻音乐块大量重叠，却各自搬运并投影同一帧。已改为先合并读取、共享线性投影，再按查询分组进行独立编码。每组最多打包32个查询，避免一个密集拍位把其他组全部填充成大张量。

同样4张真实谱面、两个完整遍历、8批大小×4累积、同样42,878个目标组件：

| 实现 | 用时 | 目标组件/秒 | 显存峰值 |
|---|---:|---:|---:|
| 最初连续实现 | 25.44秒 | 1,686 | 约5.96GiB |
| 共享帧后 | 12.01秒 | 3,571 | 约5.64GiB |
| 再限制查询打包填充 | 11.15秒 | 3,846 | 约5.10GiB |

这是新实现内部的同数据对照，不是对旧模型整轮训练速度的证明。另做了8×2048组件的形状压力检查，BF16反向传播有限，峰值约4.94GiB；这也不替代全量数据的监测。

正式训练采用8×8，保持上一任务64个训练片段的有效批量。时间编码变长、训练切片重新组织，片段数和epoch用时不能直接与旧16拍窗口一一对应。

## 已验证什么，尚不能说明什么

- 七等分跨过原16拍边界，按1／3／16事件整理上下文，都能精确编译并还原指定事件序列；另覆盖五等分、十三等分及训练追加的1/101相位。
- 中间切片无EOS，实际终点有EOS；长休止目标没有WAIT循环。
- 改动未来查询独占的音乐块，不影响更早预测；批次补齐、共享音频帧与独立音频块的结果一致。
- 增量KV与完整重算一致；真实CUDA BF16更新已通过。实测曾发现FP32/BF16汇总类型不匹配，已修复并补回归。
- 撤回落在持续动作实际起点，不向固定拍数边界移动。
- 主界面显示新旧方式区别，fresh默认连续方式，旧点仍按旧合同读取。
- 4张谱面的64次更新验证了真实训练和序列生成链路；输出仍很不足，仅生成少量事件，**不构成音乐质量改善或罕见节奏已学会的证据**。

原有检查点不迁移成这个新时间语言。它们仍可按旧方式生成。新模型必须fresh；本轮启动的新任务不使用小样本测试权重作为父点。

验收：161项相关Python检查、238项JavaScript检查通过，随后对事件恢复与界面接线再次做了定向复查。结果与实际训练状态见 验收证据（本地开发资料，不随源码发布）。

全量任务已进入第1轮，前100次更新没有非有限更新跳过，约3,688目标组件/秒、显存峰值约5.24GiB，首个完整检查点已保存。仍有明显的数据准备等待（累计约208秒，计算提交与更新等待约135秒）；这不是GPU满载证明，第一轮验证和音乐质量也尚未完成。
