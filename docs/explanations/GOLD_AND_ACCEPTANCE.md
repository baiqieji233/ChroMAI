# 金标集与谱面验收（新手向完整指南）

这份文档回答两个问题：

1. **怎么让模型知道"这一段在歌曲的什么位置、有多强"？** —— 音频特征做了哪些改动，怎么看懂它们。
2. **怎么用你自己认可的好谱面，既当训练组、又当验收标准？** —— WebUI 里从零开始的操作步骤，以及每一项指标怎么看。

配套文档：[训练参数手册](../compatibility/TRAINING_PARAMETERS.md)（每个参数的作用与推荐值）。

---

## 一、先理解问题：为什么需要"金标集"

训练会给你两个数字：训练 loss 和 token 准确率。它们只说明"模型能不能复现训练数据"，
**不能说明谱面好不好**。具体有三个坑：

| 坑 | 表现 |
|---|---|
| 无法判断"学会"还是"背下" | 没有独立验证集时，`event_best.pt` 是按**训练** loss 选的，等于最后一个 epoch |
| 无法判断什么时候该停 | 早停、学习率下降都依赖验证集，没有就全程不触发 |
| 无法判断输出质量 | `syntax_valid: true` 只代表"能解析"，不代表像人写的谱面 |

**金标集**（gold set）就是解决这三件事：挑一批你认可的谱面，切成三份，让"好谱面"同时充当
**训练信号**和**验收尺子**。

| 名称 | 内容 | 用途 |
|---|---|---|
| **预训练集** `pretrain_manifest.json` | 整个语料，但**剔除**了金标验证曲 | 第一阶段：从头训练（新模型） |
| **金标微调集** `gold_finetune_manifest.json` | 金标曲中可训练的那部分 | 第二阶段：`finetune` 精调（学习"好谱面长什么样"） |
| **金标验证集** `gold_val_manifest.json` | 金标曲中**永不训练**的那部分 | 验收尺子 + 训练时的验证集 |
| **验收基准** `gold_stats.json` | 金标验证曲的各项指标分位区间 | 生成后逐项打分的依据 |

> **关键设计**：金标验证曲从预训练集里就已经剔除了。否则第一阶段就见过这些歌，
> 第二阶段的验证 loss 会虚低，验收失去意义。

## 二、音频特征改动：让"相对位置"和"相对强度"真正参与计算

### 2.1 改动前的状况

模型每帧收到 100 个数字，其中"位置"信息只有 1 个（`song_progress` = 音频时间比例），
"强度"信息则摊薄在 95 列里、还经过两次归一化。全曲记忆只有 **64 帧**：一首 160 秒的歌
等于**每 8 拍才有 1 个记忆 token**，模型根本没有能力比较"这一段和前面哪一段像"。

### 2.2 改动后：输入维度 100 → 108

**新增 3 个声学通道**（每首歌计算一次、带缓存，按内容哈希寻址）：

| 列名 | 含义 | 实测表现（真实歌曲） |
|---|---|---|
| `relative_rms` | 相对响度，**1.0 = 全曲中位响度**，2.0 = 两倍响度 | 中位数精确 1.000，范围 0～1.37 |
| `intensity_slope` | 该值 1 秒内的变化，**正 = 渐强，负 = 渐弱** | p05 −0.355，p95 +0.345，两种符号都有 |
| `harmonic_novelty` | 和声新颖度：**稳定段落 ≈ 0，段落变化处冲高到 1** | 中位数 0.046，p99 = 1.000 |

`harmonic_novelty` 的算法是"比较某帧**前 2 秒**与**后 2 秒**的平均 chroma 的余弦距离"。
因为比较的是窗口平均值，段落内部的换和弦会被平均掉，只有真正的段落边界才会冲高——
这正是"这一段是不是换了段落"的廉价而可靠的信号。

**新增 5 个时序上下文通道**（每个片段动态计算）：

| 列名 | 含义 |
|---|---|
| `beat_progress` | 按**拍**计算的歌曲进度（0→1），比"音频时间比例"更贴合音乐结构 |
| `bar_phase_sin/cos` | 当前在**小节（4 拍）**内的相位 |
| `phrase_phase_sin/cos` | 当前在**乐句（16 拍 = 4 小节）**内的相位 |

实测：`beat_progress` 从 0.000 单调升到 1.000；`bar_phase_sin` 过零 225 次 ≈ 每小节 2 次（112 小节）；
`phrase_phase_sin` 过零 57 次 ≈ 每乐句 2 次（28 个乐句）。全部符合预期。

有了这几列，模型才可能学出"小节开头常出拍点""乐句结尾常留白""副歌更密"这类结构规律——
线性时间比例表达不了这些。

### 2.3 全曲记忆分辨率 64 → 256 帧

| | 改动前 | 改动后 |
|---|---|---|
| 160 秒歌曲的记忆分辨率 | 每 2.5 秒 1 帧（≈8 拍） | **每 0.63 秒 1 帧（≈2 拍）** |
| 单曲内存开销 | 26 KB | 110 KB |

代价是编码器注意力变长（全曲记忆是**拼接**在片段之后的），训练每轮会慢一些，换来的是
模型能"回头看"前面相似的段落。可以用 `--global-frames` 调整。

### 2.4 重要：这些改动必须重新训练

`input_dim` 写在 checkpoint 的数据合同里，从 100 变成 108 后：

- ✅ **不需要重新预处理**（音频特征缓存会自动失效并按需重建；manifest 不用动）
- ❌ **旧 checkpoint 不能续训、不能微调**——加载时会明确报错
  `事件模型数据合同 input_dim 不兼容：已有=100，当前=108`

第一次用新特征训练时，特征提取会重新跑一遍（每首歌约 3 秒，可并行）。

## 三、WebUI 操作流程（从这里开始照做）

> 前置：已经在「1. 训练集」里完成预处理，并且「训练 manifest」指向那份清单。

### 第 1 步：建一个 gold 文件夹，把好谱面放进去（推荐做法）

在**训练集目录**下新建 `gold` 文件夹，每首金标曲放成**独立文件夹**，格式和训练集里的歌完全一样：

```
训练集目录\                          ← 例如 ...\datasets\simai训练集\12426737\
├─ 某首歌\                           ← 普通训练数据（本来就是这样的）
│    maidata.txt
│    track.mp3
└─ gold\                             ← 新建这个文件夹
    ├─ GoodChart1\
    │    maidata.txt
    │    track.mp3
    ├─ GoodChart2\
    │    maidata.txt
    │    track.mp3
    └─ 2024精选\                      ← 可以再嵌套分类
        └─ GoodChart3\
             maidata.txt
             track.mp3
```

**六条规则**：

| # | 规则 | 说明 |
|---|---|---|
| ① | 每首歌一个**独立文件夹** | 和训练集歌曲的格式完全一致 |
| ② | 文件夹里必须有 `maidata.txt` | 缺少会被跳过并在界面上列明原因 |
| ③ | 音频必须是 `track.mp3` / `track.wav` / `track.ogg` | 这三个文件名之一，别的名字会被当成"没有音频"跳过 |
| ④ | 可以嵌套多层 | `gold/2024精选/GoodChart1/` 也认；隐藏目录（`.` 开头）与 `.miacode` 自动忽略 |
| ⑤ | **可以放新歌** | 不在原训练集里的曲子也能用，程序会自动纳入 |
| ⑥ | 数量随意 | 建议金标验证集 ≥30 首（默认留 30%），验证区间才稳 |

> 注意：`gold` 是**放谱面**的文件夹；**输出**（三份 manifest + `gold_stats.json`）会写到另一个目录
> （默认 `<训练集目录>\gold_set`），两者不要同名。

### 第 2 步：扫描确认

训练区 **「G. 金标集（高质量谱面）」**：

1. 「金标来源」保持默认 **「从 gold 文件夹自动生成（推荐）」**。
2. 「gold 文件夹路径」留空即自动使用「原始训练集目录」下的 `gold`（也可手动填别处）。
3. 点 **「扫描 gold 文件夹」**。界面会列出找到的曲子，并逐条说明哪些被跳过、为什么
   （例如 `NoAudio — audio_missing`）。

### 第 3 步：生成金标集切分

设置：

| 字段 | 怎么填 |
|---|---|
| 金标验证集比例 | 默认 `0.3`。留出**永不训练**的比例，建议对应 ≥30 首 |
| 最少音符数 | 默认 `300`，剔除教学谱/稀疏谱；填 0 不限制 |
| 输出目录 | 留空 = `<训练集目录>\gold_set` |

点 **「生成金标集切分」**。程序会：切分 → 写出三份 manifest → 测量金标验证曲 → 写出 `gold_stats.json`。

**完成后界面自动做三件事**：

1. 「训练 manifest」自动改为 **预训练集**；
2. 「验证 manifest」自动改为 **金标验证集**；
3. 「金标统计」自动填上 `gold_stats.json`，并显示构成条形图：

```
┌──────────────────────────┬──────────────┐
│  预训练 929 首            │ 金标验证 74 首（不训练） │
└──────────────────────────┴──────────────┘
```

> **重复保护**：如果你的 gold 谱面同时也存在于训练集里（例如本来就放在语料中），
> 程序会自动把**金标验证曲**从预训练集里剔除——按"谱面内容哈希"匹配，就算你把文件复制到别处、
> 改了文件夹名字也能认出来。所以验证损失始终可信。

### 第 4 步：两阶段训练

| 阶段 | 训练方式 | manifest | 验证 manifest | 学习率 |
|---|---|---|---|---|
| ① 预训练 | `fresh`（从头） | 预训练集 | 金标验证集 | 2e-4 |
| ② 精调 | `finetune`（已有模型加强训练） | 金标微调集 | 金标验证集 | **2e-5** |

要点：

- 两个阶段的「验证 manifest」都填**金标验证集**——这样"选哪个 checkpoint"始终由
  "能不能预测好谱面"决定。
- 第二阶段 `finetune` 只加载权重、不校验数据集指纹，因此可以安全地换到金标微调集。
- 建议 `patience` 填 3–5，两阶段都让它自动早停。
- 每个阶段的 checkpoint 建议放不同目录（如 `checkpoints/event_v3/stage1`、`stage2`）。

推荐一次配置（本项目 1000 首语料、RTX 5070 Ti 12 GB）：

| 参数 | 阶段① | 阶段② |
|---|---|---|
| epochs | 60 | 15 |
| patience | 4 | 3 |
| segment beats | 16 | 16 |
| max_tokens | 640 | 640 |
| batch size / 累积 | 32 / 1 | 16 / 1 |
| d_model / 层数 / 头数 / ffn | 320 / 8 / 8 / 1280 | 同左 |
| dropout / weight decay | 0.1 / 0.01 | 0.1 / 0.01 |
| 音频缓存上限 | 4 GB | 4 GB |

> `segment_beats` 与 `max_tokens` 属于数据合同：选了就要两阶段保持一致，且必须从头训练。

### 第 5 步：生成并看验收报告

生成区的 **「F. 谱面验收」**：

1. 确认「金标统计 gold_stats.json」已填（第 3 步自动填过）。
2. 正常生成谱面。**生成完成后会自动出现验收报告**（因为填了金标统计，生成时就直接算了）。
3. 想复核历史产物：把「待验收谱面」和「对应音频」填上，点 **「验收谱面」**。

## 四、验收报告怎么看

### 4.1 时序图（最直观的一张图）

```
密度峰值 27/点 ┤                                    ╭╮
             │      ▁▃▅█▅▃▁      ▁▃▅█▅▃▁     ▁▃▅▅▃▁
相对强度 1.0 ┤  ～～～╱～～～╲～～～╱～～～╲～～～～～
             │▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒
             └────────────────────────────────────
              0s                               158.9s
              ▒ = 空白小节（黄色阴影）
              ▁▃█ = 谱面音符密度（红色柱）
              ～ = 歌曲相对强度（青线，1.0 = 全曲中位响度）
```

**怎么读**：红柱（谱面在写什么）应该跟着青线（音乐在做什么）起伏；黄色阴影越少越好。
如果某段青线很高而红柱是空的，就是"音乐激烈但谱面没写"——直接能看出来。

### 4.2 指标表（逐项 PASS / WARN / FAIL）

| 判据 | 图标 | 含义 |
|---|---|---|
| ✔ 通过 | 绿 | 落在金标区间的 p10–p90 内 |
| ! 注意 | 黄 | 落在 p05–p95 内但出了 p10–p90，属于边缘 |
| ✘ 不达标 | 红 | 超出 p05–p95，明显不像好谱面 |
| ? 未知 | 灰 | 没算出该指标（缺音频，或金标数据不足） |

**整体判定**：只要有一项 ✘ 就是 `fail`；否则有 ! 就是 `warn`；全 ✔ 就是 `pass`。

### 4.3 十一项指标的含义与金标实测值

下表右列是**本项目真实金标曲**（未参与训练）实测出来的范围，可作为量级参考：

| 指标 | 含义 | 金标实测（3 首样本） |
|---|---|---|
| 平均音符密度 | 每秒平均音符数 | 3.9 – 7.0 /s |
| 峰值密度 | 最密一秒的音符数 | 9 – 27 |
| 和弦比例 | 同时按多键的比例 | 0.24 – 0.29 |
| 滑条比例 | 滑条占比（风格指纹） | 0.065 – 0.166 |
| 触摸音符比例 | touch 占比（风格指纹） | 0.00 – 0.052 |
| Jack 连打比例 | 短时间内重复同键的比例 | 0.11 – 0.22 |
| 按键分布熵 | 8 键使用是否均衡 | 0.995 – 0.999 |
| **空白小节比例** | 完全没有音符的小节占比 | **0.031 – 0.063** |
| **最长连续空白** | 空小节最长连续时长 | **2.5 – 6.5 秒** |
| 谱面覆盖率 | 最后一个音符占全曲时长比例 | 0.969 – 0.981 |
| **音频贴合度** | 响度包络与音符密度的相关性 | **0.32 – 0.68** |

另外两项绝对判据（不参与区间比较）：

| 判据 | 要求 |
|---|---|
| 语法合法 | 必须为真，否则谱面无法解析 |
| 重复按键 | 应为 0（同一格同一个键敲两次属于非法单元） |

### 4.4 对照：一个真实的失败例子

本项目早期某次生成（`segment_beats=256`、`max_tokens=1536`，训练窗口的 token 预算只够覆盖 51.6% 的窗口）：

| 指标 | 该次生成 | 金标范围 | 判定 |
|---|---|---|---|
| 空白小节比例 | **0.343** | 0.031 – 0.063 | ✘ 不达标 |
| 最长连续空白 | **32.3 秒** | 2.5 – 6.5 秒 | ✘ 不达标 |
| 窗口闭合率 | 3 个窗口只闭合 1 个 | — | 结构性缺陷 |

**41 拍 → 105 拍的大段空白每隔约 256 拍出现一次**，两端正好落在窗口边界上——
这就是"每隔一段时间出现大段空白"的根因：窗口的 token 预算耗尽后，`_merge_windows`
会严格裁掉越界音符，剩余拍数永久空白。验收报告把这个问题从"凭感觉"变成了
"空白 34.3% vs 金标 6%，最长 32 秒 vs 金标 6 秒"。

## 五、命令行等价做法（批量/自动化）

```powershell
$env:PYTHONPATH="E:\simai_transformer\src"

# 1) 只扫描 gold 文件夹，看看能找到什么（不写文件）
python -m maichart.training.gold_set `
  "webui_workspace\datasets\simai训练集\12426737\training_manifest.json" `
  --out-dir "webui_workspace\datasets\simai训练集\12426737\gold_set" --scan

# 2) 从 gold 文件夹生成金标切分 + 验收基准
python -m maichart.training.gold_set `
  "webui_workspace\datasets\simai训练集\12426737\training_manifest.json" `
  --out-dir "webui_workspace\datasets\simai训练集\12426737\gold_set" `
  --cache-dir "webui_workspace\datasets\simai训练集\12426737\cache" `
  --gold-root "webui_workspace\datasets\simai训练集\12426737\gold" `
  --val-ratio 0.3 --min-note-count 300

# 2b) 备选：不建文件夹，直接从现有训练集按谱师名挑
python -m maichart.training.gold_set <manifest> --out-dir <dir> `
  --designers "はっぴー,Jack" --val-ratio 0.3 --min-note-count 300

# 3) 单独验收一份谱面（可与金标对比，也可只给绝对判据）
python -m maichart.generation.acceptance "webui_workspace\generated\maidata.txt" `
  --audio "webui_workspace\uploads\<歌曲>.mp3" `
  --gold-stats "webui_workspace\datasets\simai训练集\12426737\gold_set\gold_stats.json" `
  --cache-dir "webui_workspace\datasets\simai训练集\12426737\cache" `
  -o "webui_workspace\generated\acceptance.json"

# 4) 生成时直接附带验收（WebUI 勾选金标统计时等价于此）
python -m maichart.generation.event_cli --checkpoint <pt> --audio <mp3> `
  --output out\maidata.txt --gold-stats <gold_stats.json>
```

`acceptance.json` 里包含 `criteria`（逐项判定）、`metrics`（原始数值）、
`timeline`（时序图用的采样点与空白区间），可直接喂给别的脚本做批量回归。

## 六、常见问题

**Q：金标验证集要留多少？**
至少 30 首（本项目默认 0.3 → 74 首 / 104 个难度）。太少的话分位区间会抖动，
某首歌的偶然性会被放大成"标准"。

**Q：找不到谱师名怎么办？**
两种方式二选一：
- **推荐**：直接建 `gold` 文件夹，把你认可的好谱面放进去（不依赖数据集里的谱师字段）；
- 备选：把「金标来源」切到「从现有训练集里按谱师名挑选」，先点「列出本数据集的谱师」看统计。
  若清单里 `&des` 为空（会显示 `<未填写>`），就只能用「指定歌曲 ID」逐首挑。

**Q：gold 里的谱面会被算进训练集吗？**
取决于它是否也在训练集里：
- 如果 gold 里的曲子是**新歌**，它们只出现在金标微调集与金标验证集里，预训练集不含它们（无需剔除）；
- 如果这些谱面**同时也在语料中**（例如你直接把语料里的好谱复制进 gold），程序会把**金标验证曲**
  从预训练集里自动剔除（按谱面内容哈希匹配，复制/改名也认得出），确保验收有效。
  界面会显示"已从预训练集中剔除 N 首重复曲"。

**Q：gold 里的歌需要单独预处理吗？**
不需要。音频特征是在训练/预提取时按需生成的，与语料共用同一个 cache 目录，金标曲会自动一起算。

**Q：我把 gold 文件夹放错地方了会怎样？**
「扫描 gold 文件夹」会明确告诉你"还没有 gold 文件夹：<路径>"，并显示程序实际查找的路径。
你也可以在「gold 文件夹路径」里直接填绝对路径。

**Q：验收结果全是 `unknown`？**
说明缺指标：没填音频（缺"音频贴合度"）或金标曲太少（金标少于 3 个谱面时不给区间）。
补上音频、扩大金标集即可。

**Q：某项 FAIL，我该改什么？**
按指标对症：

| FAIL 项 | 常见原因 | 处理 |
|---|---|---|
| 空白小节比例 / 最长空白 | 窗口 token 预算不够（截断） | 减小 `segment_beats`、提高 `max_tokens`（两者必须配套，见训练手册 §3.4） |
| 覆盖率低 | 模型提前停止（`<eos>` 来得太早） | 加训练数据、继续训练、检查 `windows_closed` |
| 音频贴合度低 | 模型没学会跟随音乐 | 用新特征（108 维）重训；确认训练时音频缓存是新的 |
| 密度 / 和弦 / 滑条偏离 | 风格不匹配 | 用金标集做第二阶段 `finetune`；检查条件（等级/风格）是否合理 |
| 重复按键 | 解码期缺陷 | 已由解码语法拦截；若出现说明是旧代码，报告里会列具体小节 |

**Q：改了这一堆，我原来的模型还能用吗？**
不能续训/微调（`input_dim` 100→108），但**谱面数据、预处理缓存、金标切分都还能用**。
旧模型仍可用于生成（用旧代码分支），只是不含新的结构特征。

**Q：一次验收要多久？**
谱面解析 + 金标对比是秒级；若音频特征未缓存，需要重新提取（每首歌约 3 秒）。
重复验收同一首歌会命中缓存，几乎瞬时。
