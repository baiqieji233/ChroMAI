# 连续流训练速度修复（2026-10-18）

基线提交4823059。用户要求定位本次关联输入修改造成的速度退化，允许修复后停止无checkpoint的Prism_stream_v5并按原参数重新开始；模型结构、训练目标、数据顺序和谱面拍位表达保持。

## 已确认的根因

- 实际任务`9d281b7a9802`：batch4，累积8，宽度384/6层，细节8192节点，预取2，准备线程4；但准备线程只作用于开头FormDataset，训练期仍只有1个预取线程依次处理四个样本。
- epoch1 batch175用时1559.625秒，约0.1122 batch/秒。GPU采样利用率2%，训练进程约1个CPU核；尚无权重文件，保存间隔500更新大于本轮339次更新。
- 对PID30332只读py-spy采样20秒（25Hz）：19.12秒的活跃采样位于数据预取线程，17.2秒位于`detail_queries`，主训练线程仅0.2秒。采样不含睡眠线程，不能把它当CUDA硬件时间；但足以确定本次主要堵在CPU细节证据首次构建。
- `native_measured_v2`每个节点测5个音频窗口；旧实现五个都做完整FFT、Mel、Chroma及短瞬态，而后续仅使用中心完整特征、±40ms的RMS、±10ms的Chroma。8192节点扩大了这些无用计算，已有1024节点查询缓存不能替代新查询。
- 上次19.4%的短基准测的是已准备张量的GPU计算，不能代表全量随机歌曲冷缓存吞吐。此次必须分别测冷缓存、磁盘热缓存、内存热缓存和实际重启后的近期速度。
- 旧生产训练log明确使用`cache/chart_stream_v1`，新任务使用`E:\全量官谱\cache`；旧发现规则不包含项目的stream默认子目录。因此初始结构准备命中0、重建全部谱面，还发生了一部分旧音频/1024查询缓存无法复用。新增8192查询本来也需要首次构建，不能把二者混同。

## 已实施

- 按实际需要计算邻近窗口特征；不改时间中心、FFT尺寸、归一化、音频节点或输出拍位。
- 不同源音频线程并行、同源串行；查询LRU加锁，构建按key互斥，缓存预算不按线程复制。
- CPU算子线程设有可调预算；对照1/4数据线程，不把线程数越大越快当作假设。
- 日志增加近期速度、等数据/传输提交/主机计算/保存时间、预取等待和按查询种类累计准备时间。
- CLI/WebUI新增「训练数据准备线程」「CPU算子线程」，不修改训练语义合同或强制finetune。
- 已知stream历史默认缓存纳入候选目录，仍逐项核对内容哈希/时间轴/输入合同，未放松缓存有效性检查。

该组优化约2.34倍，最大输出特征差为0，串并行张量逐元素相同。没有减少8192节点预算，没有降低原生测量精度，没有改变谱面位置。

- 主集中回归115通过：音频原生测量/边界、流训练合同、真实4曲串并行全部样本字段等价、遮罩随机性、查询LRU并发互斥和预算、持续状态、API传参、预取等。
- 缓存专项13通过（和主集合部分重叠），前端11通过，JS语法和git diff检查通过。
- 真实GPU小型训练：384宽/6层/batch4/BF16，四谱23计算块，6批次、3次优化器更新及步骤权重保存完成；训练epoch用时5.813秒，其中主动每次更新保存的耗时约1.718秒。此项验证完整训练链路，不用于估计正式整轮速度。
