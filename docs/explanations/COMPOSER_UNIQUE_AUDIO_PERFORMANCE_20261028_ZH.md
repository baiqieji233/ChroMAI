# 缓存预热复审与重复音频计算优化（2026-10-28）

本文接续 `COMPOSER_TRAINING_PERFORMANCE_HANDOFF_20261028_ZH.md` 和 `COMPOSER_PERFORMANCE_FOLLOWUP_20261028_ZH.md`。前两轮优化全部保留。本轮没有使用子代理，没有启动或停止正式训练，也没有改写原检查点。

## 对本次交接的评价

最新一轮工作的方向正确，尤其解决了此前短程热缓存测试覆盖不到的问题：训练刚遇到新歌曲时，样本线程可能正在解压整份音频缓存，甚至临时运行 BeatThis。GPU 等待这类工作时，即使模型本身很快，也会长时间没有数据可算。

源码中已经落实、应继续保留的改动：

- 读取结构身份时优先取 `.npz` 的元数据成员，避免为了几项元数据解压整个特征矩阵。
- 先提取连续的时间轴，再创建音频上下文；经过发布校验的节点库使用 LensBank 快速构建路径。
- 正式训练循环开始前补齐缺失音频库和结构库，GPU 可用时利用它完成 BeatThis，之后释放该模型。
- 建立歌曲表时复用全曲间隔和标量查询，减少逐事件小数组分配。
- 保留 0.5ms Python 切换间隔，将预取暂停范围缩小到输入搬运和设备端音频准备，前向计算期间也允许准备下一批。

“所有根因都已修复、训练全程不会再停顿”的表述仍超出了证据。36 个 batch 能证明那次采样没有长等待，不能覆盖整套数据、所有恢复步骤、验证和保存检查点。预热后的计数器会清零，某次看到 `bank_builds=0` 也只代表随后观察窗口没有建库。本文不因此撤销这些有效改动，而是把验证范围写清。

本轮顺手补齐预热去重的一个边界：同一结构内容位于不同缓存目录时，各目录都需要准备；已存在的相同音频路径也只检查一次。正常训练、验证共用缓存目录的行为保持不变。

## 进一步减少重复计算

同一首歌的相邻样本会反复查询同一个音频时刻。例如三个样本都查看 20 秒附近的声音，旧路径会准备三份相同的局部音频片段，并让 AudioLens 卷积三次。

现在分三步执行：

1. CPU 组 batch 时，按音频库身份和精确的 float64 时间找出重复查询。没有把相近时刻四舍五入到一起，也没有跨歌曲合并。
2. GPU 对每个不同查询准备一次声音特征，并运行一次局部卷积，再通过索引映射回原来的样本和候选位置。
3. 反向传播把每次使用的梯度加回共享结果，所以重复出现三次的样本仍贡献三次相应梯度；监督样本、权重、条件和历史没有减少。

AudioLens 使用卷积、LayerNorm 和确定性激活，没有随机 dropout 或依赖其他样本的 BatchNorm，适合这种批内共享。条件预测仍在还原样本维度后执行。依赖“上一已提交事件时间”的区间音频仍单独计算，因为同一目标时刻在不同历史下可能代表不同区间。

共享结果只存在于当前一次前向，不缓存训练中的模型输出跨越优化器更新。原来的卷积分块上限继续约束每次处理行数，即使重复查询很少，也不会为了共享而一次放大到整首歌。

## 实现位置与使用方式

- `composer/data.py`：构造精确时间的去重表和还原索引，工作在 CPU 预取线程。
- `composer/device_audio.py`：共享音频统计与局部片段；保留逐样本区间输入。
- `composer/audio_lens.py`：支持紧凑片段输入，通过可微索引还原完整嵌入。
- `composer/grounded_model.py`、`train.py`：自动使用新路径，日志记录 `audio_lens_execution=batch_unique_exact_v1`。
- `tests/test_composer_unique_audio.py`：验证跨来源隔离、微小时间差、连续/交错样本、标签、输出、完整梯度、随机状态和分块上限。

本轮不增加 WebUI 参数，不修改学习率、batch size、梯度累积、精度或损失定义。新的 CUDA Composer 训练进程自动使用该路径；CPU、普通生成和未携带紧凑索引的调用继续使用原路径。模型参数名称、检查点结构和数据指纹保持不变。

## 验证结果与性能证据

所有实现完成后统一测试。CPU 全量测试：**3514 passed、39 skipped**；JavaScript：**162 项通过**。CUDA 音频、共享计算及局部卷积专项：**26 项通过**。

严格 FP32 测试关闭 TF32，验证输出、参数梯度和输入梯度在数值容差内一致，并检查随机状态不变。启用 TF32 时，不同卷积分组可产生约 `6e-5` 的输出舍入差异；不能把“数学上相同”写成 GPU 训练轨迹逐位相同。正式性能测量保留 BF16，不借降低精度提速。

端到端 ABBA 使用本轮开始时保存的源码作为基线，其中已经包含缓存预热、缩窄暂停区间、指标向量累加等此前全部修改。两侧读取同一份 v19 检查点和 AdamW 状态，使用相同样本顺序；测试进程中的更新不写回检查点。输入表预热后，12 批热身、72 批计时，batch size 96、梯度累积 6、样本准备线程 1、CPU 线程 2、预取 8、BF16。

实际读取 v19 的 step 500 检查点，使用其中完整 **25,492 类词表**、48 张真实谱和已有 AdamW 状态。8 次运行的样本顺序哈希一致，各自完成 12 批热身和 72 批计时；没有省掉更新健康检查，也没有在测量期间并行跑其他 GPU 测试。

| 指标 | 本轮继承的基线 | 批内共享后 |
|---|---:|---:|
| ABBA 吞吐中位数 | 440.70 samples/s | 458.51 samples/s |
| 反向 BAAB 吞吐中位数 | 467.61 samples/s | 472.71 samples/s |
| 合并 8 次运行的中位数 | 460.79 samples/s | 467.84 samples/s |
| 每批局部音频处理数量 | 10,752 | 平均 8,599 |

合并吞吐增加 **1.53%**；查询与局部卷积处理量减少 **20.02%**，峰值显存降低约 **90 MiB**。速度提升小于运行间波动，因此应称为小幅改善，不能承诺整轮稳定加速。模型的其他计算、Python 调度和组批成本仍在，减少一部分音频计算不等于训练总耗时同比减少。

同一真实 32 行 batch、同一 v19 权重、BF16、没有优化器更新的对照：

- 完整 loss：`8.398482323 → 8.398481369`，绝对差 `9.54e-7`。
- 选时 logits 最大差为 0；配置 logits 最大差约 `3.81e-6`。
- AudioLens 梯度余弦相似度 `0.999989`，相对 L2 差约 `0.48%`。严格 FP32 的逐项梯度对照也通过。

这些检查支持数学语义保持、混合精度仅有小量舍入差异。它们不保证长程训练逐位一致，也不是谱面质量验收。

两个版本的计时窗口中，最大数据等待均约 1ms，支持上一位关于消除样本供应长停顿的优化方向。但这里是预热后的窗口，未再次证明整个首轮训练或全部 465 个缓存的构建性能；不直接用本文吞吐除以上一份文档的 591 samples/s。

## 后续边界

- 新数据加入、缓存删除、后端身份变化仍可能要求预热；预热时间应独立显示，不能隐藏进训练吞吐。
- 本轮优化的收益取决于同批查询的精确重复率。重复率低时节省会较小，仍需观察 CPU 组批耗时和 GPU 显存。
- 本轮不评价谱面音乐质量。需要用固定音频、条件和种子做生成验收的质量问题，仍按之前的交接继续处理。

## 训练失败补充：编号中心 Touch（2026-10-28）

实际训练在 `head_pad_indices_for_policy` 遇到 `C1` 报 KeyError。原生判定器已经把 `C1`～`C8` 解释为中心 `C`，Composer 的物理键位表遗漏了这些别名。现已在合并与独立键位两套映射中统一指向中心，原谱文字、词表和模型分桶保持原样，避免修复建表错误时改变既有检查点结构。

仅运行专项回归：49 项通过，覆盖 C1～C8、TouchHold/烟花修饰、中心去重和真实数据集建表/取样。按用户要求未运行全量测试。
