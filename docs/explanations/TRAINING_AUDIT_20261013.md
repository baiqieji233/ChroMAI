# song_form_v1 训练修复与运行优化

日期：2026-10-13。分支：`codex/song-form-rebuild`。

本轮针对已中断的训练进行代码审查、修复和有限验证，没有恢复正式全量训练。检查范围包括训练循环、梯度累积、质量权重、规划曲线监督、数据读取、检查点恢复，以及主界面参数与任务日志。

## 1. 最重要的错误：梯度累积未真正累积

原配置训练循环在每个 batch 开头执行 `optimizer.zero_grad()`，但每隔 `grad_accumulation` 个 batch 才更新一次参数。设置累积 4 次时，前三个 batch 的梯度被后续清零丢弃，最后一个 batch 的梯度还被除以 4。这不是正常的大 batch 训练。

现在按以下顺序工作：

1. 累积每个样本的损失之和，连续反向传播。
2. 到达累积次数或本轮末尾时，除以本组实际样本数。
3. 进行梯度裁剪，再执行一次优化器更新。
4. 更新完成后清空梯度。

这也处理了最后一个 batch 不满、最后一组不足指定累积次数的情况。混合精度下先还原梯度缩放，再归一化和裁剪；梯度或范数溢出时不写入优化器，并在日志中报告跳过。

**原有训练进度不能据此等同为有效的梯度累积进度。已有权重仍可加载，但修复前后的 loss 和训练速度不宜当作完全相同实验比较。**

## 2. 监督与兼容性修复

- 规划器曲线的生成端使用 `sigmoid` 将输出转为 0～1，但旧训练直接用未变换输出拟合 0～1 标签。训练现在使用相同变换。
- 配置模型的曲线遮罩现在逐通道生效，被隐藏的通道先清零再投影，padding 也纳入遮罩。
- 曲线损失中的按帧遮罩与等价的按通道遮罩使用相同的有效元素分母，避免四通道情况下损失相差四倍。
- 局部质量标注参与规划器各监督头的权重；排除时间段的帧不再被当作“应当静音”的目标。
- 段落关联损失也乘以样本质量权重，和 token 损失使用可累积的逐样本定义。
- token accuracy 按实际有效 token 数汇总，避免短序列和长序列被不恰当地等权平均。
- 去除曲线目标构建失败时悄悄跳过的路径，问题会显式报错。
- 明确区分旧版与当前 song_form 输入合同。仅旧合同允许缺少后来新增的曲线/null 参数；当前合同缺参数会报告损坏，避免随机初始化后被误当作完整模型。

本轮不改变 checkpoint 的模型形状与词表，也不改变旧 event 模型的生成入口。新增 `training_semantics=song_form_training_v2` 记录训练数值语义；旧权重启动训练时会提示已启用上述修正。

局部排除的粒度仍有明确区别：配置任务遇到排除区会丢弃相交的整个计算片段，规划器能够只忽略指定的音频帧。保留此行为，避免通过删掉目标音符将排除区教成休止；本轮没有引入逐 token 的局部排除监督。

## 3. 性能改动

- 新增 `auto / bf16 / fp16 / fp32` 精度选项。auto 在当前 CUDA 设备上选择 BF16，CPU 使用 FP32；不支持 BF16 的 CUDA 设备选择 FP16。
- 训练输入的有限性和草稿任务的未来信息泄漏检查放在 CPU 上完成，模型仍检查形状，减少每层输入分支中的 GPU 到 CPU 标量同步。推理默认保留完整检查。
- 损失归约保持 FP32，降低低精度归约的数值风险。
- 数据加载支持 worker、pin memory 和预取；默认 worker=0，避免 Windows 下每个 worker 复制数据集导致内存骤增。每轮重新建立 worker，保证修订遮罩跟随当前 epoch 的种子。
- 音频与确定性草稿样本采用可设预算的 LRU 缓存。修订样本不进入该缓存；spawn worker 不复制父进程已经缓存的音频和样本内容。
- 有序拍位用二分查找提取局部历史；上下文编码到达 token 预算即停止；拍号查找不再逐帧反复线性扫描。
- 音频缓存命中、未命中、大小与淘汰次数写入日志。多 worker 时这些值只代表主进程，不冒充全 worker 汇总。

缓存是否有收益取决于数据量和复用率；全量随机取样不能假定和重复访问几个样本一样快。数据准备与 batch 加载是两个不同阶段，`数据准备进程` 和 `数据加载 worker` 分别控制它们。

## 4. 保存和继续训练

新增安全边界保存：默认每 500 次成功的参数更新保存 `form_last.pt`，全曲规划结束及每个 epoch 结束也保存。计数包含规划器和配置模型的更新。0 仅关闭间隔保存，不关闭阶段末尾保存。

检查点通过临时文件替换，保存模型、优化器、FP16 scaler、随机状态、已处理 batch 游标和本轮位置。保存只发生在累积组完成后；恢复时直接从未处理 batch 开始，不重新读取跳过的样本。

`epoch` 表示已完成轮数；`training_position` 表示未完成轮次中的位置。继续训练的“追加 N 轮”从该完成轮数算起，包含当前未完成的一轮。旧 checkpoint 没有中途游标时仍从下一轮开始。

继续训练继承原 batch、累积次数、种子、质量设置、各损失权重、数据范围、每轮步数限制及实际数值精度。学习率与优化器状态一同恢复。旧训练器没有精度字段时按 FP32 处理。需要调整学习策略或数据时使用微调，并选择新的输出目录。

中途恢复后的本轮平均损失仅统计恢复后处理的部分，显式标记 `partial_epoch_metrics=true`，不会伪装成完整一轮的均值。停止任务仍可能立即结束子进程，只能恢复到最后一次已落盘的位置。

本次被中断的正式任务为 `dc51acee4d7e`，输出目录 `checkpoints/Prism_Plus_v1`。检查时该目录只有 `dataset_audit.json`，没有权重文件；因此不能从该次中断点 resume。若使用该目录继续当前计划，需要重新从头训练，或另选真实存在的 checkpoint。

## 5. WebUI 与日志含义

主训练界面选择 `song_form_v1` 后，在“训练运行与缓存”中可以看到：

| 界面名称 | 默认值 | 用途 |
| --- | --- | --- |
| 数值精度 | 自动（优先 BF16） | 控制运算精度；继续训练继承 checkpoint |
| 数据加载 worker | 0 | 0 为主进程；可尝试 2，但应观察内存和数据等待时间 |
| 预取批次数 | 2 | 每个 worker 的预取 batch 数；worker=0 时不启用 |
| 进度日志间隔（秒） | 10 | 按时间输出训练统计 |
| 按优化器步保存 | 500 | 周期保存可续训 checkpoint |
| 音频缓存上限（GB） | 1 | 各进程音频特征缓存预算；0 关闭 |
| 样本缓存上限（MB） | 256 | 各进程确定性草稿样本缓存预算；0 关闭 |

原日志中的 `total=19086` 是配置训练的 **batch 总数**。原任务的 152684 个样本除以 batch 8 后向上取整即 19086；不是 19086 首歌。它们包含草稿和修订任务。累积 4 次时，完整配置阶段预计更新 4772 次参数，另有全曲规划阶段的更新。

`overall_fraction` 保留旧字段，但界面明确解释为“本轮任务数进度（规划谱面数＋配置 batch 数）”。它不是按耗时加权的整轮完成比例，也不能直接换算整轮剩余时间。新增的 ETA 仅估计当前阶段。

新增日志包括 `form_runtime`、`form_dataset`、详细 `form_progress`、`form_checkpoint`、`form_resume`、`form_warning` 和 `form_epoch`。可查看阶段、轮次、batch 数、参数更新数、累积进度、各项损失、token accuracy、样本/token 吞吐、阶段 ETA、学习率、精度、CUDA 显存、缓存、最近梯度范数和 scaler。

`timing` 是主机累计墙钟时间，包含相关等待和同步开销；它不是 CUDA kernel 精确计时。界面同步注明这一点。

后台 API 有修改，下一次正式训练前需要重启 WebUI，再刷新页面。页面操作入口保持原样。

## 6. 有限验证结果

- 针对训练运行、规划器、配置模型、数据、旧合同与 API 的定向回归：累计 63 项通过（62 项联合回归，随后补充并通过 1 项续训参数测试）。
- 前端参数与日志定向测试：10 项通过。
- 梯度累积与真实整批更新数值等价，包括不满 batch 和不满累积组。
- CPU 中途保存、恢复与未中断训练的模型及规划器参数逐项完全一致，开启了 dropout。
- FP16 scaler 的范数溢出测试确认跳过更新、不污染优化器，并能恢复下一次正常更新。
- Windows spawn 双 worker 的修订输入、历史、段落记忆及动作状态与主进程一致。
- 读取已有 `song_form_v1_controls_probe_epoch1/form_last.pt` 与本次微调检查点，推理加载通过，模型参数均为有限值。
- Edge/Playwright 访问 `127.0.0.1:7861`，确认新增设置及说明实际可见；未通过页面启动任务。仅发现既有 favicon 404。

真实数据验证使用 `E:\后训练（官谱）\training_manifest.json` 中 2 张可用谱面（138 个样本），256 维、4 层、8 头、token 上限 2048、记忆 512、batch 8、累积 4，各处理 16 个配置 batch：

| 配置 | 配置阶段耗时 | 峰值已分配 CUDA 显存 | 额外保存 |
| --- | --- | --- | --- |
| FP32 | 4.75 秒 | 1.959 GiB | 无阶段中途保存 |
| 自动 BF16 | 2.92 秒 | 1.265 GiB | 阶段内保存两次，计入耗时 |

两次均产生有限 loss 和可读取 checkpoint。另做一次 CUDA resume 和仅 2 个 batch 的 finetune，均正常结束。结果只验证功能和小样本性能，不代表全训练集提速比例，更不能证明生成谱面的音乐质量。

测试权重和日志放在 `.scratch/training_audit_*`，不覆盖正式模型、不提交测试权重。没有启动长期后台训练。
