# v40 全量训练提速与学习率调整

日期：2026-11-02。保留原检查点，先在运行期间读日志与源码，再在第7轮完整保存后暂停验证。没有重新fresh，也没有改变训练素材、模型规模、批大小、梯度累积或学习目标。

## 先更正此前的速度判断

“v40比v39慢19%”来自两次任务最初325批的比较。这个窗口当时确实较慢，但现在完整日志已经表明，它不能代表整轮：

| 原始任务 | 完整轮次训练吞吐 |
|---|---:|
| v39 第1轮 | 25.16短段/秒 |
| v40 第1轮 | 30.06短段/秒 |
| v40 第2～6轮 | 31.63、32.44、32.89、32.06、32.77短段/秒 |

这里统计训练循环，不把轮后验证和生成抽检混进来。最初窗口变慢的各项运行因素没有被旧日志分别计时，不能凭总耗时给它指定唯一原因。可以确认的是：**全量v40并没有持续比v39慢。** 本轮仍找到了可直接省去的无效计算。

当前数据等待通常不到总时间的1%；准备线程的累计工作时长大部分与GPU计算重叠，不能把它直接加到训练耗时上。增加准备线程或重建缓存没有依据。

## 确定的浪费在哪里

全量模型有250种拍内位置，因此每次选时要比较502个候选。旧实现对每个样本的128个历史位置和16个监督位置都执行候选音频读取、时间特征计算与概率归一化。但历史位置不参与下一拍的loss，它们只需要作为理解上下文。

批大小32、长度144时，一批会展开约231万个候选。此前8张谱的小实验只有48种拍内位置，候选表小得多；不能据此估计全量成本。

现在在CPU整理batch时，收集真正参与选时监督的NOTE位置，保持歌曲批次这一维不变，只为这些位置计算选时头。算完后映射回原输出布局。历史编码、全部候选时刻、休止监督、配置监督和损失权重都保留；没有通过少学样本换取速度。

这条优化用于训练。评估、生成以及仍使用旧独立转折覆盖的路径保留完整查询。兼容路径的实际查询数量会记录在日志，不能只看开关名称推断是否生效。

## 用真正的全量训练验证

两组都从同一个完整点开始：第7轮、优化器第10000步、已消费1976批。模型、Adam、Python/NumPy/Torch/CUDA随机状态、数据游标相同。素材仍是完整训练清单：2675张可用谱面、96,065个短段；没有设置谱面数量限制。

每组真实执行100次优化器更新，即200批、6400个短段，包含数据准备、历史增强、恢复采样、反向传播、梯度裁剪和Adam更新。两组都按本次要求用固定学习率0.0005，避免把学习率变化混入速度比较。

排除起步队列预热后，比较相同的第2020～2176批区间，共4992个短段：

| 指标 | 完整位置计算 | 仅有监督位置计算 |
|---|---:|---:|
| 实际吞吐 | 31.33短段/秒 | 35.74短段/秒 |
| 匹配区间耗时 | 159.35秒 | 139.69秒 |
| 其中计算计时 | 155.47秒 | 136.10秒 |
| 等待预取数据 | 0.007秒 | 0.007秒 |
| 全部200批的选时查询数 | 921,600 | 102,400 |
| 峰值GPU分配 | 5.675GiB | 4.468GiB |
| 非有限更新跳过 | 0 | 0 |

**匹配区间提速约14.1%，峰值分配减少约21.3%。** 如果连起步预热一起算，完整200批吞吐为32.56→35.97短段/秒，约提升10.5%。两个口径都保留，不使用准备缓存冷热造成的启动时间差作为收益。

CPU对照确认有监督位置的logits、loss及全部参数梯度一致到浮点误差范围。GPU BF16下不能保证逐位相同：100次更新后的区间平均总loss为4.9387与4.9594，差约0.42%，没有出现非有限值跳过。缩小矩阵及归约尺寸可能改变浮点舍入，恢复采样也可能随之分岔；本轮没有把这当作音乐质量改善实验。

原始命令、日志、逐区间数据在 `.scratch/v40_performance_20261102/full_dense/` 和 `full_supervised/`。这次结果来自全量训练路径，不是单个小batch的计时。

## 固定0.0005如何生效

原v40的第7轮完整点为10514步，另存于 `.scratch/v40_performance_20261102/pre_lr_change/`，与暂停后的原文件哈希一致。对照实验使用更早的独立副本，实验权重没有覆盖正式模型。

正式任务从10514步恢复到第8轮，继续原50轮总目标。保留Adam状态、随机数、恢复episode和采样进度。新的学习率计划为固定0.0005、预热0步、最低比例1，不再继续余弦下降。

增加显式 `--reset-learning-rate`，普通resume仍沿用原计划。改计划时会记录旧/新计划和修改步数，并在下一次参数更新之前保存，使随后正常续训也能继承新计划，而不会悄悄恢复旧余弦计划。

主界面对应设置：

- 训练模式：继续训练。
- 勾选“调整本次续训学习率”。
- 学习率：0.0005；学习率变化方式：恒定；预热步数：0。
- 选时计算：仅有监督位置。

新控件默认不勾选；未勾选时仍锁定并继承原设置。服务缺少调整能力时，界面会提示重载，避免新页面把参数交给旧服务后被静默忽略。通用fresh默认没有一起提高，本次调整只针对用户指定的v40任务。

正式恢复任务ID：`545606ce4605`。目录仍为 `checkpoints/prism_composer_v40/`。

实际日志确认第8轮已完成更新，学习率为0.0005，未发生非有限跳过；前50批选时查询数25,600/230,400，新路径已经生效。机器证据见[完整记录](evidence/COMPOSER_V40_TRAINING_PERFORMANCE_20261102.json)。

## 验证与剩余工作

- 选时稠密/稀疏对照包含混合短历史、非整数拍位、计划区间信号、空NOTE batch，以及loss/梯度比较。
- 学习率恢复测试覆盖Adam步数与数据游标保留、显式计划变更、保存后尚未更新就中断，再正常恢复。
- 全量Python运行4311通过、13跳过；153项受到本轮沙箱的本机套接字或临时目录限制，解除相应运行限制后152项通过，最后1项在符合“项目外临时目录”前提下通过。没有据此修改产品的下载路径边界。
- 学习率持久化补充测试20项通过；全部JavaScript测试197项通过。
- 另发现候选短句库重复打包和历史原子嵌入大中间张量的优化可能性。后者只有CPU探针，尚无GPU全量证据，因此没有混入这次改动或速度结论。

本轮验证的是执行效率、数值行为及指定学习率的实际生效；0.0005是否提高最终谱面质量，仍应看后续验证与固定歌曲产出。
