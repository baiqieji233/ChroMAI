# v43 训练效率与显存调整说明（2026-11-02）

这轮只调整计算与数据准备的执行方式，保留 v43 的模型、学习目标和已有权重。用户要求的正式训练配置为：**批大小 16、梯度累积 4、固定学习率 0.0005，总目标 50 轮**。

**长程观察后的修正：这台 32GB 主内存机器最终关闭独立数据进程（设为 0）。** 初期短窗口提速不代表整机能长期容纳双份语料对象。实际运行后可用内存降至约 0.7GB，主进程驻留约 10.4GB、准备进程约 6.9GB，出现大量硬缺页读取；因此从完整的 step 1500 点改回单进程准备，保留 NumPy 标签、打包合并和指标累计等优化。不要根据下文的短程 +26% 数字，重新在这台机器上默认打开独立进程。

## 为什么显存占了很多，GPU 却经常不忙

显存里放着模型、优化器和中间结果，并不意味着 GPU 一直在计算。本次发现了两个主要等待来源：

1. **准备数据和提交 GPU 运算在同一个 Python 进程里争用执行机会。** 原先的后台线程会反复处理短句、几何标签和数据增强，拖慢主线程提交下一批运算。即使日志里的 `compute_sec` 很高，也可能包含这些等待，不能全部理解为 GPU 运算时间。
2. **细节预测按配置种类逐组循环。** 很多小矩阵运算依次提交，GPU 忙一下就要等待下一条指令。批大小调小可以省显存，但不会自动解决这种等待。

还有一个容易混淆的阶段：每轮末尾会生成固定歌曲作抽检，逐事件生成的并行度较低。它的 GPU 利用率不能当成训练阶段的利用率。本轮取消最后一个任务时，第 2 轮训练和检查点保存已经完成，正在做生成抽检。

## 具体修改

| 修改 | 目的及边界 |
|---|---|
| 用一个独立、常驻的数据准备进程 | 避开 Python 线程争用；跨轮复用，减少重复启动。Windows 首次启动仍有额外时间。 |
| 短句历史统一在批次拼接时打包 | 同一历史不再每行、每个查询都重复打包；独立读取数据集的接口保持原行为。 |
| 关系标签改用 NumPy 一次构造 | 避免大量逐元素 Torch 调用；标签值和含义不变，重复键位关系用有界缓存。 |
| 恢复样本索引复用准备阶段已有结果 | 避免训练中第一次恢复时，再扫描一次整个训练集。 |
| 诊断指标合并累计 | 避免每个标量都发起一次 GPU 运算；保留异常检测和梯度检查。 |
| 释放续训后多余的 CPU 权重副本 | 模型和优化器已复制到设备后，旧 checkpoint 字典仍保留约 0.6GB 的 CPU 权重；现在只保留后续所需元数据。 |
| 提供细节预测共享循环合并计算实验选项 | 同一套权重按槽位批量执行，保留每类配置自己的候选集合和时值计算；没有增加模型参数。全流程未证实更快，因此正式训练仍用逐类计算。 |
| 显式支持保持有效批量的重分批续训 | 从 32×2 改成 16×4，按已消耗样本数映射进度，保留原排序方式。 |

**没有**缩短历史、降低模型规模、减少监督目标或关闭恢复学习来换速度。也没有把 CPU 准备移到 GPU 上争抢训练显存。

## 已验证的收益与限制

以下结果要区分测试范围，不能相互冒充：

- 完整真实训练循环，同一父检查点和样本顺序，比较第 40—80 批：原线程方案约 **882 个有效目标/秒**，独立进程方案约 **1114 个/秒**，提高约 **26%**。首次启动的约 37 秒不在这个稳定窗口内；若只运行极短任务，启动成本会抵消收益。
- 关系标签函数在真实 4 谱数据上的 CPU 对照约 **15.2 倍**；这是一个函数的改善，不是整轮训练 15 倍。
- 同一 v43 模型、真实 B16 数据、BF16 的小批次细节计算对照：合并后 **1534.5→1669.2 个目标/秒（约 +8.8%）**，峰值显存约增加 **6.4 MiB**。但完整循环同样第 40—100 批，逐类为 **1314.8**，合并为 **987.4 个目标/秒**，未复现局部收益，**不启用为默认值**。合并会将短配置补齐至本批最长槽数，复杂配置可能放大无效计算；本次数据进程也同步变慢，另有运行环境干扰，不能把差距全部归因于合并算法。GPU 高频采样与合并对照同时进行，后续复测应排除此因素。
- BF16 合并计算的 loss 差约 `0.000076`，完整梯度相对 L2 差约 `0.368%`；CPU 严格数值和梯度对照通过。改变矩阵批量会改变浮点舍入，不能称为逐位完全相同。
- 改成 16×4 后，已观察到模型分配的峰值显存约 **3.49 GiB**；GPU 总占用还包含桌面、驱动和框架缓存，不能和这个数直接比较。较长、较复杂的批次仍可能用更多显存。
- 已采样的训练 GPU 利用率仍有明显波动，不能声称已经持续满载。后续应同时看有效目标吞吐、数据等待、训练阶段和显存，而不是只看瞬时百分比。
- 长程数据进程方案下，系统提交内存约 **57.1GB**、可用物理内存约 **674MiB**；`PagesInputPersec` 约 **12908**，E 盘读约 **11.5MB/s**。硬缺页同时包含音频映射文件和分页文件读取，不能把这些读盘全称为交换内存。停止训练和准备进程后可用内存回升约 **16GB**，证实当前运行占用已超出整机的舒适余量。
- 关闭独立进程并实际恢复训练后，观察到可用内存约 **5—6.5GB**；后一次硬缺页输入采样为 **62 页/秒**。第 3 轮相同第 1400—1440 批，独立进程为 **830.5**、共享线程为 **597.0 个有效目标/秒**。这是明确的内存与速度取舍，不能称为最终整体提速成功；线程争用仍需通过轻量语料共享解决。两个窗口的梯度范数约 **3.118/3.116**，均无跳过更新。两次执行的累计 loss 起算点不同，不直接比较累计均值。

## 维护人员接手时看什么

先确认 `composer_runtime` 中批大小、梯度累积、准备进程和细节计算方式确实生效。比较日志中两个普通训练进度点的 `effective_target_budget` 差除以 `elapsed_sec` 差；同时记录 `data_sec`、`compute_sec`、`prefetch.consumer_wait_sec` 和 GPU/主机内存。恢复、保存、验证和生成抽检需要单独标明，不要混成“每批运算时间”。

现有回归覆盖短句打包一致性、恢复索引一致性、跨进程序列化、重分批游标、指标累计、标签一致性、细节 loss/梯度和 UI 参数透传。这轮性能修改不构成谱面音乐质量提升的证据。

本轮较早的相关 Python 回归为 **950 项通过**；最后一批细节计算和默认值调整完成后，又执行 **62 项针对性 Python 测试、207 项界面测试，全部通过**。另外从同一真实父检查点执行了两条各 120 批的完整训练循环，两个实验均无跳过更新，均没有覆盖正式检查点。
