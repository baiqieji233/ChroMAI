# Composer 数据准备慢：原因与修复

本轮定位到准备缓存的无谓失效，并已修复。使用原 v22 训练清单实测，全量652张谱首次复用及补齐缓存约26.8秒，再次启动约21.1秒。原训练日志在约15分钟时只完成了283张谱，仍未进入训练。

## 为什么会重复准备

最新任务直接读取官谱数据集，而磁盘已有的准备结果很多来自此前的多数据集合并清单。两种入口给同一张谱写了不同的标注说明，例如：

- `song_id` 从原编号变成“数据集::编号”；
- `chart_id` 因来源命名空间变化而改变；
- 数据集名称从字符串变成包含ID的对象；
- 增加了来源清单、备注等字段。

原缓存把整份标注都计入身份。即使谱面、音频、训练权重和区间设置完全相同，仅这些说明改变，也会重新解析谱面、分析分段与动机、构建持续状态和标签。

实际对比找到同一张谱的多份缓存：音频/谱面摘要、结构参数、预处理版本、权重1.4和空区间相同，只有数据集命名空间与来源描述不同。最新日志共283张谱，只有33次命中、250次重建；期间没有新建有理音频特征缓存，源文件摘要也没有大量重读。因此这次主要慢在准备结果被重复重建。

## 修复做了什么

准备缓存的身份现在只保留标注中参与训练准备的值：标签、整体权重、区间起止和区间权重。谱面、音频、结构文件、预处理规则等原有身份仍严格检查。

旧缓存会通过现有发现机制查找、校验并关联到当前键，不需要删除或重建整套缓存。读取后重新绑定当前标注、谱面来源和音频路径，防止输出里留下旧的合并清单编号。

源标注仍先按当前路径、难度和内容摘要匹配；数组校验仍然保留。不同权重、不同排除区间、不同预处理结果不会被当作同一份准备数据。训练的事件、标签、采样顺序、模型和检查点格式都没有因此改变。

## 实测和正确性检查

| 验证范围 | 结果 |
|---|---|
| 同一批24首歌、28张谱；旧文件发现范围相同，写入彼此隔离的测试缓存 | 修复前20.52秒、28张全部重建；修复后10.00秒、25张复用，仅3张仍需重建 |
| 上述28张谱逐项比较 | 事件、条件、权重、持续状态、曲线、动机描述、当前标注与样本索引完全一致 |
| 实际全量训练清单：624首歌、652张谱 | 26.77秒，642张复用、10张重建；生成348,591个训练样本 |
| 再次准备同一全量清单 | 21.09秒，652张全部命中、0重建；数据指纹完全一致 |
| 相关回归测试 | 89项通过，含旧缓存迁移、当前来源重绑定、权重/区间变化失效及损坏缓存处理 |

全量第一次运行中，基础谱面准备约14.3秒，随后Composer建立事件视图、候选索引和指纹，总计约26.8秒。再次运行无需扫描旧缓存迁移。测试使用准备线程4、CPU算子线程2；没有通过缩短历史、减少候选或删标签提速。

21.1秒是本清单的**数据集准备**耗时，不包括训练前其他可能的音频/结构预热、模型初始化、验证集准备或每轮训练。全量复测结束时系统可用物理内存约13.2GiB；未将这个数值视为峰值内存保证。

证据汇总：`docs/evidence/COMPOSER_PREPARATION_CACHE_FIX_20261029.json`。测量脚本、详细日志位于 `.scratch/composer_prepare_20261029/`。

## 接下来如何使用

保留当前缓存目录，下一次从主界面启动Composer训练会自动使用修复。现有缓存关联已补齐；不需要修改batch、采样或模型参数来解决这次问题。修复位于新训练进程读取的准备模块，本轮无需为此重启WebUI。

原检查点没有被修改，本轮没有启动正式长训。若换成真正的新谱面/新音频，或改变权重、区间与预处理设置，首次准备仍会计算对应内容。

维护提示：未来若准备逻辑新增了其他标注输入，需要同步把它加入 `_annotation_inputs`；该函数应只排除展示与来源描述，不能遗漏实际参与训练计算的字段。
