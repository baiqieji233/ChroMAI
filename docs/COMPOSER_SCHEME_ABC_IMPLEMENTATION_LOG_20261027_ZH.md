## 2. 方案 A：读取未来候选音频

配置分支新增`FutureAudioHorizon`，直接读取当前候选之后0到8拍内的有效候选，附带相对拍距和秒距编码。输出投影零初始化，单独启用A时保留原先第0步输出。

这里的“8拍”是新增模块的直接读取范围。上游原有音频编码器已经混合所有候选的信息，因此不能说整个模型严格看不到过去或8拍外的音频。读取对象是候选网格，也不是连续的原始音频帧。

已修复注意力头数选择：不再固定取4头，而选择能整除宽度的小头数，避免合法的30维/6头等模型无法启动。没有为兑现错误文案而切断原有全局音频上下文。

## 3. 方案 B：独立宏观分类与桶内细化

先把音符按类型及真实起始位置集合分组，由独立分类头决定每组总概率，再在组内选择具体音符。Touch按具体位置区分，A1与A2不会因为同属A圈就混为一组；组数由实际词表决定，不固定为46。

复核前的实现仍用旧全词表分数合计来决定组总量，只是在旧头上追加了修饰。现在旧分数只参与组内细节；Tap目标不再通过这条输出路径驱动其他组的细化分数。最终归一化结果保留float32，避免BF16舍入破坏组总量。

实际生成及配置恢复也已接入同一分组方式：先确定合法组的概率，再在各组内部应用动作温度和尾部截断。动作温度为0时，先选最可能的组，再选该组内最可能的音符。合法过滤、Touch保护、类型控制仍可有意改变概率，不能把这一有限守恒性质说成“任何条件下绝不争抢”。

保留了原有同拍和跨拍键位关系。它们在新头之后作为位置调整使用，避免被组内归一化抵消。训练批量计算与生成逐槽计算使用相同顺序。

这仍需要计算合法词表中的细化分数，不是把所有计算从约1.8万类缩成几十类，也不是逐个离散属性采样的完整自回归模型。共享主干和参数仍可能产生训练干扰；多押意图和音乐质量也没有数学保证。

**迁移注意：A与B不同。** A新增残差可以从零开始不改旧输出；B改为独立宏观分类后，需要学习新的分类头。不能同时声称任意旧平面头迁移后输出逐位不变。旧v16使用`flat_v1`时保持旧路径，尝试B应使用新的训练阶段和目录。

## 4. 方案 C：已接通条件遮挡，性能方案仍待验证

“条件遮挡概率（保留等级）”现已接通主界面、API、CLI、模型配置及运行日志。默认0；训练时同一次遮挡用于占用、规划、负荷、历史负荷和直接条件投影，生成时不遮挡。显式外部曲线覆盖仍保留用户输入的含义。续训继承检查点，微调可显式调整。

前端新增了后端能力检查，防止新页面连接旧进程时，启用或关闭A/B的选择被静默忽略。刷新页面不会更新旧Python服务；应在没有活动任务时更新后端。

性能方面没有实现同曲微块共享编码，没有改变样本线程默认，也没有确认“多开线程一定快”“75分钟降至15分钟”。这些仍是待测方案，不能写成已完成结果。
