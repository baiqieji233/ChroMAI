# Beat This信号为什么很弱，以及本轮怎样修复

日期：2026-10-27。对应[独立审查原稿](COMPOSER_BEAT_THIS_AUDIT_20261027_ZH.md)。

**核心问题已复现并完成代码修复。** Beat This产生的局部节拍和强拍信号，在旧输入中没有直接交给Composer；经过多次归一化与候选平均后，相位提示也变得很弱。本轮增加了增强版结构输入。原v15使用的旧版仍按原含义读取，新版本需要新的训练阶段。

## 1. 复核确认了什么

对原问题歌曲、190 BPM、首拍0、全曲1600个查询点，用已有分析缓存重新测量：

| 输入 | 旧版RMS | 增强版RMS |
| --- | --- | --- |
| 固定4/8/16拍周期坐标 | 约0.707 | 保持相同 |
| 第一候选的四个相位通道 | 0.00252–0.00342 | 0.145–0.149 |
| 直接局部节拍概率 | 没有此输入 | 约0.453 |
| 直接局部强拍概率 | 没有此输入 | 约0.260 |

RMS是这里用来比较输入典型幅度的数值。第一候选相位的幅度约提高43–59倍；这不是说模型能力提高相同倍数。

审查中的原始神经概率也复算一致：按谱面坐标每四拍分组，某组的强拍预测平均约0.58，其余约0.02–0.04，说明原始信号确实有明显区别。当前源码实际有**79个**候选周期，原文写成88个需要更正。

还有两点要分清：谱面坐标的`beat % 4 == 0`未经人工标注，不自动等于歌曲真实小节起点；不同歌曲、不同种子的重复率，也不能证明某个结构分支已经带来质量提升。原谱本身可能需要重复、和弦和多Touch，比例更低不自动更好。

## 2. 最终改动

**直接给模型看局部预测。** 在原48维布局之外，增加节拍概率、强拍概率和“神经分析是否可用”三个通道，共51维。内置后端没有神经结果时，三个通道为0；不会把“缺少分析器”与“预测概率很低”混为一谈。

**先选出不同的代表周期，再分配权重。** 去掉32拍分析窗口内难以区分的相邻周期别名，只对最多4个代表候选和一个“未知”项归一化。加入许多近似周期，不再把同一个有效提示越分越薄。“未知”仍保留，权重不是人工确认的拍号概率。

**相位形状只做一次置信控制。** 保留一阶、二阶相位的方向和相对形状，再由候选权重控制作用幅度，避免把已经很小的绝对系数再乘一遍衰减。

**不让微小残差获得完整选票。** Beat This的beat列只辅助估计脉冲间隔，不再混入小节重音系数。其余通道先检查残差是否足够大，再按相对对比度和该周期的一致性混合。这样也避免了原生声学单位较大、神经概率单位较小时，前者仅因数值量纲大就压过后者。

一个中间方案曾直接按绝对残差能量混合，复算时把原片段的首候选带到了7.5拍；该方案已弃用，证据留在本地。最终版在254–258拍片段仍优先选出4拍、8拍候选，且第一候选相位接近原始强拍方向。

没有把所有信号统一放大到0.707，也没有手工规定所有歌必须是四拍。弱证据和静音仍应弱或为空。

## 3. 新旧版本怎样区分

| 项目 | 旧版 / 当前v15 | 增强版 |
| --- | --- | --- |
| 结构策略 | `metrical_context_v1` | `metrical_context_v2` |
| 输入维度 | 48 | 51 |
| 特征版本 | `composer_structure_native_v4` | `composer_structure_balanced_v6` |
| 结构缓存目录 | `composer_structure_v4` | `composer_structure_v6` |
| 原始Beat This预测缓存 | 原有缓存 | 直接复用相同分析器身份的原始缓存 |

没有覆盖v15权重，也没有改变其已有输入尺度。本轮对照的1600行旧特征逐位一致；保留的第4000步推理点哈希不变，并用它实际完成了短生成。

新的完整结构库需要单独准备。此前“1787份缓存已完成”指旧版，不能当作增强版也已全量准备；不过已有的原始神经预测可以复用，不需要因此重新跑全曲神经分析。

从v15微调到增强版时，音频、历史等兼容权重可转移，三层结构投影因维度和含义改变而从零学习。**这不保证切换后立刻保持原来的生成效果。** 不能手改检查点策略字符串来绕过输入检查。

## 4. 主界面应该怎样选择

- 新训练的“音乐结构条件 → 自动”现使用**节拍与小节结构（增强信号）**，也可明确选择该选项。
- “结构分析后端”选**Beat This**，或者自动选择本机可用后端。只有Beat This后端才有新增的局部神经概率；内置分析仍可运行。
- “结构条件遮挡概率”保留0.15。本轮没有改变学习率、各项损失权重、Touch配额或重复惩罚。
- “checkpoint 输出目录”使用新目录；默认按钮改为`checkpoints/prism_composer_v16_signal`。这只是目录默认值，本轮没有启动v16全量训练。
- 已有v15续训仍继承旧策略。要尝试增强版，应新建fresh或finetune阶段；保留v15作对照。

当前运行中的7860后端仍可能是旧代码。新版页面会检查后端能力，防止看似选了增强版，实际仍按旧版训练；有活动训练时保留其监控服务，在更新后的服务里准备新阶段。

需要提前准备时，命令示例：

```powershell
& .scratch/python312_runtime/Scripts/python.exe tools/prepare_composer_structure.py --manifest "E:\全量官谱\training_manifest.json" --cache-dir cache/chart_composer_v1 --backend beat_this --structure-policy metrical_context_v2 --device cpu --workers 1
```

不需要为这次变化重新下载Beat This权重。GPU预处理与正式训练应错开，避免互相争用。

## 5. 已验证与尚未验证

完成了模型、采样、数据、检查点和主界面的接线。真实数据小模型在CPU上完成2次更新及配置恢复，新增神经列的结构权重实际发生更新。新旧模型都各完成8事件短生成，仅用于确认路径可运行，不能作为质量对比。

单曲热缓存查询96个候选，本次中位耗时约从0.229毫秒变为0.455毫秒。开销增加约0.23毫秒；复杂度仍随候选数线性增长，没有每批重新跑分析器。该测试与正式训练并行，不能外推整轮吞吐。

最终回归、浏览器检查与原始数值见[机器可读证据](evidence/COMPOSER_BEAT_THIS_FIX_20261027.json)。本地脚本与日志在`.scratch/composer_beat_this_review_20261027/`。

剩余的关键验收是：同数据、同歌曲、同条件和双种子，在有足够更新的新模型上比较配置、节奏、Touch和冲突，再试听试玩。此次证明的是有用信号没有再被输入接口过度削弱，尚没有证明长期音乐质量改善或所有loss下降缓慢都由此造成。
