# v27 训练效率与学习目标复查

日期：2026-10-30。依据当前源码、实际训练日志、同输入 CPU/GPU 对照；本轮由主代理与 Astra、Sol、Terra 三个子代理分别核查。未重新训练模型，也未覆盖原检查点。

## 这次查到什么

GPU 利用率偏低确实存在，抽样为 10%～41%。但主机日志里的 `compute_sec` 包含提交 CUDA 工作和等待，不能直接当成 GPU 内核忙碌时间。原任务没有启用 CUDA 分段记录。

第 2 轮 batch 3725→3925 的匹配窗口共 12800 样本，用时 82.422 秒，155.30 样本/秒。同期 CPU 准备用时 79.486 秒，几乎贴着训练速度上限；消费者直接等待预取 11.417 秒，占窗口约 13.9%。传输阶段主机耗时 8.460 秒，计算阶段主机耗时 62.288 秒；恢复训练两次共 3.738 秒，约占 4.5%。这些计时部分重叠，不能相加解释整段时间。

因此优先处理重复准备工作。不能仅凭 GPU 利用率，直接增加线程、加大 batch 或删除恢复训练。

## 已经实现的三处修改

### 1. 合并同歌重复的未来音频查询

CPU profile 显示，128 样本中 `quality_context_inputs` 约用 0.213 秒，固定未来探针约用 0.169 秒；大量时间在反复查相同音频位置、维护缓存和拼数组。新增 survival 固定格约用 0.035 秒，并不是这次最大的准备热点。

现在同歌批次先找出不同的候选拍位与精确音频时间，只查询一次，再还原每个样本的原位置。没有减少未来 8 拍的信息、改变候选或四舍五入时间。128 个样本的所有张量与原实现逐项相等。

按生产预取的同源分组、每 8 样本一块模拟，3 轮配对中位数从 0.293981 秒降至 0.264116 秒，CPU 准备下降 **10.16%**。完整 B64 查询中位数下降约 12.37%。这是 4 首歌的小型受控测量，不是全语料速度承诺。

改动：`src/maichart/composer/data.py` 的 `__getitems__` 与 `_item`。

### 2. 不再重复搬运整曲规划音频

song-paired 批次已经有按音频来源去重的 `song_audio/song_mask/song_clock`，却仍构造和传输每条样本的 `planner_audio/planner_mask/quality_plan_clock`。模型实际使用的是前一套共享编码。

现在多行 song-paired 批次只提供唯一音频库；每条样本的监督标签、条件和历史保持原样。旧质量策略和单条恢复样本仍走原路径。没有增加开关或改变参数集合。

CPU 测试中前向、全部有效参数梯度和 RNG 状态逐位一致。真实 B64 CUDA/BF16 对照，待传输张量从 112046792 字节降至 108293192 字节，约少 3.8MB。前向最大差异约 0.000008；梯度相对 L2 差异约 0.10%，与未修改基线重复运行的 0.10% 波动相当，不能写成 GPU 逐位一致。

ABBA 短测整步中位数 187.11→175.29ms，约减少 6.3%。它排除了 CPU 准备、优化器、恢复采样和实际设备音频 materializer；轮数少，也存在 GPU 调度波动，不能把 6.3% 与上面的 10.16% 简单相加。

改动：`data.py` 的 `collate_composer`、`train.py` 的 `_forward_batch`。

### 3. 修复休止损失的高置信错误梯度

原实现先 sigmoid，再对概率算 BCE。FP32 下原始分数为 17 时，sigmoid 会舍入到 1；真实标签为 0 时，loss 为 100，反传梯度却为 0。模型在这种情况下很难纠正自己的错误。

现在保留原始休止分数，使用数值稳定的 BCEWithLogits。原来的 sigmoid 预测仍供条件和事件率使用，参数、优化器、输入合同、监督权重都不变。

该缺陷已复现，但本次真实检查点的 64 行探针中，6368 个有效规划位置的原始分数范围为 -4.94～3.03，没有达到 17。**不能把它说成当前高 loss 的主要根因，也不能据此宣称生成质量已经提高。**

改动：`planning.py`、`song_context.py`、`grounded_model.py`、`train.py` 的休止监督。

## 当前 loss 到底是什么

暂停前累计总 loss 约 7.43，主要加权贡献如下：

| 项目 | 贡献约值 |
| --- | ---: |
| 整个事件的配置联合损失 | 5.05 |
| 下一事件选时 | 1.03 |
| 音频选时与配置辅助 | 0.59 |
| 事件率 Poisson 监督 | 0.54 |
| 短段配置与间隔 | 0.10 |
| 其他负荷、占用、规划、结束等 | 剩余部分 |

配置项现在是同拍多个音符及 STOP 的联合损失，与旧版本按槽平均的数字不同。恢复后的一个运行窗口中，配置联合损失约 4.86，旧标尺 `action_legacy_ce` 约 2.79；总 loss 约 7.19。单看“7 比以前 4 高”不能判断训练比以前差。但宏观配置选择是否学好，仍需要看首槽 CE、类型/键位分布和闭环生成，不能用换标尺解释掉用户观察到的问题。

已经核查：固定格积分总概率约 1，区间内重新分配不改变区间概率和等待概率；Poisson 公式、曝光归一化正确；旧 workload 回归已剔除同一个事件率通道，没有重复施加旧回归损失；真实前缀计数没有读取未来标签。

还额外检查了“音频辅助是否与选时主目标拉扯”。同一个真实 64 行探针、关闭 dropout 后，精细选时头梯度夹角余弦约 0.998，粗选时头约 0.650，均为同向。辅助项加权梯度范数分别约为主项的 27%、25%。这个探针不支持直接删除音频辅助监督；它也不能代表所有歌曲、共享主干或所有训练阶段。

## 在此基础上，还值得做的方案

以下是进一步实验方案，不是已上线功能，也没有先行改变当前训练目标。

1. **训练时只算目标宏观组里的细节。** 当前 compact 头仍展开完整音符词表。常规 Tap 的目标组往往只有极少数变体，却仍计算大量 Slide 细节。按“宏观分类 + 目标组内部分类”直接求同一个联合损失，有机会减少词表投影和归一化，保持概率目标不变。先证明前向损失、梯度和 STOP 处理等价，再测真实 B64 的完整步骤；不能因省了 FLOPs 就假定墙钟一定变快。生成端仍需要完整合法分布。

2. **让休止监督能看见短空隙。** 当前 planner 的 rest 标签是“整个四拍计算段没有起音”。段内存在半拍、一拍休止时，这个标签仍为非休止；段中心之间插值又会平滑边界。优先利用已有精确起音计数和固定格，评估短休止边界的事件率误差，并尝试以已有局部计数预测短窗空白概率，不再新增一个大编码器。需同时校准事件率与休止门，避免两者重复压低同一段的出音概率；固定格损失并不天然保证每个边界都学对。

3. **用小而一致的谱集做学习能力对照。** 从现有数据选约 50～100 张风格、等级较一致且覆盖常规单押、双押、短 Hold/Slide 的谱，另留固定开发曲目；比较相同样本数和时间预算下的首槽配置学习、选时、自由生成。少量优质数据确实值得认真尝试。这能区分“训练目标本身很难学”和“全语料差异太大、早期更新被分散”，但不能仅因为训练集 loss 更低就切换正式数据。

4. **让相同的恢复预算优先处理真实失败段。** 当前恢复计算约占 4.5%，不宜直接删掉。可以保持调用频率和样本数，优先取静段误出音、双押成员快速重复、段落衔接失败附近的自产前缀，检查模型能否重新接回参考谱的合理后续。主要风险是参考谱不是唯一合理编排，以及自产持续动作可能使参考后续不可达；需要保留现有可达性检查和失败统计。

5. **用正确的权重评估 planner。** 目前全曲计划随每个事件样本反复监督，事件多的谱影响更大。先增加按曲或按时间均匀的验证汇总，再对照是否需要把全曲计划监督集中到较少、均匀抽取的样本。这可能同时减计算和减密集谱偏置，但直接降低重复次数会改变实际损失权重，必须保持可比。

优先级是先做第 1 项的严格等价计算优化，同时用第 3 项建立较快的质量实验基线；第 2、4 项针对当前休止与衔接质量，单独做固定音频对照。加大 batch、删历史、放宽梯度裁剪、提高所有辅助权重均不是已证实的解决办法。当前梯度裁剪前范数约 5～6，但 AdamW 下不能把统一裁剪简单等同于学习率缩小五六倍。

## 测试、训练保存与恢复

所有修改合并后，最终相关 CPU 回归 **56 项通过**；此前各子代理的重叠测试不能相加当成独立总数。真实完整模型 GPU 前向、反向及数值对照已完成。

为必要 GPU 测试，完整保存点 2500 已复制到 `checkpoints/prism_composer_v27/snapshots/before_efficiency_fix_20261030/composer_last.pt`。旧任务最后报告 2505，取消时尚未保存的尾部更新会从 2500 后重放，不能声称零训练进度损失。

恢复任务：`5fbb4701c0a4`，仍在 7864 主界面和 v27 目录。保留完整模型、优化器、RNG 与样本游标，从第 2 轮继续，总目标仍为第 20 轮。API 的 epochs 表示恢复起点起算的轮数，因此请求为 19；实际 `end_epoch=20` 已核实。action_slots 按检查点实际自动扩展值 33 继承，不能用最初界面请求的 8 去续训。

运行约 400 批后观测约 219 样本/秒，随后约 213；旧窗口约 155～163。歌曲窗口、缓存与运行时环境不同，这不是严格端到端 A/B。GPU 仍有 6%～55% 的波动，尚未消除所有等待。恢复任务前 64 批开启了 CUDA 分段计时，后续自动停止采集，便于下一位协作者继续定位。
