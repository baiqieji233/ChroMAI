# 训练与生成结构修复交接说明

## 目的与边界

这份文件交给后续具备更完整谱面/音频专业知识的智能体团队，作为继续审查和修复的起点。用户明确要求：不要在本轮直接展开结构性改造；其中一些结论需评估或先验证可行性。**本轮只整理交接，没有修改训练、生成、模型或数据筛选代码，也没有启动训练/生成。**

当前已有的只读审计报告：[STRUCTURE_AUDIT.md](STRUCTURE_AUDIT.md)。其中有统计、路径和初步建议；本文件补充用户最新的优先级与操作边界，并标出哪些结论不能直接当成定论。

## 用户当前意图

1. 对“条件与音频冗余、导致雷达/风格控制弱”这一判断先做专业评估；必要时再考虑改动。不要把相关性或单次敏感度测量直接当成因果证明。
2. 音频窗口超过 `max_audio_tokens` 时的池化问题，必须专门验证可行性后才能操作。需要先核实实际帧数分布、池化影响、替代参数对缓存/契约/checkpoint/显存和训练时长的影响，再给出决策。
3. 早停与学习率调度冲突是用户已感受到的问题，用户此前明确同意直接修复；但在本轮最新指示下，**尚未开始实现**。后续团队可将其作为明确的代码修复项。
4. 空窗/稀疏窗比例问题由用户通过训练集调整尝试修正。不要擅自改数据样本构成或 `<eos>` 权重。
5. 成对难度监督需要谨慎评估，不要因低难度谱面可解析就直接纳入、复制或重采样。先检查谱面语义质量、同曲难度间对齐关系、训练分布偏置和评估方法。
6. 难度曲线可以作为设计参考，但本轮不要求实现。
7. 用户此前要求难度筛选可调整：允许 Basic、Advanced、Expert 等级参与训练，并希望能在 WebUI 中选择最低难度或具体允许纳入的谱面。该项应纳入后续设计评估；在选定策略、契约和验证方式前，不要擅自扩大数据集或改筛选默认值。

## 审计背景与可复核事实

### 难度条件与难度筛选

- 当前训练集选择逻辑在 `src/maichart/training/event_dataset.py` 中对 `difficulty_index` 和 `level` 有硬筛选；原始审计观察到当前有效训练范围主要是 lv 12–15。
- 只读解析抽样统计显示 manifest 的难度槽 2–6 有大量可解析谱面；槽位名称映射及数据质量、是否适宜训练，必须由后续团队再对照数据准备流程核验。**“可解析”不等于“可作为高质量监督”。**
- 后续可配置筛选至少要区分：难度槽/类别白名单、最低/最高等级、可选谱面 allowlist 或排除列表；配置要写入训练参数、数据集签名/checkpoint 元数据和 WebUI 作业记录，避免同名 checkpoint 对应不同训练集。
- UI 应能显示筛选后各难度档的谱面数、歌曲数、窗口数与排除原因；配置改变后必须重新构建/验证数据集，不能只改界面展示。

### 条件响应与曲内变化

- 已有一次模型敏感度测量：`note_density` 变化时 next-token 分布差异约 1.2%，`level` 变化时约 19%。这说明当前 checkpoint 对两类输入的响应不同，但**不能单独证明“条件与音频冗余”是因果根因**。
- `condition_mask_prob` 已从多个 checkpoint 的真实 args 核实为 0.5，不应引用早期误判“15/16 条件维恒为 0.5”。训练样本一部分使用目标谱面统计条件，一部分使用掩码条件。
- 条件目前按整首 chart 计算并在多个窗口间复用，因此没有显式表达每个 16 拍窗口的难度/风格目标。逐窗条件、音频派生强度、用户曲线和成对监督是不同设计，不应混为一个改动。
- CFG null 与训练掩码值不一致是一个真实实现差异；但对同一 null 下两组请求的相对差异测量几乎不变（0.0348 vs 0.0347），因此不要把该差异直接宣称为 density 响应弱的根因。

### 音频池化可行性待验证

- 既有只读帧数统计：输入帧数 p50 约 533、p90 约 701、p99 约 960、最大约 2193；当前 `max_audio_tokens=512`，超限时走 `adaptive_avg_pool1d`（`src/maichart/generation/event_model.py`）。
- 池化压缩程度并不均一：中位数约 4%，p90 约 27%，p99 约 47%。因此“整体时间分辨率都被抹平”是过度表述，重点应核查长尾样本及其谱面误差。
- `audio_margin_beats=4` 或将 token 上限提高到 1024 都只是候选方案，不是已批准实施项。需比较音频缓存签名变化、训练/推理一致性、显存峰值、速度和长尾窗口质量，再决定。

### 早停/调度问题（已同意修复，但尚未改）

- checkpoint args 显示当前 run 使用 `patience=5`；审计记录的训练轨迹为 best val loss 约 0.7384@epoch 18、val 相邻变化标准差约 0.0403，epoch 22 才降低学习率，epoch 23 早停。
- 这提示 early stopping 与 `ReduceLROnPlateau` 的等待窗口可能冲突，但需要修复时应先检查当前训练代码及真实 run 的 scheduler 状态/恢复逻辑，不能只机械把 patience 改成 15。
- 后续实现应明确一个互相兼容的策略（例如让 scheduler 有充分降 lr 后观察期，或换 warmup+cosine），保证 resume checkpoint 可恢复 scheduler/early-stop 状态，并添加单元测试覆盖“降 lr 后不会立刻早停”和 resume 行为。
- 用户此前允许直接修改这一点；**本轮没有进行修改**。

## 后续团队建议工作顺序

1. 复核数据 manifest 的难度槽映射、筛选规则及谱面质量，设计 WebUI 可调筛选配置与可追溯的 dataset signature；先给出方案和统计，不要直接扩大训练集。
2. 对“条件弱响应”的因果解释做可控对照：固定音频、比较输入条件、验证条件掩码和 CFG 对绝对分布/相对差异的影响；对“逐窗条件/曲线/成对难度监督”分别提出实验，不要一次混合改动。
3. 专门验证音频池化：从真实训练样本重算帧长与池化比例，选取长尾窗口做时间对齐/谱面质量对照；测算 512、768、1024 上限以及 margin 4 的显存和吞吐，再决定参数与缓存契约。
4. 修复早停与学习率调度：先锁定实际恢复和保存语义，再修改训练参数/逻辑并添加测试。
5. 等用户完成训练集稀疏度调整后，再统一评估空窗、弱音、曲内密度 CV 与 `<eos>` 行为。
6. 成对难度监督和用户难度曲线分别评审；先验证语义、样本配比、评价指标与失败回退方案，再决定是否改契约。
